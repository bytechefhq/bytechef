White-label execution means your customers use ByteChef's integrations, workflow engine and workflow builder from inside your product, not from a ByteChef UI. This page describes what your customers see, how their workflows run, and which isolation guarantees the platform provides.

Two levels of separation apply:

- **Connected user** - one end user of your product, identified by the external user id your backend puts in the JWT `sub` claim. Each connected user has their own connections, integration instances and workflows.
- **Tenant** - one organization on a ByteChef installation. A single-tenant installation (`BYTECHEF_TENANT_MODE=SINGLE`, the default) has exactly one tenant. In multi-tenant mode (`MULTI`, Enterprise) each tenant gets its own database schema. See [Multi-tenancy](/platform/use-bytechef/self-hosted/architecture#multi-tenancy).

In a typical embedded setup, your company is the tenant and your customers' users are connected users.

## Architecture

```
       Your SaaS product
       ┌────────────────────────────────┐
       │  Your UI / Your branding       │
       │  ┌──────────────────────────┐  │
       │  │  ByteChef-rendered       │  │
       │  │  surfaces (SDK)          │  │  ◄── iframe or hosted dialog
       │  └──────────────────────────┘  │
       │  ┌──────────────────────────┐  │
       │  │  Your business logic     │  │
       │  └──────────────────────────┘  │
       └────────────────────────────────┘
                      │  JWT per end user
                      ▼
       ┌────────────────────────────────┐
       │  ByteChef Enterprise           │
       │  ┌──────────────┐  ┌────────┐  │
       │  │ Connected    │  │ Conn.  │  │
       │  │ user A       │  │ user B │  │  ◄── per-user connections
       │  └──────────────┘  └────────┘  │      and workflows
       └────────────────────────────────┘
```

The `@bytechef/embedded` SDK renders ByteChef surfaces inside your pages: the Connect dialog, the activation dialog, the Automation Hub, the Integration Marketplace and the workflow builder. The Automation Hub, the Integration Marketplace and the workflow builder load in an iframe that you position. Your product controls the surrounding navigation, wording and layout. See [Theming and Localization](/platform/embedded/build/theming-and-localization) for what you can restyle.

## The customer flow

{/* TODO screenshot: the embedded workflow builder rendered inside a host app's UI, white-labeled with the host product's branding */}

1. The customer signs in to your product.
2. Your backend mints a short-lived JWT for that user. See [Installing the SDK](/platform/embedded/get-started/initial-setup/installing-the-sdk).
3. The customer opens your integrations page, which lists the integrations and automation templates you published.
4. The customer connects their account in an external system (Salesforce, Slack and so on) through the standard authorization flow. ByteChef stores the credential in [encrypted credential storage](/platform/use-bytechef/self-hosted/configuration#encryption-of-stored-credentials), attached to that connected user.
5. The workflow runs each time its trigger fires.

You see every run in the ByteChef admin UI under **Embedded** → **Workflow Executions**. The SDK does not include an execution history view for end users.

When you embed the workflow builder, the component palette is the built-in catalog, optionally restricted with the `includeComponents` prop of `EmbeddedWorkflowBuilder`.

## Integration models

| Model | What the customer does | Built with |
|---|---|---|
| **Pre-built integrations and templates** | Picks an integration or automation template, connects an account, fills in inputs and turns it on. | [Integrations](/platform/embedded/build/integrations), [Automations](/platform/embedded/build/automations), the Connect dialog and the Automation Hub |
| **Builder access** | Builds their own workflows in the visual editor. | `EmbeddedWorkflowBuilder`, or the **New Workflow** tab of the Automation Hub |

You can combine both: offer templates as the default and expose the builder to advanced users.

## How a customer's workflow runs

When a customer's workflow runs:

- It runs on your ByteChef deployment.
- It uses that connected user's connections (their Salesforce key, their Slack token).
- It can use the built-in components and any [custom components](/platform/settings/components/custom-components) you publish for your own product.
- It records an execution in the history for that connected user.

## Tenant-isolated security

This section lists what the platform guarantees, what you configure yourself, and where the guarantees end.

### Built-in guarantees

These apply without configuration, including on a single-tenant deployment, where every request resolves to the one tenant.

| Guarantee | Behavior |
|---|---|
| **Requests resolve to one tenant first** | Every request (API call, webhook, scheduled run, MCP call) resolves its tenant before it reads any data and stays on that tenant for its whole lifetime. For an embedded JWT, the tenant comes from the Signing Key named in the token's `kid` header. List endpoints return the contents of one tenant only. |
| **Credentials are encrypted and never returned** | Connections are encrypted before they reach the database. Read endpoints obfuscate them. The plaintext exists only in memory while a workflow that uses the connection runs. |
| **Connections belong to a connected user** | A connection a connected user authorizes is bound to that user and is not offered to other connected users. The exception is a connection that a tenant admin explicitly marks as shared on the **Embedded** → **Connections** page. |
| **Requests are bound to the token's user** | On the public API, a JWT can act only for the user in its `sub` claim. A request whose path names a different external user id is rejected. |
| **Knowledge bases stay in their tenant** | One tenant's indexed documents are never searched by another tenant. |
| **Logs carry the tenant** | Every log line includes the tenant id it was written for, so you can extract one tenant's audit trail. |

### Limits of the isolation

**The encryption key is per deployment, not per tenant.** Credentials are separated by the tenant boundary, not by separate key material. One key protects all stored credentials against a stolen database. External secret managers are not supported.

**Queues are shared.** Runs for all tenants and connected users pass through the same message broker. Each message carries its tenant. The data each run reads and writes is isolated; the broker is not.

**Metrics and traces are not tagged by tenant.** Logs are. For per-customer dashboards or alerts, derive them from the logs or add the tag in your own collector.

**There is no per-tenant or per-user rate limiting.** One customer's traffic can increase another customer's latency. See [Limits and Concurrency](/platform/embedded/configure/limits).

### Your responsibilities

- [ ] **Mint one JWT per end user**, with `sub` set to that user's id. Never reuse one token for several users. The token decides which connected user a request acts for.
- [ ] **Keep API Keys on your backend.** An API Key can act for any external user id you put in the request path.
- [ ] **Rate-limit per customer at your own ingress**, so one customer cannot degrade the others.
- [ ] **Supply the encryption key from your secret manager**, not from a checked-in configuration file (`BYTECHEF_ENCRYPTION_PROVIDER=PROPERTY` with `BYTECHEF_ENCRYPTION_PROPERTY_KEY`).
- [ ] **Back up the encryption key separately from the database.** A restored database without its key cannot decrypt any stored credential.

## What the platform provides

ByteChef provides the parts of an integration platform that you would otherwise build yourself:

- the visual workflow builder;
- the components (connectors);
- the execution engine;
- credential storage and OAuth handling;
- webhook ingress and scheduling;
- execution history and logs.

You provide the product wrapper: branding, billing, customer onboarding and your business logic. The [built-in components](/platform/automation/build/workflows/components) are maintained in ByteChef, so a new or updated provider arrives with a ByteChef upgrade rather than as integration code you write. Embedded runs in the ByteChef deployment you already operate; there is no separate service to deploy.
