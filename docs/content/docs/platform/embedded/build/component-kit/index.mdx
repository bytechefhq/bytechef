title: "Component Kit"
description: An API that exposes a connected user's integrations as actions your code calls, tools a language model calls, and triggers that send events to your backend.
---

**AI ComponentKit** is an API that exposes what a [connected user](/platform/embedded/monitor/connected-users) has connected as operations you run under that user's own credentials. One API covers every integration, so your backend acts through the user's ByteChef connections without per-integration code. Developers use it to call third-party operations from their own code, to give a language model tools, or to receive the user's events.

It exposes them three ways: **actions** for your code, **tools** for a model, and **triggers** that push the user's events to your backend.

## Actions, tools and triggers

An **action** is the unit ByteChef executes: one operation on one component, such as Slack's `sendChannelMessage`. Your code names it, supplies its input, and gets the result.

A **tool** is an action projected for a language model. A component publishes selected actions as tools; the platform gives each one a flat name, a description, and a JSON Schema, hands that catalogue to your model, and the model chooses.

The execution and the connection are the same for both. The two surfaces differ as follows:

|  | Action | Tool |
|---|---|---|
| **Who chooses it** | Your code, before the call | The model, at inference time |
| **Endpoint** | `POST /{externalUserId}/components/{componentName}/versions/{componentVersion}/actions/{actionName}` | `POST /{externalUserId}/tools` |
| **Address** | Component, version and action name, in the path | One flat name in the body, for example `SLACK_SEND_CHANNEL_MESSAGE` |
| **Coverage** | Every action the component defines | Only the actions the component publishes as tools |
| **Versioning** | Pinned in the path | Resolved server-side, always the component's current version |
| **Discovery** | None. Your code already knows what it calls. | `GET /{externalUserId}/tools`, scoped to that user |
| **Request body** | `{ "input": { ... } }` | `{ "name": ..., "parameters": { ... } }` |
| **Response** | `{ "result": ... }` | The result, unwrapped |
| **File input** | Binary and form-data uploads supported | Not supported |

Use tools when a model chooses the operation. Call the action when your code has already decided.

Both live under `/api/embedded/v1` and authenticate with an embedded [API key](/platform/embedded/administration/api-keys) (`Authorization: Bearer`). The optional `X-Environment` header selects `DEVELOPMENT`, `STAGING` or `PRODUCTION` and defaults to `PRODUCTION`. Your code never sees the user's credential: ByteChef resolves it from the connected user. If that user has more than one instance of the same integration, the optional `X-Instance-Id` header selects one.

The same tool catalogue is also reachable over **MCP**. An [MCP Server](/platform/embedded/configure/mcp-servers) exposes the same actions, and also whole workflows, to agents that speak that protocol. ComponentKit is the plain-HTTP path; MCP is the protocol path.

**Triggers** go the other way. Instead of your code calling the user's integrations, you subscribe a connected user to a component trigger, such as a new message in the user's Slack channel. The trigger runs under the user's own connection, and ByteChef posts each event to your webhook endpoint, signed with a secret only you and ByteChef know.

## In this section

- [Tools](/platform/embedded/build/component-kit/tools) - list a connected user's tool catalogue and run a tool a model chose.
- [Actions](/platform/embedded/build/component-kit/actions) - call an action your code has already chosen, including file input.
- [Triggers](/platform/embedded/build/component-kit/trigger-subscriptions) - subscribe a connected user to a component trigger and receive its events at your webhook endpoint.
