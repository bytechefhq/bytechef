ByteChef exposes a [Model Context Protocol (MCP)](https://modelcontextprotocol.io) server that lets AI assistants - such as Claude, Cursor, and Windsurf - interact directly with your ByteChef instance to manage projects, workflows, and components.

This is the **management** server: its tools operate on ByteChef itself. To publish your own component actions and workflows as tools for an assistant to call, use [MCP Servers](/platform/automation/deploy/mcp-servers) in the Automation workspace instead - that is a different server, with a different URL and a different tool set.

The management server is **on by default**. An administrator turns it off with:

```
BYTECHEF_AI_MCP_SERVER_ENABLED=false
```

See the [AI MCP Server configuration reference](/platform/use-bytechef/self-hosted/configuration/environment-variables#ai-mcp-server-configuration).

## Get Your MCP Server URL

{/* TODO screenshot: Settings → MCP Server page - the MCP server URL with the client tabs (Claude / Cursor / Windsurf / Other) */}

The management server has one URL: `https://<your-host>/api/management/mcp`. It is the same for every ByteChef account and contains no secret, so you can add it to an MCP directory or share it with teammates. ByteChef works out which account a request belongs to from the credential: an admin API key, or the account you signed in with (this requires the embedded authorization server - see [Sign in with ByteChef](#sign-in-with-bytechef-optional)).

1. Open ByteChef and go to **Settings** → **MCP Server**
2. Copy the **MCP server URL**. The snippets are grouped into per-client tabs - **Claude**, **Cursor**, **Windsurf**, and **Other**.

The server speaks the Streamable HTTP transport only.

The settings page is available to tenant admins only.

The URL alone is never enough to connect: every request must also carry a credential - see [Authentication](#authentication).

## Authentication

Every request must carry a credential: an admin API key or a sign-in through ByteChef itself. Requests without one are rejected with `401`. There is no anonymous mode.

> **Upgrading?** Earlier versions had a **Require authentication** setting that could be switched off. That setting is gone: a server that had it off now requires a credential like any other, so its clients must send one - see [API key](#api-key-default) below. Admin API keys are an Enterprise Edition feature; on Community Edition, connect by [signing in with ByteChef](#sign-in-with-bytechef-optional).

### API key (default)

Create an admin API key under **Settings** → **Admin API Keys** (an Enterprise Edition page) and send it with every request as a Bearer header:

```
Authorization: Bearer <your-api-key>
```

It must be an **Admin** API key. A workspace API key - the kind under **Settings** → **API Keys**, for the automation public API - is rejected here with `401`, because it is bound to a workspace while this server administers the whole account.

The connection snippets below include this header. An admin API key works in every environment: it is not checked against the `X-ENVIRONMENT` header, whichever environment it was created under. Tools that work inside a workspace take their own `environment` argument, which defaults to Development. A key that belongs to a deactivated user is rejected. Because the key is bound to your user account, the AI assistant acts with your permissions - and you can revoke a single client by deleting its key without touching the server URL or other clients.

### Sign in with ByteChef (optional)

When the embedded OAuth2 authorization server is enabled, an MCP client that supports OAuth can connect to `https://<your-host>/api/management/mcp` without an API key. The client registers itself, you sign in with your ByteChef account and approve the connection, and the client then acts with your permissions. An administrator can see and revoke these connections under [OAuth2 Clients](/platform/settings/oauth2-clients); a revoked connection stops working on its next request.

Two settings are needed. First, turn the server on with `BYTECHEF_OAUTH2_AUTHORIZATION_SERVER_ENABLED=true`. Second, tell ByteChef to trust its own tokens by adding an issuer entry for itself:

```
BYTECHEF_OAUTH2_RESOURCE_SERVER_ISSUERS_0_SELF=true
BYTECHEF_OAUTH2_RESOURCE_SERVER_ISSUERS_0_URI=<your public URL>
BYTECHEF_OAUTH2_RESOURCE_SERVER_ISSUERS_0_TENANT_CLAIM=tenant_id
```

If an external issuer already uses index `0`, add the self issuer at the next free index instead (for example `_1_`). Discovery advertises the first issuer, so put the self issuer at index `0` only when it should be the advertised sign-in.

Set `BYTECHEF_PUBLIC_URL` to the address clients use to reach ByteChef. The issuer, the discovery documents and the `401` challenge all name that address, and an MCP client refuses a server whose discovery names a different one - which is what happens behind a proxy when the public URL is not set.

What the client gets:

- **A consent screen every time a client asks for access** that you have not approved yet. Approving grants the requested scope (`mcp:management` here, `mcp:automation` for automation MCP servers) and nothing more.
- **A token for this URL only.** The access token names the MCP URL the client connected to; it does not work on another MCP server, and the client cannot exchange it for one.
- **An access token that lasts one hour and a refresh token that lasts 30 days.** The client renews the access token on its own, without sending you back to the browser. Each refresh token works once - the client gets a new one with every renewal - so a stolen refresh token is useless after the client's next renewal.

See [Environment Variables](/platform/use-bytechef/self-hosted/configuration/environment-variables#oauth2-configuration) for details.

## Connect an AI Assistant

<Tabs items={['Claude', 'Cursor', 'Windsurf', 'Other clients']}>
<Tab value="Claude">

**Claude.ai (web)**

> claude.ai integrations cannot send custom headers, so they cannot send the admin API key this server requires. Use Claude Desktop instead - unless the embedded authorization server is enabled, in which case claude.ai can connect to the tenant-less URL by signing in with ByteChef (see [Sign in with ByteChef](#sign-in-with-bytechef-optional)).

**Claude Desktop**

1. Open Claude Desktop
2. Go to **Settings** → **Developer** → **Edit Config** → **Open `claude_desktop_config.json`**
3. Add the following, replacing the URL with yours and `YOUR_API_KEY` with an admin API key:

   ```json
   {
     "mcpServers": {
       "ByteChef": {
         "command": "npx",
         "args": [
           "-y",
           "mcp-remote",
           "https://<your-host>/api/management/mcp",
           "--header",
           "Authorization: Bearer YOUR_API_KEY"
         ]
       }
     }
   }
   ```

4. Save the file, then quit and restart Claude Desktop

</Tab>
<Tab value="Cursor">

1. Open Cursor → **Settings** → **Cursor Settings** → **MCP** → **Add new global MCP server**

   ```json
   {
     "mcpServers": {
       "ByteChef": {
         "headers": {
           "Authorization": "Bearer YOUR_API_KEY"
   ```

## Available Tools

The MCP server exposes the following tools to connected AI assistants.

Tools that list, search or create things inside a workspace take a `workspaceId`. The assistant finds it with `listWorkspaces`; a call that needs a workspace and names none returns an error pointing there. Tools that take a project or workflow id act on that object directly, and your permissions in its workspace decide whether the call is allowed.

### Workspaces

| Tool | Description |
|---|---|
| `listWorkspaces` | List the workspaces you can access (all workspaces for an admin), with their ids |

### Projects

| Tool | Description |
|---|---|
| `createProject` | Create a new project |
| `updateProject` | Update an existing project |
| `deleteProject` | Delete a project |
| `getProject` | Get project details |
| `listProjects` | List the projects of a workspace |
| `searchProjects` | Search projects by keyword |
| `publishProject` | Publish a project |
| `getProjectStatus` | Get the current status of a project |

### Workflows

| Tool | Description |
|---|---|
| `createProjectWorkflow` | Create a new workflow in a project |
| `updateWorkflow` | Update an existing workflow |
| `deleteWorkflow` | Delete a workflow |
| `getWorkflow` | Get workflow details |
| `listWorkflows` | List the workflows of a project |
| `searchWorkflows` | Search workflows by keyword |
| `saveWorkflowTestConnection` | Select or create the connection a workflow uses when it is tested, in the current environment |

### Components & Actions

| Tool | Description |
|---|---|
| `listComponents` | List all available components |
| `getComponent` | Get component details |
| `searchComponents` | Search components by keyword |
| `listActions` | List the actions of all components |
| `getAction` | Get action details |
| `searchActions` | Search actions by keyword |
| `getActionDefinition` | Get the full definition of an action |
| `getOutputProperty` | Get output property details |
| `getProperties` | Get all properties of a trigger, action, or cluster element |
| `searchClusterElements` | Find components that support a given cluster element type |
| `getClusterElement` | Get cluster element details |

### Triggers

| Tool | Description |
|---|---|
| `listTriggers` | List the triggers of all components |
| `getTrigger` | Get trigger details |
| `searchTriggers` | Search triggers by keyword |
| `getTriggerDefinition` | Get the full definition of a trigger |

### Tasks

These tools address a *task* through a `type` argument - an action, a trigger, a task dispatcher, or, for some of them, a cluster element. `listTasks` and `searchTasks` cover actions, triggers and task dispatchers; `getTaskDefinition` does not accept cluster elements; `getTaskDispatcherBuildInstructions` takes no `type`.

| Tool | Description |
|---|---|
| `listTasks` | List tasks in the project, optionally filtered by type |
| `getTask` | Get details for one task of a given type |
| `searchTasks` | Search across actions, triggers, and task dispatchers |
| `validateTask` | Validate a task's structure and properties against its definition |
| `getTaskDefinition` | Get a JSON template for configuring the task in a workflow |
| `getTaskDispatcherBuildInstructions` | Get instructions for building with task dispatchers |
| `getTaskProperties` | Get a task's properties, including nested ones |
| `getTaskOutputProperty` | Get the structure of a task's output property |

### Task dispatchers

| Tool | Description |
|---|---|
| `listTaskDispatchers` | List all task dispatchers |
| `getTaskDispatcher` | Get task dispatcher details |
| `searchTaskDispatchers` | Search task dispatchers by keyword |
| `getTaskDispatcherDefinition` | Get the full definition of a task dispatcher |
| `getTaskDispatcherProperties` | Get a task dispatcher's properties |
| `getTaskDispatcherOutput` | Get a task dispatcher's output property |

### Editing a step in place

| Tool | Description |
|---|---|
| `updateScriptComponentCode` | Replace the code of a script component task |
| `updateClusterElementTask` | Update a cluster element attached to a task |
| `updateWorkflowRootProperties` | Merge root-level properties - label, description, inputs, outputs - into a workflow definition |

### Workspace resources

| Group | Tools |
|---|---|
| Skills | `getAiSkills`, `getAiSkill`, `createAiSkill`, `updateAiSkill`, `updateAiSkillContent`, `getAiSkillFilePaths`, `getAiSkillFileContent`, `createAdditionalFilesInSkill`, `removeFileInSkill` |
| MCP servers | `listMcpServers`, `createMcpServer`, `updateMcpServer`, `createMcpProject`, `cloneMcpProject`, `listMcpProjectWorkflows` |
| Deployments | `listProjectDeployments`, `createProjectDeployment`, `updateProjectDeployment`, `deleteProjectDeployment`, `rollbackProjectDeployment`, `toggleProjectDeployment`, `promoteWorkflow` |
| Knowledge bases | `listKnowledgeBases`, `queryKnowledgeBase`, `createKnowledgeBase`, `addKnowledgeBaseDocument`, `deleteKnowledgeBaseDocument`, `cloneKnowledgeBase`, `deleteKnowledgeBase` |

### Delegate tools

Some capabilities are exposed as a single delegate tool that takes a natural-language instruction and calls the underlying operations itself, rather than as a flat list of tools like the ones above. Each accepts a `workspaceId` (find it with `listWorkspaces`).

| Tool | Description |
|---|---|
| `buildWorkflow` | Designs, edits, debugs or explains a workflow |
| `importWorkflow` | Converts a workflow definition from another tool (n8n, Make, Zapier, Workato, …) into an existing ByteChef workflow |
| `configureClusterElement` | Designs, edits or explains cluster elements, such as an AI Agent's model, chat memory, RAG source, guardrails or tools |
| `writeScript` | Writes, edits, debugs or explains the JavaScript, Python or Ruby code of a script task |
| `authorSkill` | Lists, explains, creates or updates skills |
| `debugWorkflowExecution` | Inspects or diagnoses a past workflow run and fixes the underlying workflow |
| `configureMcpServer` | Writes the tool name, tool description and per-input `fromAi(...)` mapping of every workflow already attached to an MCP server; it never creates the server, attaches workflows or enables it |
