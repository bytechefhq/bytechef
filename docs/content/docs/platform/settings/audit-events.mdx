**Settings → Audit Events** records privileged actions across the platform. Recording is automatic - there is no per-resource opt-in and no way for a user to suppress an entry. The page requires the `ADMIN` authority and is Enterprise Edition.

## Finding an event

The **Search** box on the right of the page header matches events whose principal or any recorded event data value contains the text you type, ignoring case, e.g. `admin` or `createProject`. It applies shortly after you stop typing, surrounding spaces are ignored, and `%`, `_` and `\` are matched literally. When [principals are masked](#masking-principals), Search matches event data values only.

The filter button next to it opens the **Filter Audit Events** menu. The button is highlighted while any menu filter is active.

| Menu group | What it does |
|---|---|
| **Event type** | Restrict to one event type; **All** clears it. A check mark shows the active choice. |
| **Platform** | **All**, **Automation**, or **Embedded**. Entries without a platform appear only under **All**. |
| **Date** | **All time**, **Last 24 hours**, **Last 7 days**, **Last 30 days**, or **Custom range**. The presets count back from the moment you pick them. **Custom range** opens a small panel with **From** and **To** date pickers; a range starts at the beginning of the **From** day and ends at the end of the **To** day, in your local time. |

**Clear all filters** at the bottom of the menu resets the menu filters and leaves the search text as it is. It is disabled when no menu filter is active.

Each active menu filter appears as a chip above the table, e.g. **Event type: JOB_FAILED**, **Platform: Embedded**, **Last 7 days**, or **From:** / **To:** for a custom range. Click the **×** on a chip to remove that filter, or **Clear all** to remove every menu filter. The search text has no chip; clear the Search box to remove it. Changing the search or a filter always returns to the first page of results. A failed sign-in is recorded under the name that was typed, so searching that name finds it. With no matches the table reads "No audit events match the current filters."

The results table lists **Date**, **Principal**, **Platform** (**Automation**, **Embedded**, or a dash when the entry has none), and **Event Type**. Clicking a row opens the **Audit Event Details** panel, showing the event type with its timestamp, the **Principal**, the **Platform**, the **Event ID**, and the event's recorded **Data** as key/value pairs. When results span multiple pages, **Previous** / **Next** page through them.

## What an entry contains

Each entry is a row in `persistent_audit_event` plus its data map in `persistent_audit_event_data`:

- **Event ID** - the entry's identifier.
- **Principal** - the acting user's login.
- **Platform** - **Automation** or **Embedded**, the side of the product the action belongs to. API key events take it from the key's own type, job events from the job's owner, and other actions from the area of the product that performed them. Sign-in events, platform-wide actions, and entries recorded before the platform was tracked have none.
- **Event type** - the verb, e.g. `WORKFLOW_UPDATED`, `CONNECTION_DELETED`. The full set is catalogued below.
- **Event date** - when it happened.
- **Data** - a string-to-string map of whatever the emitting site chose to record, typically the affected resource's id and name. Null values are dropped rather than stored.

Anything you want to filter on later has to be in the **Data** map - that is what **Search** matches besides the principal.

### Correlation IDs for bulk operations

A single admin action that fans out into many writes - reassigning every connection in a workspace, for example - would otherwise read as dozens of unrelated entries. When a bulk operation establishes a correlation scope, every audit event raised beneath it picks up the same id and records it under the `correlationId` data key, so the timeline can be reassembled without relying on timestamps being close together.

The correlation id is carried in a plain thread-local, deliberately not an inheritable one: work handed to another thread does not inherit it, because leaking a correlation id across a recycled pool thread is worse than losing the grouping.

### Strict-audit events

Some events are marked *strict*: if the audit entry cannot be written, the operation itself fails rather than proceeding unrecorded. The events that can remove someone's access are the ones marked this way - `CONNECTION_DELETED`, `CONNECTION_VISIBILITY_CHANGED`, `CONNECTION_ACCESS_REVOKED`, `CONNECTION_REASSIGNED`, and `AI_HUB_CHAT_DELETED`. A failed non-strict write is counted on the `bytechef_connection_audit_failed` / `bytechef_ai_hub_audit_failed` counters instead of failing the request.

## Event types

The **Event type** group of the filter menu is populated from the events your instance has actually recorded. The full set the platform can emit:

| Area | Event types |
|---|---|
| **Users** | `USER_CREATED`, `USER_ACTIVATED`, `USER_PASSWORD_CHANGED`, `USER_DELETED` |
| **SCIM provisioning** | `SCIM_USER_CREATED`, `SCIM_USER_UPDATED`, `SCIM_USER_PATCHED`, `SCIM_USER_DEACTIVATED`, `SCIM_USER_DELETED`, `SCIM_GROUP_CREATED`, `SCIM_GROUP_UPDATED`, `SCIM_GROUP_DELETED` - recorded under the `scim:<identity provider name> (<identity provider id>)` principal; a PUT or PATCH that deactivates an active user is recorded once, as `SCIM_USER_DEACTIVATED` |
| **Workspace membership** | `WORKSPACE_USER_ADDED`, `WORKSPACE_USER_REMOVED`, `WORKSPACE_USER_ROLE_UPDATED`, `WORKSPACE_USER_ENVIRONMENT_ROLE_UPDATED`, `WORKSPACE_USER_ENVIRONMENT_ROLE_REMOVED` |
| **Custom roles** | `CUSTOM_ROLE_CREATED`, `CUSTOM_ROLE_UPDATED`, `CUSTOM_ROLE_DELETED` |
| **Projects** | `PROJECT_CREATED`, `PROJECT_UPDATED`, `PROJECT_DELETED` |
| **Workflows** | `WORKFLOW_CREATED`, `WORKFLOW_UPDATED`, `WORKFLOW_DELETED` |
| **Deployments** | `DEPLOYMENT_CREATED`, `DEPLOYMENT_UPDATED`, `DEPLOYMENT_ENABLED`, `DEPLOYMENT_DISABLED`, `DEPLOYMENT_DELETED` |
| **Connections** | `CONNECTION_CREATED`, `CONNECTION_DELETED`, `CONNECTION_VISIBILITY_CHANGED`, `CONNECTION_ACCESS_GRANTED`, `CONNECTION_ACCESS_REVOKED`, `CONNECTION_REASSIGNED`, `WORKFLOW_PAUSED` |
| **API keys** | `API_KEY_CREATED`, `API_KEY_DELETED`, `WORKSPACE_API_KEY_CREATED`, `WORKSPACE_API_KEY_DELETED` |
| **Custom components** | `CUSTOM_COMPONENT_CREATED`, `CUSTOM_COMPONENT_UPDATED`, `CUSTOM_COMPONENT_DELETED`, `CUSTOM_COMPONENT_ENABLED`, `CUSTOM_COMPONENT_DISABLED`, `CUSTOM_COMPONENT_PUBLISHED` |
| **Data tables** | `DATA_TABLE_CREATED`, `DATA_TABLE_COLUMN_ADDED`, `DATA_TABLE_DELETED` |
| **Knowledge bases** | `KB_CREATED`, `KB_UPDATED`, `KB_DELETED`, `KB_ASSIGNED_TO_WORKSPACE`, `KB_REMOVED_FROM_WORKSPACE` |
| **API collections** | `API_COLLECTION_CREATED`, `API_COLLECTION_DELETED` |
| **MCP** | `MCP_PROJECT_CREATED`, `MCP_PROJECT_DELETED` |
| **Context store** | `CONTEXT_STORE_SOURCE_CREATED`, `CONTEXT_STORE_SOURCE_DELETED`, `CONTEXT_STORE_SOURCE_ENABLED`, `CONTEXT_STORE_SOURCE_DISABLED` |
| **AI Hub** | `AI_HUB_WORKSPACE_SETTINGS_UPDATED`, `AI_HUB_CHAT_CREATED`, `AI_HUB_CHAT_DELETED` |
| **Integrations (embedded)** | `INTEGRATION_CREATED`, `INTEGRATION_UPDATED`, `INTEGRATION_DELETED` |
| **Jobs** | `JOB_CREATED`, `JOB_STARTED`, `JOB_COMPLETED`, `JOB_FAILED`, `JOB_STOPPED` - recorded under the `SYSTEM` principal, with the job id in the data |
| **Access checks** | `PERMISSION_CHECK` - a guarded call that was denied or failed, or a successful call that changes something; successful reads are not recorded |

## What is not logged

- **Secret values.** The log records that a credential was created or deleted, by whom, and when - never the secret material.
- **Workflow execution data.** Execution inputs and outputs live in execution history, so the audit log stays focused on privileged administrative actions rather than data flow.

## Retention

Audit entries persist in your operational database. A scheduled job deletes entries older than the retention window:

| Property | Default | Meaning |
|---|---|---|
| `bytechef.audit.retention-days` | `365` | Age at which an entry is purged. |
| `bytechef.audit.retention-cron` | `0 0 2 * * *` | When the purge runs - daily at 02:00 local time. |

A `retention-days` of zero or less disables the purge rather than deleting the whole trail. Retention is instance-wide, not per workspace.

## Masking principals

Set `bytechef.audit.mask-principals` to `true` to mask principals when entries are read through the API, e.g. `a***@example.com`. The stored entries are unchanged. While masking is on, **Search** does not match principals at all, so it cannot be used to probe for logins; it matches event data values only.
