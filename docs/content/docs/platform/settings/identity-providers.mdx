Identity providers let users sign in to ByteChef through your organization's SAML 2.0 or OIDC identity provider (IdP) instead of a local password. Administrators register each provider on **Settings → Identity Providers** and route users to it by email domain.

<Callout title="Availability">
    External identity provider federation is an Enterprise Edition feature, enabled with `bytechef.security.sso.enabled` (`BYTECHEF_SECURITY_SSO_ENABLED`). The **Settings → Identity Providers** page is behind the `ff-1040` feature flag and requires the `ADMIN` authority. Community Edition ships local email/password login, plus optional [social login](#social-login) with Google and GitHub.
</Callout>

---

## Protocols

Two protocols are supported:

- **SAML 2.0** - assertion-based SSO, used by ADFS, Shibboleth, and similar IdPs.
- **OIDC** - for IdPs such as Okta, Auth0, Google Workspace, Keycloak, and Microsoft Entra ID.

The IdP must publish a SAML metadata URL or an OIDC discovery document (`.well-known/openid-configuration`).

Providers are registered at runtime. Metadata URLs, client IDs and secrets can be changed without a redeploy, and in a multi-tenant deployment each tenant registers its own providers.

## The providers list

**Settings → Identity Providers** lists configured providers with these columns: **Name**, **Type**, **Issuer / Metadata URI**, **Domains**, **Status**, and **Enforced**, plus per-row edit and delete actions. **Add Identity Provider** opens the configuration dialog.

## Configuring a provider

The dialog is titled **Add Identity Provider** (or **Edit Identity Provider**) and adapts to the selected **Type**:

| Field | Applies to | Purpose |
|---|---|---|
| **Type** | Both | `OIDC` or `SAML`. Cannot be changed after the provider is created. |
| **Name** | Both | Display name for the provider, e.g. `Acme Corp SSO`. |
| **Issuer URI** | OIDC | Issuer whose `.well-known/openid-configuration` is auto-discovered, e.g. `https://accounts.google.com`. |
| **Client ID** / **Client Secret** | OIDC | OAuth client credentials. The secret can be left blank on edit to keep the current one. |
| **Scopes** | OIDC | Requested scopes, e.g. `openid,profile,email`. |
| **Metadata URI** | SAML | IdP metadata URL used to auto-configure endpoints and certificates. |
| **Signing Certificate (optional)** | SAML | PEM certificate, when the metadata does not carry one. |
| **NameID Format (optional)** | SAML | Email Address, Unspecified, Persistent, Transient, or **Default (from metadata)**. |
| **Email Domains** | Both | Domains that route users to this provider at login, added and removed as chips. |
| **Default Role** | Both | `ROLE_USER` or `ROLE_ADMIN`, granted to users created through this provider. |

Four checkboxes control behavior:

| Checkbox | Description |
|---|---|
| **Auto-provision users on first SSO login** | Creates a ByteChef account, with the **Default Role**, the first time an unknown user signs in through the provider. |
| **Enforce SSO (block password login for matching domains)** | Users whose email domain is listed in **Email Domains** cannot sign in with a password. |
| **Enabled** | Turns the provider on or off without deleting it. |
| **Require MFA (policy only)** | Stores an MFA policy flag. The **MFA Method** selector (TOTP or Email) is disabled, and the flag is not enforced. |

For SAML, editing a saved provider exposes a **Download SP Metadata** button to hand to your IdP.

### MCP servers

Identity providers configured here are used for signing in to ByteChef. MCP servers do not accept their tokens. To connect an automation MCP client with a token from an external issuer, list that issuer in the installation's configuration. See [MCP Servers → JWT from a trusted issuer](/platform/automation/deploy/mcp-servers#jwt-from-a-trusted-issuer-optional).

## What gets federated

- **Authentication** - the IdP performs the login, and ByteChef trusts the SAML assertion or OIDC ID token.
- **Identity attributes** - email and display name.
- **Provisioning** - with **Auto-provision users on first SSO login**, accounts are created at first sign-in. Multi-tenant deployments also expose SCIM 2.0 endpoints under `/api/scim/v2` (`Users`, `Groups`), authenticated with the identity provider's SCIM API key as a bearer token. The dialog does not expose this key. SCIM groups map to organization authorities, not to workspace roles.

## What does not get federated

Service credentials that workflows use (API keys, OAuth tokens, and basic-auth secrets) stay in ByteChef's encrypted [connection](/platform/settings/connections) storage. SSO governs user identities, not workflow credentials.

## Migrating from local accounts

Existing local accounts are matched by email. After SSO works for your users, select **Enforce SSO** on the provider to block password login for its email domains.

## Social login

<Callout type="warn" title="Coming soon">
    Social login is on the upcoming release track and is not yet available in the latest released version of ByteChef.
</Callout>

In addition to local email and password, users can sign in with **Google** or **GitHub**. Enable it with `bytechef.security.social-login.enabled` (`BYTECHEF_SECURITY_SOCIAL_LOGIN_ENABLED`) and supply each provider's client ID and secret. Social login is separate from the IdP federation above and is available in Community Edition.

## Two-factor authentication

<Callout type="warn" title="Coming soon">
    Two-factor authentication is on the upcoming release track and is not yet available in the latest released version of ByteChef.
</Callout>

For local accounts, ByteChef can require a time-based one-time password (TOTP) as a second factor at sign-in, enabled with `bytechef.security.two-factor-authentication.enabled` (`BYTECHEF_SECURITY_TWO_FACTOR_AUTHENTICATION_ENABLED`). Users register an authenticator app and enter the rotating code after their password.
