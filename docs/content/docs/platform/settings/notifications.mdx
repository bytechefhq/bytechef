---
title: Notifications
description: Send an email, Slack message, or webhook when a workflow run reaches a given status - create, edit, and delete notification rules.
---

A **notification** is a rule that says *"when a job reaches this status, tell this target"*. Each rule
names one or more job lifecycle events and one delivery target: an email address, a Slack channel, or a
webhook URL. When a workflow run hits one of those
events, every notification subscribed to it fires.

**Settings → Notifications** requires the `ADMIN` authority. Unlike most of the Settings area, the page
is available in both Community and Enterprise Edition. The **Email** delivery type works in both
editions; the **Slack** and **Webhook** delivery types are Enterprise Edition only. Slack as an approval
channel in a workflow is a separate feature of the Slack component and is not affected.

## The page

The header reads **Notifications**, with a **New Notification** button. With no rules yet, the body
shows an empty state titled **No Notifications** with the message "You do not have any Notifications
created yet."

| Column | Description |
|---|---|
| **Name** | The label you gave the rule. |
| **Events** | The subscribed events, one badge each. |
| **Last Modified Date** | When the rule last changed. |
| **Last Modified By** | Who changed it. |
| **Actions** | An **edit** (pencil) and a **delete** (trash) button. |

## Create a notification

1. Click **New Notification**. The **Create Notification** dialog opens, described as "Define
   notification parameters."
2. Enter a **Name** - required, up to 256 characters.
3. Pick one or more **Events** from the multi-select. At least one is required.
4. Choose a **Type**.
5. Fill in the type's fields.
   For a Webhook, you can also pick a **Preset** first, which fills in the URL, headers and body template
   for a vendor. See [Presets](#presets).
6. Click **Save**.

Editing works the same way: the pencil icon reopens the dialog, titled **Edit Notification**, with the
current values loaded.

## Events

Events are job lifecycle transitions. The full set:

| Event | Fires when |
|---|---|
| `JOB_CREATED` | A run has been created but not started. |
| `JOB_STARTED` | A run has started executing. |
| `JOB_COMPLETED` | A run finished successfully. |
| `JOB_FAILED` | A run failed. |
| `JOB_CANCELLED` | A run was cancelled before it ever started. |
| `JOB_STOPPED` | A run was stopped mid-execution. |

The list is not per-workspace or per-project: a notification subscribes to an event across the whole
deployment.

## Delivery types

| Type | Field | Edition | Notes |
|---|---|---|---|
| **EMAIL** | **Email** - the recipient address. | Community and Enterprise | The default. Requires a mail host to be configured; without one the send is skipped with a warning. |
| **SLACK** | **Slack Webhook URL** - a Slack [incoming webhook](https://api.slack.com/messaging/webhooks) URL. | Enterprise only | Posts one message to the channel the incoming webhook belongs to. |
| **WEBHOOK** | **Webhook URL** - any HTTPS or HTTP endpoint. | Enterprise only | Sends a JSON `POST` to the URL. See [Webhook requests](#webhook-requests). |

In Community Edition the **Type** dropdown offers only **Email**, and the API refuses to save a Slack or
Webhook notification. A Slack or Webhook notification created earlier under an Enterprise license is kept
but skipped, with a warning in the server log, while the deployment runs as Community Edition.

### Message content

Email subject and body come from the platform's message bundle, parameterised with the workflow's
label and the job id. A Slack message carries the same text as the email body, prefixed with an emoji. There is no
per-notification template for Email and Slack; only Webhook has a [body template](#body-template).

Email and Slack messages now end with the same details lines, one per line, each shown only when the
value is known: `Workflow`, `Project` (with the version, for example `CRM (v3)`), `Environment`,
`Failed task` (with the task type), `Error` and `Execution` (the link to the run).

### Webhook requests

Each delivery is a single `POST` with a `Content-Type: application/json` body. The body starts with the
fields it has always had (`eventType`, `jobId`, `jobName` and `timestamp`). These are unchanged. A summary of the event is added beside
them:

| Field | Type | Present when |
|---|---|---|
| `eventType` | string | Always. |
| `jobId` | number | Always. |
| `jobName` | string | Always. |
| `timestamp` | string | Always. ISO-8601, for example `2026-11-03T10:00:00Z`. |
| `deliveryId` | string | Always. Unique per delivery: each notification gets its own id, and the value equals the `X-ByteChef-Delivery` header. |
| `source` | string | The job belongs to an automation project (`AUTOMATION`) or an embedded integration (`EMBEDDED`). |
| `job.id` | number | The job exists. |
| `job.name` | string | The job has a name. |
| `job.status` | string | The job has a status, for example `FAILED`. |
| `job.startDate` | string | The run has started. ISO-8601. |
| `job.endDate` | string | The run has ended. ISO-8601. |
| `job.durationMillis` | number | The run has started and ended. |
| `workflow.id` | string | The job has a workflow. |
| `workflow.name` | string | The workflow still exists. A deleted workflow still gives `workflow.id`. |
| `project.id` | number | The project could be resolved. For an embedded job, the integration id. |
| `project.name` | string | The project could be resolved. For an embedded job, the integration name. |
| `project.version` | number | The project could be resolved. For an embedded job, the integration version. |
| `environment` | string | The environment could be resolved: `DEVELOPMENT`, `STAGING` or `PRODUCTION`. |
| `error.taskName` | string | `JOB_FAILED` only, when a failed task was found. |
| `error.taskType` | string | `JOB_FAILED` only, when a failed task was found. |
| `error.message` | string | `JOB_FAILED` only, and only when the failing task's error has a message. Cut to 1000 characters. |
| `error.stackTrace` | string | `JOB_FAILED` only, when the error has a stack trace. Cut to 2000 characters. |
| `executionUrl` | string | `bytechef.public-url` is set and the run's project or integration could be resolved. Opens the execution. |

A field that has no value is left out of the body, not sent as `null`. If a lookup fails (for example
the workflow was deleted), the field is left out and the notification is still sent.

`deliveryId` is the same value as the `X-ByteChef-Delivery` header, and `timestamp` is the same moment
as the `X-ByteChef-Timestamp` header. The header is in milliseconds since the epoch, the body field is
ISO-8601.

`executionUrl` opens the execution in ByteChef: `<public-url>/automation/executions?id=<jobId>` for an
automation run and `<public-url>/embedded/executions?id=<jobId>` for an embedded run. It is left out
when `bytechef.public-url` is not set.

Task inputs and outputs are never included. Open the execution through `executionUrl` to see them.

A `JOB_FAILED` event from an automation run:

```json
{
  "eventType": "JOB_FAILED",
  "jobId": 1042,
  "jobName": "Sync new leads",
  "timestamp": "2026-11-03T14:03:27.512Z",
  "deliveryId": "6f1c2d3e-8a4b-4c5d-9e6f-7a8b9c0d1e2f",
  "source": "AUTOMATION",
  "job": {
    "id": 1042,
    "name": "Sync new leads",
    "status": "FAILED",
    "startDate": "2026-11-03T14:03:25.101Z",
    "endDate": "2026-11-03T14:03:27.480Z",
    "durationMillis": 2379
  },
  "workflow": {
    "id": "wf-3a9f1c",
    "name": "Sync new leads"
  },
  "project": {
    "id": 7,
    "name": "CRM",
    "version": 3
  },
  "environment": "PRODUCTION",
  "error": {
    "taskName": "Create contact",
    "taskType": "hubspot/v1/createContact",
    "message": "401 Unauthorized",
    "stackTrace": "com.bytechef.exception.ConfigurationException: 401 Unauthorized\n\tat ..."
  },
  "executionUrl": "https://bytechef.example.com/automation/executions?id=1042"
}
```

Every request carries these headers:

| Header | Value |
|---|---|
| `X-ByteChef-Event` | `job.status` |
| `X-ByteChef-Timestamp` | The send time, in milliseconds since the epoch. |
| `X-ByteChef-Delivery` | A random UUID, unique per delivery. It equals `deliveryId` in the body. Use it to deduplicate. |
| `X-ByteChef-Signature` | Only when the notification has a signing secret. See [Verifying signatures](#verifying-signatures). |

The URL must use `http` or `https` and must resolve to a public address: loopback, private,
link-local and carrier-grade NAT ranges are refused. On a self-hosted instance, to reach an internal
receiver, list its host in `bytechef.webhook-delivery.allowed-hosts` (comma-separated, for example
`alerts.internal,10.0.0.5`). A listed host must match the URL's host exactly and skips the address
check. The same list applies to Slack notifications. Each request has a 10-second connect timeout and
a 30-second read timeout, and a `4xx` or `5xx` response counts as a failure. A failed delivery is
logged and not retried.

### Custom headers

In the **Create Notification** or **Edit Notification** dialog, a Webhook notification has a **Headers**
list. Click **Add header** to add a name and value pair, for example `Authorization: Bearer <token>`
for a receiver that needs one. The headers are sent on every delivery.

| Rule | Limit |
|---|---|
| Number of headers | At most 20. |
| Header name | 1 to 256 characters. Letters, digits and the symbols `! # $ % & ' * + . ^ _ ~ -`, the backtick and the pipe character are allowed. |
| Header value | At most 4096 characters, with no line breaks or other control characters. |
| Uniqueness | Names must be unique, ignoring case. |

These names are reserved and are refused, ignoring case: any name starting with `X-ByteChef-`, and
`Content-Type`, `Content-Length`, `Host`, `Transfer-Encoding` and `Connection`. ByteChef always sends
its own values for the reserved names, and skips a reserved name even if one is found in a stored
notification.

Header values are stored encrypted and are never returned by the API. When you reopen a notification,
each saved value shows as `********` with the hint "Saved, leave unchanged to keep". Leave it alone and
the stored value is kept. A saved header that you rename must have its value entered again: the dialog
clears the value, and a renamed header sent without a new value is refused with the message
`Header <name> has no saved value`. Placeholders such as `{{workflow.name}}` are not expanded in header values
or in the URL; they are sent as written.

Changing the webhook URL of a saved notification that has headers means entering every header value
again, so a saved token is never sent to a new receiver. The dialog clears the saved values as soon as the
URL differs from the saved one, and the "Enter a value" message asks for each. This applies to **Save** and
to **Test**: a header sent as `********` or without a value is refused with
`Re-enter header <name> to send to a new URL`, and a request that leaves out the headers is refused with
`Re-enter the headers to send to a new URL`. A URL that differs only in surrounding spaces, in the case of
the scheme or host, or by an explicit default port (`:80` for `http`, `:443` for `https`) counts as the same
URL. Any other change, including to the path or query, counts as a new URL. Saving with a new URL keeps the
signing secret.

Only header values are stored encrypted. The webhook URL and the body template are stored and returned
by the API in plain text, so put API keys and tokens in custom headers, not in the URL or the template.

### Body template

By default a Webhook notification sends the JSON body described in [Webhook requests](#webhook-requests).
To send a different body, for example one in the shape a chat tool or ticketing system expects, enter a
**Body template** in the dialog. Leave it empty to keep the default body.

A template is JSON text with placeholders. A placeholder is `{{path}}`, where `path` is a dotted path
into the default body, such as `{{workflow.name}}` or `{{error.message}}`. Spaces inside the braces are
allowed, so `{{ jobId }}` works too. Use the field names from the tables above.

- A value is inserted escaped for a JSON string, without surrounding quotes. Write the quotes yourself:
  `"text": "{{workflow.name}}"`. Quotes, backslashes and line breaks in the value are escaped, so the
  result stays valid JSON.
- Numbers and booleans are inserted as text in the same way, so `"id": "{{jobId}}"` sends the string
  `"1042"`.
- A path that does not exist, or whose value is empty, renders as an empty string.
- A path that points at an object or a list, such as `{{error}}`, renders as that object's JSON written
  as escaped text, so it also belongs inside quotes.
- `{{summary}}` is the one exception. It inserts the whole default body as raw JSON, so write it without
  quotes: `"event": {{summary}}`.
- Only `{{summary}}` and fields that every event carries, such as `{{jobId}}`, may be left without
  quotes. Put every other placeholder inside quotes. Optional fields, such as `{{job.durationMillis}}`
  or `{{error.message}}`, are empty on some events, and an empty value without quotes breaks the JSON.

For example, this template:

```json
{
  "text": "{{workflow.name}} failed in {{environment}}: {{error.message}}",
  "jobId": "{{jobId}}",
  "link": "{{executionUrl}}"
}
```

sends this body for the `JOB_FAILED` event above:

```json
{
  "text": "Sync new leads failed in PRODUCTION: 401 Unauthorized",
  "jobId": "1042",
  "link": "https://bytechef.example.com/automation/executions?id=1042"
}
```

The template is checked when you save. It can have at most 10000 characters, and it must produce valid
JSON twice: once filled with sample data for every field, and once with only the fields every event
carries. Otherwise the save is refused with the message "Webhook body template must render to valid JSON
for every event; quote optional fields". A template changes only the body. The headers described above are still
sent.

### Presets

In the dialog, a Webhook notification has a **Preset** control above **Webhook URL**, with the placeholder
"Start from a preset" and the description "Fills in the URL, headers and body template. You can edit
every field." It offers **Custom**, **Datadog** and **New Relic**, and a new Webhook notification starts on
**Custom**.

Picking a preset fills in three things: the **Webhook URL**, the **Headers** list and the **Body
template**. **Custom** clears the URL and headers and fills in a starter template with the main fields of
the event, one placeholder each. To send the default body instead, clear the template. Then change
anything you need. Every field stays editable.

- **Nothing about the preset is saved.** Only the URL, headers and template are saved, like any other
  webhook. When you open a saved notification, the control shows **Datadog** or **New Relic** if the URL's
  host belongs to that vendor, and **Custom** otherwise.
- **Header values start empty.** A preset adds the header names the vendor needs, with no values. **Save**
  and **Test** show "Enter a value" until you paste your key into each one.
- **A preset replaces all three fields.** While the fields still hold what the last preset filled in, or
  are all empty, another preset applies at once. Once you have changed one of them, the dialog first asks
  "Replace the URL, headers and body template?" with **Replace** and **Cancel**, and **Cancel** keeps the
  current preset selected.
- **Saved header values are dropped.** When you edit a saved notification and pick a preset, its header
  rows replace the saved ones, and you enter the values again. See [Custom headers](#custom-headers).

After you fill in a preset, click **Test** to send a sample event to the vendor before you save. See
[Testing a notification](#testing-a-notification).

The URL and header values are sent as written, so a placeholder in them is plain text that you replace
yourself, such as `YOUR_ACCOUNT_ID`. The templates follow the rules in [Body template](#body-template).

| US2-FED | `https://event-management-intake.us2.ddog-gov.com/api/v2/events` |

The body template:

```json
{
  "data": {
    "type": "event",
    "attributes": {
      "title": "{{workflow.name}}: {{eventType}}",
      "category": "alert",
      "integration_id": "custom-events",
      "message": "Job {{jobName}} ({{jobId}}) in {{environment}}. {{error.message}} {{executionUrl}}",
      "aggregation_key": "bytechef-job-{{jobId}}",
      "tags": ["source:bytechef", "environment:{{environment}}", "event:{{eventType}}"],
      "attributes": {
        "status": "error",
        "custom": {{summary}}
      }
    }
  }
}
```

Datadog groups events with the same `aggregation_key` into one alert. The preset keys on the job
(`bytechef-job-{{jobId}}`), so use `bytechef-workflow-{{workflow.id}}` to group every run of a workflow
instead.

The template always sends `"status": "error"`. For a notification that subscribes to success events,
such as `JOB_COMPLETED`, change it to `"status": "ok"`. The whole default body is sent under
`attributes.custom`, so no detail is lost.

#### New Relic

Sends one event to the New Relic Event API.

| Field | Value |
|---|---|
| **Webhook URL** | `https://insights-collector.newrelic.com/v1/accounts/YOUR_ACCOUNT_ID/events` |
| **Api-Key** header | Your New Relic license key. |

Replace `YOUR_ACCOUNT_ID` with your account id. The host depends on your New Relic region:

| Region | Host |
|---|---|
| US | `insights-collector.newrelic.com` |
| EU | `insights-collector.eu01.nr-data.net` |
| JP | `insights-collector.jp.nr-data.net` |
| FedRAMP | `gov-insights-collector.newrelic.com` |

The body template:

```json
[
  {
    "eventType": "ByteChefNotification",
    "notificationEvent": "{{eventType}}",
    "jobId": "{{jobId}}",
    "jobName": "{{jobName}}",
    "jobStatus": "{{job.status}}",
    "workflowName": "{{workflow.name}}",
    "projectName": "{{project.name}}",
    "environment": "{{environment}}",
    "source": "{{source}}",
    "errorTaskName": "{{error.taskName}}",
    "errorMessage": "{{error.message}}",
    "executionUrl": "{{executionUrl}}"
  }
]
```

New Relic attributes must be flat, so the template has no nested objects. Every value is sent as a
string, including `jobId`. The event type in New Relic is `ByteChefNotification`.

A 200 from **Test** only means New Relic received the request. Events that are not valid are dropped
later and reported as `NrIntegrationError`. To confirm the event arrived, run this NRQL query:

```
SELECT * FROM ByteChefNotification SINCE 10 minutes ago
```

If nothing shows, look for the reason with:

```
SELECT * FROM NrIntegrationError SINCE 10 minutes ago
```

#### Sentry via Custom

Sentry is not a preset. Its current ingest format is a newline-delimited envelope, which one JSON
template cannot produce. You can still send an event to the older JSON `store` endpoint with the
**Custom** preset or no preset:

| Field | Value |
|---|---|
| **Webhook URL** | `https://YOUR_DSN_HOST/api/YOUR_PROJECT_ID/store/` |
| **X-Sentry-Auth** header | `Sentry sentry_version=7, sentry_key=YOUR_PUBLIC_KEY` |

Your Sentry DSN gives the three values. It has the form `https://<public_key>@<host>/<project_id>`: use the
public key for `YOUR_PUBLIC_KEY`, copy the host as is for `YOUR_DSN_HOST`, and use the last part for
`YOUR_PROJECT_ID`. For the DSN `https://abc123@o123.ingest.us.sentry.io/456`, the URL is
`https://o123.ingest.us.sentry.io/api/456/store/`. EU organizations have hosts like
`o123.ingest.de.sentry.io`, and self-hosted Sentry uses its own host.

The body template:

```json
{
  "message": "{{workflow.name}}: {{eventType}} {{error.message}}",
  "level": "error",
  "platform": "other",
  "tags": {"environment": "{{environment}}", "event": "{{eventType}}", "jobId": "{{jobId}}"},
  "extra": {{summary}}
}
```

Sentry marks the JSON `store` endpoint as deprecated in favour of envelopes, and it may stop accepting
it. If a test to it starts failing, check Sentry's documentation for the current ingest format.

### Verifying signatures

A Webhook notification can sign each request so the receiver can prove it came from ByteChef.
Signing needs a signing secret:

- A new Webhook notification gets a secret when you save it. The **Signing Secret** dialog shows it
  once, with a **Copy** button: "Copy this secret now. You won't be able to see it again."
- Changing an Email or Slack notification to Webhook also generates a secret when you save it, and the
  **Signing Secret** dialog shows it once in the same way.
- Webhook notifications created before signing existed have no secret and are sent unsigned until they
  get one. Saving the notification generates one, or open the notification and click **Generate signing
  secret**, then confirm.
- To replace a secret, click **Regenerate signing secret** and confirm. The old secret stops working
  immediately, so update your receiver with the new one.
- The secret is stored encrypted and is never shown again or returned by the API.
- Changing a notification's type drops the secrets of the old type, including its signing secret.

When a secret exists, every request carries an `X-ByteChef-Signature` header:

```
X-ByteChef-Signature: t=1793801007512,v1=5f2b0c9e4d7a1b8c3e6f9a0d2c4b6e8f1a3c5e7092b4d6f8a1c3e5072b9d4f61
```

`t` is the same value as `X-ByteChef-Timestamp`, in milliseconds since the epoch. `v1` is the
lowercase hexadecimal HMAC-SHA256 of the string `<t>.<raw request body>`, using the signing secret
(the full `whsec_...` text) as the key. Compute it over the exact bytes received, before parsing the
JSON. When a body template is set, the signed body is the rendered body.

To verify a request, recompute the signature, compare it in constant time, and reject old timestamps to
stop replays. In Node.js:

```javascript
const crypto = require('crypto');

const FIVE_MINUTES_MS = 5 * 60 * 1000;

function verifyByteChefSignature(rawBody, signatureHeader, secret) {
  const parts = Object.fromEntries(
    signatureHeader.split(',').map((part) => part.split('=', 2))
  );
  const timestamp = parts.t;
  const received = parts.v1;

  if (!timestamp || !received) {
    return false;
  }

  if (Math.abs(Date.now() - Number(timestamp)) > FIVE_MINUTES_MS) {
    return false;
  }

  const expected = crypto
    .createHmac('sha256', secret)
    .update(`${timestamp}.${rawBody}`)
    .digest('hex');

  const expectedBuffer = Buffer.from(expected);
  const receivedBuffer = Buffer.from(received);

  return (
    expectedBuffer.length === receivedBuffer.length &&
    crypto.timingSafeEqual(expectedBuffer, receivedBuffer)
  );
}
```

`rawBody` must be the request body as received, for example `req.body.toString('utf8')` with
`express.raw({type: 'application/json'})`, not a re-serialised object.

Slack notification URLs are also stored encrypted now, and show as `********` when you edit a Slack
notification.

## Testing a notification

Click **Test** in the **Create Notification** or **Edit Notification** dialog, next to **Save**, to send
one sample message to the target before you save. **Test** is offered for every type the dialog offers:
**Email** and, in Enterprise Edition, **Slack** and **Webhook**. A Slack or Webhook test is refused in
Community Edition for the same reason the save is. Testing needs the `ADMIN` authority, like the rest of the page,
and each test is recorded in the audit log as `NOTIFICATION_TESTED`.

- **It uses what is in the form.** The values you typed are used, saved or not. The form is validated
  first, with the same rules as **Save**, and nothing is sent if it is invalid. A test never saves or
  changes the notification.
- **Saved secrets are kept.** When you edit a saved notification, a header value or Slack URL that shows
  as `********` is replaced by the saved value for the test, so you do not have to enter it again. The
  exception is a Webhook whose URL you changed: its header values must be entered again, as described in
  [Custom headers](#custom-headers).
- **The message is a sample.** It is a `JOB_FAILED` event with example values, such as the workflow
  `Example workflow` and the error `Example error: connection refused`. The timestamp is the time of the
  test, so a receiver that rejects old timestamps accepts it. It is not a run of one of your workflows.
- **It is a real request.** A Webhook or Slack test goes out through the same URL rules, timeouts, headers,
  body template and signing as a real delivery. See [Webhook requests](#webhook-requests). An **Email**
  test sends a real email to the configured address, and a **Slack** test posts a real message to the
  channel.
- **It is sent right away and only once.** A test is not queued and is never retried. It is not counted
  in the delivery metrics, and a failed test never counts toward pausing a webhook endpoint, so testing
  cannot pause your real alerts.
- **An unsaved webhook is not signed.** A new Webhook notification has no signing secret until you save
  it, so its test goes out without an `X-ByteChef-Signature` header. The result says "Sent without a
  signature; save the notification to get a signing secret." A saved Webhook notification is signed with
  its stored secret. See [Verifying signatures](#verifying-signatures).
- **A test to a changed URL is not signed.** When you test a saved Webhook notification with a URL that
  differs from the saved one, the stored secret is not used, so a receiver you have not saved yet never
  gets a signed request. The result says "Sent without a signature because the URL changed; save the
  notification to sign with its secret." After you save, tests and deliveries to the new URL are signed.
- **It can take a while.** A Webhook or Slack test waits up to 10 seconds to connect and up to 30 seconds
  for each read, so a slow receiver can keep the test running for longer than 30 seconds. An Email test has
  the same limits on the mail server: 10 seconds to connect and 30 seconds for each read and each write.

While a test runs, the button is disabled and shows a spinner. The result appears below the form:

| Result | What it shows |
|---|---|
| **Test sent** | For a Webhook, the line `HTTP <status>` and the start of the response body. Email and Slack tests show no status on success. |
| **Test failed** | The reason, such as a URL that is not allowed, a timeout, or the receiver's `HTTP <status>` and response body. |

The response body is cut to its first 1000 characters, with `…` added when it was longer. Error messages
name the host only. The result never shows a saved header value, the signing secret or the Slack URL: if
the receiver echoes one back in its response or it appears in an error, it is replaced with `********`.
Header values shorter than four characters are left as they are, so that common short words in a response
are not masked.

## Delete a notification

Click the **delete** (trash) icon on the row and confirm in the **Delete &lt;name&gt; notification?** dialog
("This action cannot be undone."). The rule stops firing immediately; runs already in flight are
unaffected.
