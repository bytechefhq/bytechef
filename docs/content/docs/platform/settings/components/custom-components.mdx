A component is ByteChef's unit of integration: a bundle of actions, triggers and connection logic for one external system or capability. When the built-in catalog does not cover a system, you can upload a custom component.

<Callout title="Availability">
    Custom components are an Enterprise Edition feature. The settings page is open to the `ADMIN` and `USER`
    authorities and is gated by the `ff-1024` feature flag; with the flag off, the settings entry is hidden.
    Uploading a component requires `ADMIN`. [API Connectors](/platform/settings/components/api-connectors) is a
    separate entry behind its own `ff-207` flag.
</Callout>

---

## When to use a component

A script step can do anything a component can. A component is the better choice when:

- **The integration is reused across many workflows.** You define it once and use it everywhere.
- **The integration has a meaningful schema.** Components expose typed input and output properties, which the workflow editor shows in the data-pill picker.
- **The integration needs authentication.** Components declare connection types that use encrypted credential storage and the standard OAuth flow.
- **The integration should be an MCP tool.** Components are what the platform exposes over MCP.

## Implementation options

| Language | File | Notes |
|---|---|---|
| Java | `.jar` | Full component API: actions, triggers, connections, properties and output schemas. |
| JavaScript | `.js` | Single source file. Declares actions only (see [Script components](#script-components)). |
| Python | `.py` | Single source file. Same contract as JavaScript. |
| Ruby | `.rb` | Rejected at upload with `LANGUAGE_NOT_SUPPORTED` ("Uploading of Ruby custom components is temporarily disabled"). |

### Java components

A Java component implements `ComponentHandler` and is annotated with `@AutoService(ComponentHandler.class)` for ServiceLoader discovery. It defines a static `ComponentDefinition` that describes its actions, triggers and connection:

```java
@AutoService(ComponentHandler.class)
public class MyComponentHandler implements ComponentHandler {
    private static final ComponentDefinition COMPONENT_DEFINITION = component("my-system")
        .title("My System")
        .connection(CONNECTION_DEFINITION)
        .actions(MyAction.ACTION_DEFINITION)
        .triggers(MyTrigger.TRIGGER_DEFINITION);
}
```

You build a Java component outside ByteChef and upload the `.jar`. See the [developer guide](/developer-guide) for the full authoring reference.

### Script components

A JavaScript or Python component is a single source file whose last expression evaluates to an object with these members:

| Member | Type | Required |
|---|---|---|
| `name` | String | Yes |
| `version` | Integer | Yes |
| `title` | String | No |
| `description` | String | No |
| `actions` | Array of `{ name, title, description, perform }` | No |

```javascript
({
    name: "greeter",
    title: "Greeter",
    version: 1,
    actions: [
        {
            name: "sayHello",
            title: "Say Hello",
            description: "Returns a greeting.",
            perform: function () {
                return {message: "Hello"};
            }
        }
    ]
})
```

The platform calls `perform` with no arguments, so a script action cannot read input parameters or connection values. Script components cannot declare triggers, a connection, an icon, properties or an output schema. Each action run evaluates the script in a new GraalVM polyglot context.

## The Custom Components page

**Settings → Custom Components** is headed "Extend the component catalog with your own components." With no components installed, the page shows the **No Custom Components** empty state with an **Import Component** button and a "How custom components work" link.

Each row shows:

- The component **title**, a `v<version>` badge and the component **name**. Hovering the title shows the description.
- A **language** badge (`JAVA`, `JAVASCRIPT` or `PYTHON`).
- A switch that enables or disables the component.
- The last modification time ("Modified at ...").
- A row menu with **Delete**, which asks for confirmation.

The chevron at the start of a row expands it to show the component's actions and triggers, read-only.

### Importing a component

**Import Component** opens the **Import Custom Component** dialog. Drop one or more files on the **Select Component File** area, or click it to browse. The dialog lists the selected files with their size, and you can remove a file before uploading.

An upload is deployed immediately; there is no separate release step. The platform loads the file to read its name and version:

- A new name and version creates a new row, enabled by default.
- An existing name and version replaces that version and refreshes its title, description and icon.

Each version of a component is its own row. Workflows reference the version they were built with, so uploading version 2 does not change what a workflow bound to version 1 runs.

## Deploying programmatically

The same upload is available through the public API:

```
POST /api/platform/v1/custom-components/deploy
```

Send a multipart request with a `componentFile` part. The file extension selects the language (`.jar`, `.js`, `.py`). The call requires `ADMIN` and returns `204` on success.

For example, to deploy the `greeter` script above from a CI job, authenticating with an [Admin API key](/platform/settings/admin-api-keys):

```bash
curl -X POST "https://your-bytechef-host.example.com/api/platform/v1/custom-components/deploy" \
  -H "Authorization: Bearer <admin-api-key>" \
  -F "componentFile=@greeter.js"
```

## Runtime and isolation

- A Java component is loaded through its own isolating classloader, so dependency versions in one component do not conflict with another.
- A script component runs in a GraalVM polyglot context.
- Uploading a new version does not require a restart.

## Scaffolding with the CLI

The CLI generates a Java component module from an OpenAPI specification:

```bash
bytechef component init --name my-component --open-api-path ./openapi.yaml --output-path .
```

| Option | Required | Default | Description |
|---|---|---|---|
| `--name`, `-n` | Yes | | Component name. |
| `--output-path`, `-o` | Yes | | Directory for the generated files. |
| `--open-api-path` | No | | Local file or `http(s)` URL of the OpenAPI specification. Without it, nothing is generated. |
| `--base-package-name` | No | `com.bytechef.component` | Package for the generated classes. |
| `--version`, `-v` | No | `1` | Component version. |
| `--internal-component` | No | `false` | Generate a component that ships with the platform instead of a custom one. |

The command generates a module skeleton with a handler class, action stubs, tests and a README template. The generated code lives in your repository and ships through the same pipeline as a hand-written component.

For a connector built from a specification without code, see [API Connectors](/platform/settings/components/api-connectors).

## Distribution

| Method | When to use |
|---|---|
| **Upload** | Components for one installation, through the **Import Custom Component** dialog or the deploy endpoint. |
| **Bundle into the build** | First-party components shipped with your own build. The built-in catalog ships this way: each component is a Gradle module under `server/libs/modules/components/` whose handler is discovered by ServiceLoader through `@AutoService(ComponentHandler.class)`. |

## Audit

Each upload is recorded in the [audit log](/platform/settings/audit-events) as `CUSTOM_COMPONENT_SAVED`, with the component id, name, version and language.
