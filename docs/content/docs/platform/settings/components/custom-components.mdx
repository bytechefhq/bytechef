A component is ByteChef's unit of integration: a bundle of actions, triggers and a connection definition that wraps
one external system or capability. When the built-in catalog does not cover what you need, you write a **custom
component**. Once published it appears in the workflow editor next to the built-in components, with its own typed
properties, output schema, connection type and triggers.

<Callout title="Availability">
    Custom components are an Enterprise Edition feature. **Settings → Custom Components** is shown when the `ff-1024`
    feature flag is on and is open to the `ADMIN` and `USER` authorities. Creating, importing, editing the source of
    and publishing a component require `ADMIN`. [API Connectors](/platform/settings/components/api-connectors) is a
    separate entry behind its own `ff-207` flag.
</Callout>

---

## When to write a custom component

ByteChef gives you four ways to add your own logic. Pick the lightest one that fits.

| You need | Use |
|---|---|
| A few lines of logic used in one workflow | A [Script step](/platform/automation/build/workflows/code-workflows#scripting-languages) |
| A whole workflow, or a project of workflows, kept in Git | A [code workflow](/platform/automation/build/workflows/code-workflows) |
| A REST API with an OpenAPI specification and no custom logic | An [API connector](/platform/settings/components/api-connectors) |
| A reusable integration with its own schema, connection, triggers or AI tools | A custom component |

A custom component is worth the extra structure when:

- **It is reused across many workflows.** Define it once and every workflow picks it from the catalog.
- **It has a meaningful schema.** Declared properties and outputs give the editor typed inputs, validation and data
  pills for downstream steps.
- **It authenticates.** A declared connection plugs into encrypted credential storage, the Connections page and the
  platform's OAuth2 flow.
- **It starts workflows.** Polling and webhook triggers are only available in components.
- **An AI agent should call it.** An action marked as a tool becomes an AI agent tool.

A code workflow and a custom component do different jobs. A code workflow is a workflow: it calls components. A
custom component is a building block: workflows, including code workflows, call it. A script custom component cannot
call other components.

## Languages and artifacts

The language comes from the file extension.

| Language | Artifact | Extension | Create in ByteChef | Edit source in ByteChef |
|---|---|---|---|---|
| JavaScript | one source file | `.js` | Yes | Yes |
| Python | one source file | `.py` | No, upload only | Yes |
| Java | jar | `.jar` | No, upload only | No |

JavaScript and Python components run in the GraalVM polyglot sandbox. Java components run in the server JVM behind an
isolating class loader. An administrator can turn off Java uploads; see [Restricting Java uploads](#restricting-java-uploads).

Ruby (`.rb`) is recognized by the language detection but uploads are rejected with `LANGUAGE_NOT_SUPPORTED`. Any other
extension is rejected as an unsupported language.

## Identity, versions and status

A custom component is identified by its **name** and its **version**, both declared in the component itself. Each
version is a separate row in the list, and workflows pin the version they use: publishing version 2 does not change
what a workflow bound to version 1 runs. In a workflow, an action is referenced as
`<name>/v<version>/<actionName>`, for example `sampleCustomComponentJavaScript/v1/sampleAction1`.

Each version has a **status**:

| Status | Editable in ByteChef | Visible to workflows |
|---|---|---|
| **Draft** | Yes | No |
| **Published** | No: saving a change starts a new draft version | Yes |

and an **enabled** switch. A disabled component is left out of the component catalog, so it cannot be added to new
steps. Steps that already reference that name and version keep resolving it.

There is at most **one draft per component name**.

## The script contract

This section applies to JavaScript and Python components. For Java, see [The Java contract](#the-java-contract).

### The file

A script component is **one file**. ByteChef evaluates it and reads the value it evaluates to:

- **JavaScript**: the file's completion value is the definition, usually one parenthesized object expression,
  `({ ... })`. Do not use `export`, `module.exports` or a bundler: they hide the object from the server.
- **Python**: the file's **last expression** is the definition, a `types.SimpleNamespace`. Define your functions with
  `def` above it. The members inside it (actions, properties, connection) are ordinary `dict`s and `list`s.

ByteChef evaluates the file again for every call: loading the definition, each action run, each trigger poll or webhook
request, each options lookup. Top-level code should only build the definition. Nothing you store in a variable survives
from one call to the next; a polling trigger carries its state in `closureParameters` instead.

### Component

| Member | Type | Required | |
|---|---|---|---|
| `name` | string | Yes | The component's identity. Cannot change once the component exists. A letter followed by letters and digits (camelCase, for example `acmeTasks`), at most 128 characters, and not the name of a built-in component. |
| `version` | integer | Yes | The component version. |
| `title` | string | No | Shown in the catalog and the list. |
| `description` | string | No | |
| `icon` | string | No | An inline SVG, shown in lists and on the canvas. |
| `connection` | object | No | See [Connections](#connections). |
| `actions` | list of actions | No | See [Actions](#actions). |
| `triggers` | list of triggers | No | See [Triggers](#triggers). |

### Actions

| Member | Type | Required | |
|---|---|---|---|
| `name` | string | Yes | Unique within the component. A letter followed by letters and digits, for example `createTask`. Trigger names follow the same rule. |
| `perform` | function | Yes | Called as `perform(input, connection, context)`. Its return value is the action's output. |
| `title` | string | No | |
| `description` | string | No | For a tool, the text the model reads. |
| `properties` | list of properties | No | The action's inputs. See [Properties](#properties). |
| `output` | property | No | The output schema. See [Output](#output). |
| `sampleOutput` | any | No | A sample of the output. |
| `tool` | boolean | No | `true` also exposes the action as an AI agent tool. See [Tools](#tools). |

### The perform function

`perform(input, connection, context)` receives three arguments, named like the
[Script component's](/platform/automation/build/workflows/code-workflows#scripting-languages):

| Argument | Holds |
|---|---|
| `input` | The values the step configured for the action's `properties`, keyed by property name. Empty when the action declares none. |
| `connection` | The parameters of the connection selected for the step, keyed by connection property name (for OAuth2, the platform's token values such as `access_token`). Empty when no connection is configured. |
| `context` | Two functions: `context.http(request)` and `context.log(level, message)`. |

Return any JSON-like value: an object, a list, a string, a number, a boolean or `null`. It becomes the step's output.

In JavaScript, a `perform` that declares fewer parameters still works, because JavaScript ignores extra arguments. In
Python, declare all three.

#### context.http

`context.http(request)` executes an HTTP request through the platform's HTTP client, the same client built-in
components use, so the selected connection's authorization (for example the bearer token or API key header) is applied
to the request unless you turn it off. It returns `{statusCode, headers, body}`.

| Request member | Required | |
|---|---|---|
| `url` | Yes | The full URL. |
| `method` | Yes | `GET`, `POST`, `PUT`, `PATCH`, `DELETE` or `HEAD`. |
| `headers` | No | `{name: value}`. A value is a string or a list of strings. |
| `queryParameters` | No | Same shape as `headers`. |
| `body` | No | A wrapper around the payload, `{content, contentType, mimeType}`. See below. |
| `configuration` | No | Request options. See below. |

`body` is not the payload itself. `contentType` is required and is one of `JSON`, `FORM_URL_ENCODED`, `FORM_DATA`,
`RAW` or `XML`. `mimeType` applies to `RAW` and `XML` only. `BINARY` bodies are not supported in the sandbox and fail
when the action runs.

```javascript
body: {content: {id: 1}, contentType: "JSON"}
body: {content: "a,b\n1,2", contentType: "RAW", mimeType: "text/csv"}
```

`configuration` takes `timeoutMillis` (a number), `responseType` (`JSON`, `TEXT`, `XML` or `BINARY`), and the
booleans `followRedirect`, `followAllRedirects`,
`allowUnauthorizedCerts` and `disableAuthorization`.

```javascript
const response = context.http({
    url: "https://api.example.com/items",
    method: "POST",
    body: {content: {name: "widget"}, contentType: "JSON"},
    configuration: {timeoutMillis: 10000, responseType: "JSON"}
});

return response.body;
```

<Callout type="warn">
    Enumerated values are resolved by name on the server, so they are case sensitive. A lowercase `"get"` or a
    `contentType` of `"application/json"` fails when the action runs, not when the component is saved.
</Callout>

#### context.log

`context.log(level, message)` writes a line to the step's execution log. `level` is `TRACE`, `DEBUG`, `INFO`, `WARN`
or `ERROR`, in upper case. Any other value, including the lower-case forms, is logged at `INFO`.

```javascript
context.log("WARN", "item " + input.itemId + " has no owner");
```

`console.log` in JavaScript and `print` in Python do not reach the execution log. They go to the server log, prefixed
with `[guest]`.

### Properties

Actions, triggers and connections declare their inputs as a list of properties, each an object with a `name` and a
`type`.

| Type | Type-specific members |
|---|---|
| `STRING` | `minLength`, `maxLength`, `regex`, `defaultValue`, `options`, `controlType` |
| `INTEGER` | `minValue`, `maxValue`, `defaultValue`, `options` |
| `NUMBER` | `minValue`, `maxValue`, `defaultValue`, `options` |
| `BOOLEAN` | `defaultValue` |
| `DATE`, `DATE_TIME`, `TIME` | |
| `OBJECT` | `properties`, `additionalProperties` (lists of properties) |
| `ARRAY` | `items` (a list of properties), `minItems`, `maxItems`, `multipleValues` |
| `FILE_ENTRY` | |
| `NULL` | |
| `DYNAMIC_PROPERTIES` | `properties` (a function), `propertiesLookupDependsOn`. Actions only; see [Dynamic properties](#dynamic-properties). |

Every type also takes `label`, `description`, `placeholder`, `required`, `advancedOption`, `hidden`,
`expressionEnabled` and `displayCondition`. `controlType` is the name of an editor control, such as `TEXT_AREA`,
`PASSWORD`, `EMAIL` or `URL`, and applies to `STRING` properties. `optionsLookupDependsOn` lists the names of the
properties whose values an options function reads.

Static `options` are a list of `{label, value}` entries whose values match the property's type:

```javascript
{
    name: "priority",
    type: "STRING",
    label: "Priority",
    options: [
        {label: "Low", value: "low"},
        {label: "High", value: "high"}
    ],
    defaultValue: "low"
}
```

An unknown `type` fails the load with `Unsupported property type`.

#### Dynamic options

On an action property of type `STRING`, `INTEGER` or `NUMBER`, `options` can be a function. The editor calls it when
the user opens the dropdown, so the choices can depend on the other inputs and on the selected connection:

```javascript
{
    name: "projectId",
    type: "STRING",
    label: "Project",
    required: true,
    options: function (input, connection, searchText) {
        return [
            {label: "Website", value: "p-1"},
            {label: "Mobile App", value: "p-2"}
        ];
    }
}
```

The function receives the action's current input values, the selected connection's parameters and the search text
the user typed (or `null`). It returns a list of `{label, value}` entries, or a list of plain values, each used as both
label and value. Values are passed to the editor as strings. To re-run the lookup when another field changes, list
that field in `optionsLookupDependsOn`.

#### Dynamic properties

A property of type `DYNAMIC_PROPERTIES` stands for a set of properties computed at edit time, for example the fields of
a record type the user picked:

```javascript
{
    name: "fields",
    type: "DYNAMIC_PROPERTIES",
    propertiesLookupDependsOn: ["recordType"],
    properties: function (input, connection) {
        if (input.recordType === "contact") {
            return [
                {name: "email", type: "STRING", label: "Email", required: true},
                {name: "phone", type: "STRING", label: "Phone"}
            ];
        }

        return [{name: "title", type: "STRING", label: "Title"}];
    }
}
```

The function receives the action's current input values and the connection's parameters, and returns a list of
properties in the same shape as a static `properties` list. It must not return another `DYNAMIC_PROPERTIES` property.

Dynamic options and dynamic properties are supported on **action** properties. Trigger and connection properties are
static.

### Output

Without an output declaration an action publishes no schema, and downstream steps have no data pills to pick from.
Declare `output` as a property, usually an `OBJECT` with nested `properties`, and optionally a `sampleOutput`:

```javascript
{
    name: "getItem",
    properties: [{name: "itemId", type: "STRING", required: true}],
    output: {
        type: "OBJECT",
        properties: [
            {name: "id", type: "STRING"},
            {name: "name", type: "STRING"}
        ]
    },
    sampleOutput: {id: "42", name: "Widget"},
    perform: function (input, connection, context) { /* ... */ }
}
```

A `sampleOutput` without an `output` is accepted too. Triggers take the same two members.

### Tools

An action with `tool: true` is also registered as a `TOOLS` cluster element, so an
[AI agent](/platform/automation/build/workflows/ai/agent) can call it. It stays available as a normal action. The
model decides when to call the tool from its `description`, so write the description for the model:

```javascript
{
    name: "lookupCustomer",
    title: "Lookup Customer",
    description: "Finds a customer by their email address and returns the customer's id.",
    tool: true,
    properties: [{name: "email", type: "STRING", required: true}],
    output: {type: "OBJECT", properties: [{name: "id", type: "STRING"}]},
    perform: function (input, connection, context) { /* ... */ }
}
```

### Triggers

A trigger has a `name`, a `type` and, optionally, `title`, `description`, `properties`, `output` and `sampleOutput`.
Three types are supported. A trigger without a `type` is a `POLLING` trigger.

| Type | Functions | Fires when |
|---|---|---|
| `POLLING` | `poll` | The scheduled poll returns records. |
| `STATIC_WEBHOOK` | `webhookRequest` | A request reaches the workflow's webhook URL, which you register with the provider yourself. |
| `DYNAMIC_WEBHOOK` | `webhookEnable`, `webhookDisable`, `webhookRequest` | A request reaches the webhook URL the trigger registered with the provider when the workflow was enabled. |

`LISTENER` triggers are rejected when the component loads: a listener holds a live connection open, and a script that
is evaluated per call has nowhere to keep it.

#### Polling triggers

`poll(input, connection, closureParameters)` is called on a schedule. `closureParameters` holds what the previous poll
returned, empty on the first poll. Return `{records, closureParameters, pollImmediately}`:

- `records`: a list. Each record starts one workflow run.
- `closureParameters`: an object handed to the next poll. Use it for a cursor or a last-seen timestamp.
- `pollImmediately`: `true` polls again right away instead of waiting for the next scheduled poll, for paging
  through a backlog.

```javascript
triggers: [
    {
        name: "newItem",
        title: "New Item",
        type: "POLLING",
        properties: [{name: "folder", type: "STRING", required: true}],
        output: {type: "OBJECT", properties: [{name: "id", type: "STRING"}]},
        poll: function (input, connection, closureParameters) {
            const since = closureParameters.cursor || 0;

            const items = [{id: "1", createdAt: since + 1}];

            return {records: items, closureParameters: {cursor: since + 1}};
        }
    }
]
```

<Callout title="Every function gets a context">
    The same `context` that `perform` receives is passed as the last argument to the other functions too: trigger
    functions (`poll(input, connection, closureParameters, context)`, `webhookRequest`, `webhookEnable`,
    `webhookDisable`), options functions (`options(input, connection, searchText, context)`), dynamic properties
    functions (`properties(input, connection, context)`) and connection URL and `apply` functions
    (`tokenUrl(connection, context)`). A polling trigger can call the provider's API with `context.http`, and a
    `DYNAMIC_WEBHOOK` trigger's `webhookEnable` can register the URL with it. The argument is optional: a function that
    does not declare it is called without it, in Python as well as in JavaScript.
</Callout>

#### Static webhook triggers

`webhookRequest(input, connection, request)` is called for each request that reaches the workflow's webhook URL.
`request` is `{headers, parameters, body, method}`, and the return value becomes the trigger's output:

```javascript
{
    name: "onPush",
    title: "On Push",
    type: "STATIC_WEBHOOK",
    webhookRequest: function (input, connection, request) {
        return {event: request.body.event, sender: request.headers["x-sender"]};
    }
}
```

#### Dynamic webhook triggers

A `DYNAMIC_WEBHOOK` trigger registers its URL with the provider. Add `webhookEnable` and `webhookDisable` alongside
`webhookRequest`:

```javascript
{
    name: "onIssue",
    title: "On Issue",
    type: "DYNAMIC_WEBHOOK",
    webhookEnable: function (input, connection, args) {
        // args.webhookUrl is the URL the platform minted for this workflow.
        return {subscriptionId: "sub-123"};
    },
    webhookDisable: function (input, connection, args) {
        // args holds what webhookEnable returned, for example args.subscriptionId.
    },
    webhookRequest: function (input, connection, request) {
        return request.body;
    }
}
```

`webhookEnable` runs when a workflow using the trigger is enabled. Whatever object it returns is stored and passed to
`webhookDisable` when the workflow is disabled. A `DYNAMIC_WEBHOOK` trigger without one of the three functions fails
when that function would run.

### Connections

The optional `connection` member declares the component's connection type. The Connections page can then create
connections of that type, the workflow editor offers them on the component's steps, and `perform` receives the selected
connection's parameters as its `connection` argument.

| Member | |
|---|---|
| `baseUri` | A string, the API's base URL. |
| `authorizations` | A list of authorizations. A connection without it, but with `properties`, gets one implicit `CUSTOM` authorization. |
| `properties` | Connection-level properties. They apply to every authorization that declares no `properties` of its own. |

An authorization has a `type` and optional `properties`, `authorizationUrl`, `tokenUrl`, `refreshUrl`, `scopes` (a list
of strings) and `apply`. `type` is one of `API_KEY`, `BASIC_AUTH`, `BEARER_TOKEN`, `CUSTOM`, `DIGEST_AUTH`,
`OAUTH2_AUTHORIZATION_CODE`, `OAUTH2_AUTHORIZATION_CODE_PKCE`, `OAUTH2_CLIENT_CREDENTIALS`, `OAUTH2_IMPLICIT_CODE` or
`OAUTH2_RESOURCE_OWNER_PASSWORD`. For OAuth2 types the platform runs the whole flow: the authorization redirect, the
callback, the token exchange and the refresh. The component only declares the endpoints.

```javascript
connection: {
    baseUri: "https://api.example.com",
    authorizations: [
        {
            type: "OAUTH2_AUTHORIZATION_CODE",
            authorizationUrl: "https://example.com/oauth/authorize",
            tokenUrl: "https://example.com/oauth/token",
            scopes: ["read", "write"],
            properties: [
                {name: "clientId", type: "STRING", label: "Client Id", required: true},
                {name: "clientSecret", type: "STRING", label: "Client Secret", required: true}
            ]
        }
    ]
}
```

`authorizationUrl`, `tokenUrl` and `refreshUrl` take a string or a function of the connection parameters, for region-
or tenant-specific endpoints. The function must return a string:

```javascript
tokenUrl: function (connection) {
    return "https://" + connection.region + ".example.com/oauth/token";
}
```

An authorization's `apply(connection)` function overrides how the credentials decorate outgoing requests. It returns
`{headers, queryParameters}`, each an object whose values are strings or lists of strings:

```javascript
{
    type: "CUSTOM",
    properties: [{name: "token", type: "STRING", label: "Token", required: true}],
    apply: function (connection) {
        return {headers: {"X-Api-Token": connection.token}};
    }
}
```

`apply` runs on every request the connection makes, so each request pays for one more evaluation of the file.

### A complete JavaScript component

A component with an API key connection, an action with dynamic options and a polling trigger:

```javascript
({
    name: "acmeTasks",
    title: "Acme Tasks",
    description: "Create and watch tasks in Acme.",
    version: 1,
    connection: {
        baseUri: "https://api.acme.example",
        authorizations: [
            {
                type: "BEARER_TOKEN",
                properties: [{name: "token", type: "STRING", label: "API Token", required: true}]
            }
        ]
    },
    actions: [
        {
            name: "createTask",
            title: "Create Task",
            description: "Creates a task in a project.",
            tool: true,
            properties: [
                {
                    name: "projectId",
                    type: "STRING",
                    label: "Project",
                    required: true,
                    options: function (input, connection, searchText) {
                        return [
                            {label: "Website", value: "p-1"},
                            {label: "Mobile App", value: "p-2"}
                        ];
                    }
                },
                {name: "title", type: "STRING", label: "Title", required: true},
                {name: "notes", type: "STRING", label: "Notes", controlType: "TEXT_AREA"}
            ],
            output: {
                type: "OBJECT",
                properties: [
                    {name: "id", type: "STRING"},
                    {name: "title", type: "STRING"}
                ]
            },
            perform: function (input, connection, context) {
                const response = context.http({
                    method: "POST",
                    url: "https://api.acme.example/projects/" + input.projectId + "/tasks",
                    body: {content: {title: input.title, notes: input.notes}, contentType: "JSON"},
                    configuration: {responseType: "JSON"}
                });

                context.log("INFO", "Created task " + response.body.id);

                return response.body;
            }
        }
    ],
    triggers: [
        {
            name: "newTask",
            title: "New Task",
            type: "POLLING",
            properties: [{name: "projectId", type: "STRING", label: "Project ID", required: true}],
            output: {type: "OBJECT", properties: [{name: "id", type: "STRING"}]},
            poll: function (input, connection, closureParameters) {
                const lastSeen = closureParameters.lastSeen || 0;

                return {records: [], closureParameters: {lastSeen: lastSeen}};
            }
        }
    ]
})
```

### A Python component

The same contract in Python. Define the functions with `def`, then end the file with the `types.SimpleNamespace`:

```python
import types


def list_projects(input, connection, search_text):
    return [
        {"label": "Website", "value": "p-1"},
        {"label": "Mobile App", "value": "p-2"},
    ]


def create_task(input, connection, context):
    response = context.http({
        "method": "POST",
        "url": "https://api.acme.example/projects/" + input["projectId"] + "/tasks",
        "body": {"content": {"title": input["title"]}, "contentType": "JSON"},
        "configuration": {"responseType": "JSON"},
    })

    context.log("INFO", "Created a task")

    return response["body"]


types.SimpleNamespace(
    name="acmeTasksPython",
    title="Acme Tasks (Python)",
    version=1,
    connection={
        "baseUri": "https://api.acme.example",
        "authorizations": [
            {
                "type": "BEARER_TOKEN",
                "properties": [{"name": "token", "type": "STRING", "label": "API Token", "required": True}],
            }
        ],
    },
    actions=[
        {
            "name": "createTask",
            "title": "Create Task",
            "properties": [
                {"name": "projectId", "type": "STRING", "label": "Project", "required": True,
                 "options": list_projects},
                {"name": "title", "type": "STRING", "label": "Title", "required": True},
            ],
            "perform": create_task,
        }
    ],
)
```

## The Java contract

A Java custom component is a jar that contains a `ComponentHandler` implementation, exactly like a built-in
component. The [Developer Guide](/developer-guide) and the
[component specification](/developer-guide/component-specification/component) cover the full Java DSL: components,
[actions](/developer-guide/component-specification/action), [triggers](/developer-guide/component-specification/trigger),
[connections](/developer-guide/component-specification/connection) and
[properties](/developer-guide/component-specification/property).

What the loader requires of the jar:

- **A `ComponentHandler` registered for `ServiceLoader`.** Annotate the handler with
  `@AutoService(ComponentHandler.class)` (or write `META-INF/services/com.bytechef.component.ComponentHandler` by hand).
  The loader uses the first handler it finds, so put one component in each jar.
- **An icon at `assets/sample.svg`.** The loader reads the component's icon from that path in the jar, whatever the
  handler's own `.icon(...)` says. A jar without that file fails to load.
- **Everything except the ByteChef API inside the jar.** Classes in `java.*`, `jdk.*` and `com.bytechef.*` come from the
  server; every other class is loaded only from your jar, with no fallback to the server's class path. Build against
  the ByteChef `component-api` and `definition-api` without bundling them, and bundle every other runtime dependency
  (a fat or shaded jar). Do not put your own classes in a `com.bytechef` package.

The component's `name` and `version` come from the `ComponentDefinition` (`component("name").version(2)`; the version
defaults to `1`).

Java components cannot be edited in ByteChef. To change one, rebuild the jar and upload it again; see
[Versions and drafts](#versions-and-drafts) for what an upload does to an existing version.

## Example: the Java sample

[bytechef-sample-custom-component-java](https://github.com/bytechefhq/bytechef-sample-custom-component-java) is a
Gradle project with one component, `sampleCustomComponentJava`, that has one action, `sampleAction`. The ByteChef API
jars it compiles against are checked in under `libs/`. The listings below omit the files' license headers.

`build.gradle.kts`:

```kotlin
plugins {
```

## Example: the JavaScript sample

[bytechef-sample-custom-component-javascript](https://github.com/bytechefhq/bytechef-sample-custom-component-javascript)
contains one file that matters, `src/sample_custom_component.js`, and that file is what you upload. There is no build
step:

```javascript
({
  name: 'sampleCustomComponentJavaScript',
  title: 'Sample Custom Component',
  description: 'A sample custom component written in JavaScript.',
  version: 1,
  actions: [
    {
      name: 'sampleAction1',
      title: 'Sample Action 1',
      description: 'Builds a greeting for a name.',
      properties: [
        {
          name: 'name',
          type: 'STRING',
          label: 'Name',
          required: true,
        },
      ],
      output: {
        type: 'OBJECT',
        properties: [
          { name: 'message', type: 'STRING' },
        ],
      },
      sampleOutput: { message: 'Hello, ByteChef' },
      perform(input, connection, context) {
        context.log('INFO', `Greeting ${input.name}`);

        return { message: `Hello, ${input.name}` };
      },
    },
  ],
});
```

The file is one parenthesized object expression, so the value it evaluates to is the definition. Do not use `export`,
`module.exports`, `require` or a bundler: they hide the definition from the server. The action has one required
`STRING` property, `name`, and an `OBJECT` output that declares `message`, so downstream steps get a data pill for it.
`perform(input, connection, context)` logs `Greeting <name>` with `context.log('INFO', ...)`, which writes to the step's
execution log (`console.log` goes to the server log instead), and returns `{"message": "Hello, <name>"}`. The component
declares no connection; see [Connections](#connections) to add one.

### Check

```bash
git clone https://github.com/bytechefhq/bytechef-sample-custom-component-javascript.git
cd bytechef-sample-custom-component-javascript
npm install
npm run check
```

`npm run check` evaluates `src/sample_custom_component.js` the way the server does and checks that it declares a name, a
version and a `perform` function for each action. It prints:

```
sampleCustomComponentJavaScript v1: sampleAction1
```

`npm run lint` runs ESLint over the project.

### Deploy

From the UI, **Settings → Custom Components → New Component → Import Component**, then pick
`src/sample_custom_component.js`. Through the API:

```bash
curl -X POST "$BYTECHEF_URL/api/platform/v1/custom-components/deploy" \
  -H "Authorization: Bearer $BYTECHEF_ADMIN_API_KEY" \
  -F "componentFile=@src/sample_custom_component.js"
```

The file must keep its `.js` extension: ByteChef picks the language from it. The component appears as **Sample Custom
Component**, version 1, published. Add **Sample Action 1** to a workflow, fill in **Name** and run the step. Because it
is a script component, clicking its row opens the source editor, so you can continue in ByteChef: raise `version` to
`2`, save, and a draft of version 2 is created next to the published version 1.

## Working in the UI

### The Custom Components page

**Settings → Custom Components** lists every version of every custom component, sorted by name. Each row shows the
title with a version badge, the name, a language badge (`JAVASCRIPT`, `PYTHON`, `JAVA`), a **Draft** or **Published**
badge, an enable/disable switch, the last modified time, and a **⋮** menu with **Delete**.

- Clicking a **JavaScript or Python** row opens its [source editor](#the-source-editor).
- A **Java** row is not clickable. Its chevron expands the row to show the component's actions and triggers, read-only.

**Delete** asks for confirmation, then removes that version and its stored file. It does not check whether workflows
still use the version.

### The New Component menu

**New Component** in the page header (or in the empty state, when there are no custom components yet) opens a menu
with two entries:

- **New Component** opens the [create dialog](#creating-a-component).
- **Import Component** opens the [import dialog](#importing-files).

### Creating a component

The **New Custom Component** dialog ("Create an empty custom component and start building it.") has two fields:

| Field | |
|---|---|
| **Name** | Required, up to 256 characters. It becomes the component's `name` and `title`. It must not contain quotes, backslashes or line breaks, and must not be taken. Use an identifier such as `acmeTasks`: the name is part of every step type that uses the component. |
| **Language** | **JavaScript**, the only language that can be created in ByteChef. To start in Python, write the file and import it. |

**Create** generates a starter component, version 1, as a **draft**, and opens it in the source editor. The starter
declares one action, `myAction`, with one `input` property, a `perform(input, connection, context)` that returns its
input, and commented-out examples of a connection, `context.log` and `context.http`.

### The source editor

The editor page shows a back arrow, the component's title, its language badge and its **Draft** or **Published**
badge, with **Save** and **Publish** buttons, above a Monaco editor with the source.

- **Save** is enabled once you change the source. The server loads the edited source before it stores it, so source
  that does not evaluate, or that breaks the contract, is rejected with the loader's error and nothing is saved.
- **Publish** is enabled on a draft with no unsaved changes. It makes the draft visible to workflows.

What **Save** does depends on the version you are editing:

- **A draft**: the draft is updated in place. You may change its `version`, as long as no other version of the
  component has that number.
- **A published version**: you must raise `version` above the highest existing version of the component. **Save**
  then creates a new draft with that version and the editor switches to it. The published version is unchanged and
  keeps serving workflows.

The source cannot change the component's `name`.

### Importing files

The **Import Custom Component** dialog ("Upload a custom component file to deploy it to the platform.") takes one or
more files: click the drop zone to browse. It accepts `.jar`, `.js` and `.py` files, or only `.js` and `.py` when
[Java uploads are off](#restricting-java-uploads). **Import** uploads the files one by one and shows the result of each.

An import publishes immediately; see [Versions and drafts](#versions-and-drafts).

### Versions and drafts

To release a new version of a published script component:

1. Open the published version and raise `version` in the source above the highest existing version, for example from
   `version: 1` to `version: 2`.
2. **Save**. A draft of version 2 is created and opened.
3. Keep editing and saving the draft.
4. **Publish** when it is ready. Version 1 stays published next to version 2, and each workflow keeps the version it
   was built with until you change its steps.

An upload, through the import dialog or the API, works by name and version instead:

| The uploaded file declares | Result |
|---|---|
| A name and version that do not exist yet | A new version, already **published** and enabled. |
| The name and version of a **published** version | That version's file, title, description and icon are replaced in place. Workflows using it pick up the change. |
| The name and version of a **draft** | Rejected with `VERSION_ALREADY_EXISTS`. Publish or delete the draft first. |

### Errors

| Error | Cause |
|---|---|
| `VERSION_NOT_BUMPED` | Saving a published version without raising `version` above the highest existing version. |
| `DRAFT_ALREADY_EXISTS` | Saving a published version while the component already has a draft. Edit, publish or delete that draft. |
| `VERSION_ALREADY_EXISTS` | A draft's new `version` collides with another version, or an upload targets a version owned by a draft. |
| `COMPONENT_NOT_DRAFT` | Publishing something that is not a draft. |
| `COMPONENT_ALREADY_EXISTS` | Creating a component whose name is taken. |
| `INVALID_COMPONENT_NAME` | Creating a component with a blank name, or one containing quotes, backslashes or line breaks. |
| `SOURCE_RENAME_UNSUPPORTED` | The edited source declares a different `name`. |
| `JAVA_SOURCE_NOT_EDITABLE` | Reading or saving the source of a Java component. |
| `LANGUAGE_NOT_SUPPORTED` | Creating a component in a language other than JavaScript, or uploading a Ruby file. |
| `JAVA_CUSTOM_COMPONENT_UPLOAD_DISABLED` | Uploading a `.jar` while Java uploads are off. |

## Deploying through the API

Deploy from CI or a script with the public endpoint:

```
POST /api/platform/v1/custom-components/deploy
```

| | |
|---|---|
| Body | `multipart/form-data` with one file part, `componentFile`. |
| Language | Taken from the file name's extension: `.jar`, `.js` or `.py`. |
| Authentication | `Authorization: Bearer <key>` with an [Admin API key](/platform/settings/admin-api-keys). Workspace and embedded API keys are rejected. |
| Authorization | The key's owner must have the `ADMIN` authority. |
| Success | `204 No Content`. |

The upload follows the rules in [Versions and drafts](#versions-and-drafts): a new name and version is created
published, an existing published version is replaced in place, and a version owned by a draft is rejected. A rule
violation, such as `JAVA_CUSTOM_COMPONENT_UPLOAD_DISABLED` or `VERSION_ALREADY_EXISTS`, answers `400` with a problem
detail. A key whose owner is not an administrator answers `403`.

```bash
curl -X POST "$BYTECHEF_URL/api/platform/v1/custom-components/deploy" \
  -H "Authorization: Bearer $BYTECHEF_ADMIN_API_KEY" \
  -F "componentFile=@acme_tasks.js"
```

`BYTECHEF_URL` is the server's base URL, for example `http://localhost:9555` for a local development server. The
deploy endpoint runs on the instance that hosts the coordinator.

The import dialog uses a second endpoint, `POST /api/platform/internal/custom-components/deploy`, with the same body
and the same `204` response. It authenticates with the signed-in user's session cookie and CSRF token instead of an API
key, and is meant for the ByteChef client, not for scripts.

## Restricting Java uploads

A Java custom component is arbitrary bytecode running in the server JVM. To accept only sandboxed script components,
turn Java uploads off:

| Property | Environment variable | Default |
|---|---|---|
| `bytechef.component.custom-component.java-enabled` | `BYTECHEF_COMPONENT_CUSTOM_COMPONENT_JAVA_ENABLED` | `true` |

With `false`:

- Uploading a `.jar`, through the import dialog or the API, fails with `JAVA_CUSTOM_COMPONENT_UPLOAD_DISABLED`.
- The import dialog accepts only `.js` and `.py` files.
- JavaScript and Python components, and Java components uploaded before the switch, keep working.

Code workflows have their own switch, `bytechef.workflow.code-workflow.java-enabled`. See
[Environment Variables](/platform/use-bytechef/self-hosted/configuration/environment-variables#component-configuration).

## How custom components run

A published, enabled custom component is part of the component catalog: it appears in the workflow editor, its
connection type appears on the Connections page, its tools appear among the AI agent's tools, and
[Component Visibility](/platform/settings/components/component-visibility) policies apply to it like to a built-in
component. Drafts are not in the catalog, so a draft cannot be run from a workflow. Publish it, or test the logic in a
[Script step](/platform/automation/build/workflows/code-workflows#scripting-languages) first.

- **JavaScript and Python** components run in the strict GraalVM sandbox, the same one behind the Script component:
  no host class access, no file system, process or thread creation, no environment access, and only the network
  access `context.http` provides. Each call gets a fresh guest context that evaluates the file again, and the sandbox's
  CPU, memory and time limits apply to each call. See [Script Sandbox](/platform/use-bytechef/self-hosted/configuration/script-sandbox)
  for the limits and how to tune them, and [Task Runners](/platform/automation/build/workflows/task-runners) for
  running guest code outside the server process.
- **Java** components are loaded in the server JVM through an isolating class loader per component version, so two
  components cannot see each other's classes. The loaded handler is cached and reused across calls. A new upload is
  picked up without a restart.

If a component fails to load, for example because its source no longer evaluates, it is left out of the catalog and
the server logs a warning naming it. The other components keep working.

## Audit

Every upload, through the import dialog or the API, is recorded in the [audit log](/platform/settings/audit-events) as
`CUSTOM_COMPONENT_SAVED`, with the component's id, name, version and language.

## Scaffolding a Java component with the CLI

The ByteChef CLI generates a Java component project from an OpenAPI specification:

```bash
bytechef component init --name my-component --open-api-path ./openapi.yaml --output-path .
```

| Option | |
|---|---|
| `--name`, `-n` | Required. The component name; it is lower-cased. |
| `--output-path`, `-o` | Required. Where to write the generated project. |
| `--open-api-path` | A local file or an `http(s)` URL. The command generates nothing without it. |
| `--base-package-name` | The package of the generated classes. Defaults to `com.bytechef.component`. Change it for a custom component, since classes in `com.bytechef` packages are not loaded from a custom component jar. |
| `--version`, `-v` | The component version. Defaults to `1`. |
| `--internal-component` | `true` for a component that ships with the platform. Defaults to `false`. |

The generated code is yours to edit. Build it into a jar that meets [the Java contract](#the-java-contract) and upload
it. For a REST API that needs no code at all, an [API connector](/platform/settings/components/api-connectors) turns
the specification into a component directly.
