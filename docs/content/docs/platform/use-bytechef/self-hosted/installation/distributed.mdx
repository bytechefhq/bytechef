By default ByteChef runs as a single monolith process (`server-app`) that contains the workflow
coordinator, the task workers, all domain services, and the HTTP API. The Enterprise Edition can
instead be deployed as a set of cooperating microservices, so that task execution scales
independently from the API and coordination layers.

This page describes the services, how a request moves between them, how to configure them, and how
to start them with the shipped Docker Compose file.

> **Edition note:** the distributed apps live under `server/ee/apps/` and run with
> `bytechef.edition: ee`. Distributed mode is an Enterprise Edition deployment model.

## The services

| Service | App | Role |
|---|---|---|
| API gateway | `api-gateway-app` | The only app the browser talks to. Serves the web client, owns users, login, and the user GraphQL schema, keeps the login session in Redis, and routes `/api/**`, `/graphql`, and `/webhooks/**` to the apps behind it. |
| Configuration | `configuration-app` | Projects, workflows, deployments, platform and embedded configuration, API keys, and connected users. |
| Connection | `connection-app` | Connections (credentials to external services). |
| Execution | `execution-app` | Jobs, task executions, trigger executions, and the workflow-execution APIs. The only app that owns job state. |
| Coordinator | `coordinator-app` | The workflow engine's control plane: starts jobs, runs task dispatchers (condition, loop, fork/join, each, map, parallel, subflow, approval), and puts task executions on the message broker. Loads **no** components. |
| Worker | `worker-app` | Runs task executions taken from the broker. The only app with the component modules on its classpath, and the app other services ask for component definitions. Scale it horizontally for throughput. |
| Scheduler | `scheduler-app` | Quartz-backed (JDBC job store) schedules, polling triggers, and delayed wake-ups. |
| Webhook | `webhook-app` | Receives inbound `/webhooks/**` requests, approval and callback links, and turns them into trigger events. Synchronous webhooks run their job inside `webhook-app` and keep the job's state on `execution-app`. |

Two more apps exist under `server/ee/apps/` but are not part of the Compose deployment:
`runtime-job-app` (a one-shot workflow runner with its own in-memory configuration) and
`ai-gateway-app`.

The coordinator owns job state transitions and puts task executions on broker queues; workers
consume those queues, run the component action, and send completions back. All coordinator and
worker traffic goes through the message broker.

## How a request flows

1. **Browser to gateway.** The browser loads the client from `api-gateway-app` and logs in there.
   The gateway stores the login session in Redis (Spring Session).
2. **Gateway to an app.** The gateway forwards the request, session cookie included, to the app that
   owns the path. Every browser-facing app reads the same session from Redis, so a user logged in
   at the gateway is logged in everywhere.
3. **App to app.** When an app needs data or work another app owns, it calls that app over
   **gRPC**. Every call carries the shared service token, the current tenant, and, for a user who
   logged in through the web session, that user's login and authorities. The receiving app rejects
   calls without the token. A failure on the receiving app comes back to the browser as 400 for a bad
   request, 404 for a missing resource, and 500 for anything else.
4. **Discovery.** Apps register in Redis under their `spring.application.name` and publish their
   gRPC port in the registration. Callers find each other through that registry; there are no static
   service addresses. A fixed address can still be set per service with
   `bytechef.remote.grpc.targets.<app-name>`.

There is no REST between services: the browser-facing APIs are HTTP, everything service to service
is gRPC or the message broker.

## Required infrastructure

- **PostgreSQL 15+** - one shared database. The `migrate` service (`migration-app`) applies every
  Liquibase changelog once before the apps start; the apps themselves run with Liquibase disabled.
- **Redis** - login sessions and service discovery.
- **Caches** - `bytechef.cache.provider` stays `CAFFEINE`: the distributed apps keep their caches in
  memory. Set to `REDIS`, they log a warning and keep `CAFFEINE`.
- **Message broker** - `bytechef.message-broker.provider` set to `AMQP` (RabbitMQ, the Compose
  default), `REDIS`, `KAFKA`, or `AWS`. The `MEMORY` provider is in-process only and **cannot** be
  used in distributed mode.
- **SMTP** - the Compose file starts [Mailpit](https://mailpit.axllent.org/) so sign-up and
  password-reset mail can be read at `http://localhost:8025`. Point `BYTECHEF_MAIL_HOST` and
  `BYTECHEF_MAIL_PORT` at your own server in production.

## Configuration

Every app is configured through environment variables only. The Compose file passes the same set to
each app; these must be set before it starts:

| Variable | Purpose |
|---|---|
| `POSTGRES_PASSWORD` | Database password, also used for the bundled PostgreSQL container. |
| `RABBITMQ_PASSWORD` | Broker password, also used for the bundled RabbitMQ container. |
| `BYTECHEF_ENCRYPTION_KEY` | Encryption key for stored credentials (`openssl rand -base64 16`). |
| `BYTECHEF_SECURITY_REMEMBER_ME_KEY` | Remember-me cookie key (`openssl rand -base64 32`). |
| `BYTECHEF_REMOTE_GRPC_SERVICE_TOKEN` | Shared secret on every gRPC call between apps (`openssl rand -hex 32`). An app that serves gRPC refuses to start without it. |

Optional variables include `BYTECHEF_PUBLIC_URL` (default `http://localhost:8080`),
`BYTECHEF_PORT` (the gateway's published port, default `8080`), `BYTECHEF_MESSAGE_BROKER_PROVIDER`
(default `AMQP`), and `MAILPIT_UI_PORT` (default `8025`).

gRPC settings, under `bytechef.remote.grpc`:

| Property | Default | Purpose |
|---|---|---|
| `service-token` | none | The shared secret above. |
| `plaintext` | `false` | Send gRPC without TLS. Set it to `true` only on a trusted network, such as the Docker Compose network; the Compose file does. |
| `deadline` | `10s` | Longest an ordinary call between apps may take. |
| `execution-deadline` | `1h` | Longest a call that runs component code on another app may take, such as an action or a trigger. |
| `max-inbound-message-size` | `64MB` | Largest message an app accepts, such as all component definitions with their icons. |
| `targets.<app-name>` | discovery | Fixed address for one app instead of discovery. |

With `plaintext` off, each app that serves gRPC needs a TLS certificate: set
`spring.grpc.server.ssl.bundle` to a Spring SSL bundle. An app with neither TLS nor
`plaintext: true` refuses to start rather than serving gRPC unencrypted.

## Running it with Docker Compose

The repository root contains `docker-compose.microservices.yml`. Build the jars and the client,
then start everything:

```bash
./gradlew :server:ee:apps:api-gateway-app:bootJar :server:ee:apps:configuration-app:bootJar \
  :server:ee:apps:connection-app:bootJar :server:ee:apps:coordinator-app:bootJar \
  :server:ee:apps:execution-app:bootJar :server:ee:apps:migration-app:bootJar \
  :server:ee:apps:scheduler-app:bootJar :server:ee:apps:webhook-app:bootJar \
  :server:ee:apps:worker-app:bootJar
(cd client && npm run build)

export POSTGRES_PASSWORD=... RABBITMQ_PASSWORD=...
export BYTECHEF_ENCRYPTION_KEY=$(openssl rand -base64 16)
export BYTECHEF_SECURITY_REMEMBER_ME_KEY=$(openssl rand -base64 32)
export BYTECHEF_REMOTE_GRPC_SERVICE_TOKEN=$(openssl rand -hex 32)

docker compose -f docker-compose.microservices.yml up -d --build --wait
```

Compose starts PostgreSQL, Redis, RabbitMQ, and Mailpit, runs `migrate` to completion, then starts
the eight apps and waits until each reports ready on `/actuator/health/readiness`. Open
`http://localhost:8080` and sign up; the confirmation mail is in Mailpit.

Keep the encryption key: credentials stored with one key cannot be read with another.

## Worker queues and scaling

Workers subscribe to broker queues with per-queue concurrency configured under
`bytechef.worker.task.subscriptions`:

```yaml
bytechef:
  worker:
    task:
      subscriptions:
        default: 10        # concurrent consumers on the default task queue
```

A workflow task can target a dedicated queue via its `node` property; the queue is created on
worker bootstrap and only workers subscribing to it will execute those tasks. This lets you run
specialized worker pools (for example, a pool with more memory for file-heavy components) by
deploying `worker-app` instances with different subscription maps.

Coordinator and worker roles are controlled by `bytechef.coordinator.enabled` and
`bytechef.worker.enabled` (both default `true`); in practice the roles are determined by which app
you deploy, since only `worker-app` has the component modules and only `coordinator-app` has the
dispatcher stack.

## Scaling out

The coordinator/worker split is shared-nothing on the dispatch path. Workers never talk to each
other, the coordinator holds no per-execution state in memory, and the broker is the only fan-out
point - so throughput scales with the number of worker instances rather than flattening against a
shared singleton.

| Action | Effect |
|---|---|
| Add worker instances | More concurrent task throughput. Each instance consumes its subscribed queues independently. |
| Add domain-app or gateway instances | More API throughput; more runs admitted per second. |
| Remove a worker mid-run | Its in-flight tasks are redelivered to another worker (at-least-once, per your broker - see [Message brokers](/platform/use-bytechef/self-hosted/configuration/message-brokers)). |
| Restart the coordinator mid-run | Job state lives in the database, not in coordinator memory, so a surviving or restarted coordinator continues the run. |

Useful autoscaling signals:

| Signal | Scale |
|---|---|
| Broker queue depth or consumer lag growing | `worker-app` |
| Worker CPU saturation | `worker-app` |
| Gateway or API latency growing | `api-gateway-app` and the domain apps behind it |

Kubernetes HPA on the Micrometer metrics described in
[Observability](/platform/use-bytechef/self-hosted/management/observability) covers the common cases.

### What does not scale by adding instances

- **PostgreSQL.** The database is the durable backbone and is scaled vertically (or split by tenant
  schema). The architecture pushes the bulk of the work onto workers, but Postgres is still the
  single shared store.
- **The scheduler.** The shipped Quartz configuration is not clustered - run exactly one
  `scheduler-app` instance. See [Scheduler backends](#scheduler-backends) below.

### Idempotency

At-least-once delivery means a task can be delivered more than once under failure, and auto-resume
after a crash re-runs the interrupted task from the last completed node. Components that write to
external systems should therefore be safe to re-run: every task execution carries a stable job and
task execution id you can use as an idempotency key for the downstream API.

### Suspended state survives the hop

A workflow that suspends (waiting on an approval, a delay, or an external signal) persists its state
to the database with **type fidelity**: each value is stored as a `TaskStateValue(Object value,
String classname)` record with Spring Data JDBC converters on either side, so a resume reconstructs
the original Java types rather than a generic map. A long-running workflow can therefore suspend on
one worker and resume on another.

## Scheduler backends

`BYTECHEF_SCHEDULER_PROVIDER` (property `bytechef.scheduler.provider`) selects how time-based work is
scheduled. Both backends drive the same four things:

- **Schedule (cron) triggers** in user workflows.
- **Polling triggers** that periodically check an external system.
- **Dynamic webhook trigger refresh** - re-registering a provider-side webhook subscription before
  it expires.
- **One-time tasks** - delayed wake-ups for suspended runs.

OAuth2 connection-token refresh is scheduled through the same backend by a separate scheduler
component.

### `QUARTZ` (default)

`scheduler-app` runs [Quartz](https://www.quartz-scheduler.org/) with a **JDBC job store** against
the shared database (`spring.quartz.job-store-type: jdbc`, the PostgreSQL driver delegate, and
`initialize-schema: never` - the Quartz tables are created by Liquibase, not by Quartz itself).
Schedules therefore live in the database and survive a restart.

<Callout type="warn">
  Quartz clustering is not enabled in the shipped `scheduler-app` configuration. Run exactly one
  `scheduler-app` instance. Two non-clustered instances sharing one job store will contend and can fire
  a schedule twice.
</Callout>

### `AWS` (EventBridge Scheduler)

For AWS-native deployments, ByteChef creates **EventBridge Scheduler** schedules whose target is an
SQS queue, and consumes those queues with SQS listeners:

| Queue | Carries |
|---|---|
| `scheduler-schedule_trigger_queue` | Cron trigger fires |
| `scheduler-polling_trigger_queue` | Polling trigger fires |
| `scheduler-dynamic_webhook_trigger_refresh_queue` | Webhook subscription refreshes |
| `scheduler-one_time_task_queue` | Delayed one-time wake-ups |

Schedules are created with the target role `arn:aws:iam::<accountId>:role/schedule-role` and the
queue ARNs derived from `BYTECHEF_CLOUD_AWS_REGION` and `BYTECHEF_CLOUD_AWS_ACCOUNT_ID`, so the
credentials you configure need permission to create and update EventBridge schedules, and the role
needs permission to send to those queues. Schedules then live in AWS rather than in your database,
and their availability is AWS's concern rather than yours.

Switching backends is a provider change plus a replay of existing schedules; workflow definitions are
unaffected.

## Plan-limit enforcement in HA

<Callout type="warn" title="Coming soon">
    Plan-limit enforcement is on the upcoming release track and is not yet available in the latest
    released version of ByteChef.
</Callout>

If you configure a plan tier (`bytechef.plan.tier`), rate limits and concurrency slots are
enforced per node by default - an N-node deployment admits up to N× the budget. For strict
global limits set:

```yaml
bytechef:
  plan:
    enforcement:
      provider: redis
```

on every app that admits work (the gateway-fronted domain apps and the coordinator). This moves
the token buckets and the per-tenant concurrency counters onto the shared Redis instance; both
fail open if Redis is briefly unreachable, so an enforcement hiccup never blocks traffic.

The monthly-cost cap and the quota checks (workspaces, members, storage) read shared database
state, so they are naturally global and need no Redis provider.

## Broker redelivery

<Callout type="warn" title="Coming soon">
    The Redis pending-entry reclaim described here is on the upcoming release track and is not yet
    available in the latest released version of ByteChef.
</Callout>

When Redis is the message broker, redelivery after a worker crash is handled by a consumer-group
pending-entry reclaim: every consumer sweeps its queue's pending entries (XPENDING), claims
entries idle for 60+ seconds (XCLAIM), and re-runs them through the normal invoke-then-ack path.
Semantics are at-least-once, matching the AMQP/Kafka brokers - a task interrupted mid-flight runs
again on another worker.

## Current limitations

- **Single tenant verified.** The Compose deployment has been verified with
  `BYTECHEF_TENANT_MODE=single` only.
- **Web-session users only between apps.** Only users who logged in through the gateway's web
  session are carried on gRPC calls. Embedded API-key and JWT authentication on `execution-app` and
  `webhook-app`, and passing embedded connected users between apps, are not yet available.
- **One database.** All services share one PostgreSQL database; there is no per-service schema
  split.
- **No Helm chart.** Kubernetes deployments of the microservices need your own manifests; the
  `bytechef` Helm chart deploys the monolith only.
- **Service token is the only trust root.** Any app holding the service token can call every other
  app as any user. Keep it secret and rotate it by restarting every app with the new value.
