---
title: "Flow Controls"
description: Branch, loop, parallelize, and error-handle your workflows with the built-in task dispatchers.
---

Flow controls are the structural building blocks of a workflow - they decide *which* steps run, *how many times*, and *what happens when something fails*. In the editor they appear alongside components in the step picker; under the hood each one is a task dispatcher that orchestrates its child tasks.

| Flow control | What it does |
|---|---|
| **Condition** | Run one of two branches depending on a boolean expression. |
| **Branch** | Route to one of several cases by matching a value (switch-style). |
| **Loop** | Repeat its child steps over a list or a fixed number of iterations, with access to the current item and index. |
| **Loop Break** | End the enclosing Loop early from inside one of its iterations. |
| **Each** | Execute child steps once per item of a list. |
| **Map** | Transform a list by running child steps for every item and collecting the results. |
| **Parallel** | Run several child steps at the same time and continue when all finish. |
| **Fork/Join** | Split into multiple named branches that run concurrently, then join their results. |
| **Subflow** | Invoke another workflow as a step and use its output - see [Subflows](/platform/automation/build/workflows/subflows). |
| **Approval** | Pause the workflow until a human approves or rejects - see [Human-in-the-Loop](/platform/automation/build/workflows/human-in-the-loop). |
| **On Error** | Catch a failing step and run a recovery branch instead of failing the run. |
| **Terminate** | End the workflow immediately from inside a branch. |
| **Graph** | Route through named nodes and expression-based transitions, with cycles allowed - a state machine *(coming soon)*. |

Every flow control's inputs and outputs are documented in the [flow-controls reference](/reference/flow-controls). Flow controls nest freely - a Loop inside a Condition inside a Fork branch is a normal workflow.

### Outputs

**Map** returns a value today: a list of each iteration's last-task output, in source-list order - reference it downstream as `${mapNodeName}`.

> **Coming soon.** Condition, Branch, and Fork/Join return values are on the upcoming release track and are not yet available in the latest released version of ByteChef.

Once released, **Condition** and **Branch** will return the last task's output from whichever case actually ran - an empty case returns nothing (`null`), and a Branch case with a literal value instead of tasks returns that value directly. **Fork/Join** will return an object keyed `branch_0`, `branch_1`, … in branch declaration order, each value being that branch's last task's output.

### Graph

> **Coming soon.** The Graph flow control is on the upcoming release track and is not yet available in the latest released version of ByteChef.

Where Loop repeats a fixed body and Condition/Branch pick one of a small, fixed set of paths, **Graph** is a state machine: a set of named nodes wired together by transitions that decide which node runs next. A transition can point forward, sideways, or back to a node that already ran - the shape you'd otherwise hand-build out of nested Loop and Condition steps for a "retry until it passes" or "send it back for another pass" flow.

#### Nodes and transitions

A graph's `nodes` list is an ordinary task list - each node **is** one task, and its `name` is the same task name you'd give any step elsewhere in the workflow, unique across the whole workflow. A node can be any task, including another flow control or a nested graph.

The `transitions` list is separate from `nodes` and holds the graph's edges. Each transition has:

- **`from`** - the node the transition leaves.
- **`to`** - the node the transition enters. Either a plain node name (a static edge) or a formula-mode expression that resolves to one, evaluated against the accumulated run context (a dynamic edge - see the LLM-routed example below).
- **`condition`** - an optional formula-mode expression evaluated against the accumulated run context. Blank or absent means the transition is unconditional. The expression must evaluate to an actual boolean - a truthy non-boolean value such as a number or a non-empty string (other than the literal `"true"`) is treated as false, so `condition: "=${count}"` does not do what it looks like; compare it explicitly instead, e.g. `condition: "=${count} > 0"`.

```yaml
- name: triage
  type: graph/v1
  parameters:
    startNode: classify            # optional; defaults to the first declared node
    maxTransitions: 100            # optional; default 100
    nodes:                         # a plain task list - every entry is an ordinary task
      - name: classify
        type: aiAgent/v1/chat
        parameters: { ... }
      - name: review
        type: ...
      - name: approve
        type: ...
    transitions:                   # the edges between nodes
      - from: classify
        to: approve
        condition: "=${classify.score} > 0.8"
      - from: classify
        to: review                 # no condition -> the node's default transition
      - from: review
        to: classify
        condition: "=${review.verdict} == 'REDO'"
      - from: review
        to: approve
```

**Evaluation rule:** on node completion, take that node's outgoing transitions; evaluate the conditional ones in declared order, first truthy `condition` wins; if none matched take the first unconditional one; if there is none the node is terminal. If a node has more than one unconditional transition, the first declared one is taken - the editor warns about this, but it's also the runtime rule.

A dynamic `to` that resolves blank counts as "did not match" and evaluation continues to the next candidate - the same as a `condition` that evaluates false. Once a transition is chosen, though, its resolved target must name a real node: if `to` evaluates to a non-blank value that isn't one of the graph's declared node names, the run fails - the error names the source node and the value that was produced (`Unknown graph transition target node: '<to>' resolved from node '<from>'`) rather than the graph silently stalling.

A run starts at `startNode` if set, otherwise the first declared node.

#### Cycles and the transition budget

Because a transition can target a node that already ran - including the node it leaves from - a graph can express review loops and retry-until-done flows directly: `review` transitioning back to `classify` above is a normal edge, not an error. To keep a cycling graph from running forever, every graph carries a **transition budget**, `maxTransitions` (default 100). Every node-to-node hop counts against it; once the budget is used up the run fails cleanly instead of looping indefinitely.

Context accumulates across the whole run the normal way: it is last-write-wins, so a node that runs a second time (after a cycle back to it) sees everything produced so far, including its own earlier run, and a data pill referencing a step inside that node resolves to that step's *most recent* execution.

#### Outputs

`${graphName}` resolves to the **terminal node's output** - the same convention as Condition and Branch above. When the terminal node produced no output, `${graphName}` is `null`.

#### In the editor

The graph's canvas is a free-form box: drag nodes to arrange them however makes sense for the flow, drag from a node's transition handle to another node to connect them with a transition, and click an edge to set its `condition`. The box header carries **Add node**, which picks a component to add to the graph, and **Auto-arrange**, which lays every node and edge out automatically when you'd rather not position them by hand.

A **Start** pill marks where the run begins; drag the edge leaving it onto a different node to change `startNode`. Selecting the graph node itself lists every **transition** in its Properties tab, grouped by the node each one leaves. Some things only that list can show: the declared order within a group, which is the priority conditions are evaluated in; a warning when a node has more than one unconditional transition; and a transition whose `from` or `to` names a node the graph no longer declares, which cannot be drawn on the canvas at all.

#### An LLM-routed example: ticket triage

A common use of Graph is letting an AI Agent node choose the next node itself instead of hand-writing the routing logic. Give the agent a **structured output** schema with an enum of the possible next states, and point a transition's `to` straight at the field the model fills in.

Take a support-ticket triage flow: an AI Agent node classifies an incoming ticket, and the graph routes to whichever node handles that outcome.

```yaml
- name: triage
  type: graph/v1
  parameters:
    startNode: classify
    maxTransitions: 20
    nodes:
      - name: classify
        type: aiAgent/v1/chat
        parameters:
          format: SIMPLE
          systemPrompt: >-
            You triage incoming support tickets. Choose exactly one category and say
            how confident you are in that choice.
          userPrompt: "Subject: ${trigger.subject}\n\n${trigger.body}"
          response:
            responseFormat: JSON
            responseSchema: |
              {
                "type": "object",
                "properties": {
                  "decision": {
                    "type": "string",
                    "enum": ["refund", "technical", "escalate", "resolved"]
                  },
                  "confidence": { "type": "number" }
                },
                "required": ["decision", "confidence"]
              }
      - name: refund
        type: ...
      - name: technical
        type: ...
      - name: escalate
        type: ...
      - name: resolved
        type: ...
    transitions:
      - from: classify
        to: "=${classify.decision} ?: 'escalate'"
```

Setting `response.responseFormat` to `JSON` (with a `response.responseSchema` describing the shape) is what turns the AI Agent's reply from free text into a structured object - the model's answer is parsed against the schema, and its properties become data pills exactly like any other step's output: `${classify.decision}`, `${classify.confidence}`. The transition's `to` expression then does nothing more than forward the model's own `decision` as the target node name, falling back to `'escalate'` with the Elvis operator (`?:`) if the model produced no usable answer at all - a parsing failure or an empty response - so a bad turn from the model routes to a safe node instead of failing the whole run.

Because the schema's enum only ever produces one of `refund`, `technical`, `escalate`, or `resolved`, every value the model *can* return already names a real node in the graph - the fallback exists for "the model produced nothing," not for an out-of-vocabulary answer.

**Gating on confidence.** A dynamic `to` doesn't have to trust the model outright. Declare two transitions off the same node and let `condition` pick between them:

```yaml
transitions:
  - from: classify
    to: "=${classify.decision}"
    condition: "=${classify.confidence} > 0.7"
  - from: classify
    to: human_review
```

The first transition, whose `to` reads the model's own `decision`, only matches when confidence clears the threshold; anything less certain falls through to the second, unconditional transition and lands on a `human_review` node instead - worth adding to the graph with a task that notifies a person and lets them pick a category before the graph continues.
