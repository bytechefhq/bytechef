A project groups related workflows. It is also the unit that ByteChef versions, publishes and deploys. This page
describes how to create and manage projects and add workflows to them.

## A project is the unit you publish

The project boundary decides which workflows are released together.

- **Workflows in one project are published together.** Publishing saves every workflow in the project
  into one immutable version. You cannot publish part of a project.
- **Versions are immutable.** After a version is published, its workflows do not change; further edits
  go to a new draft. A published version is what a deployment runs, and it stays available for
  rolling back. See [Deploy Workflows](/platform/automation/deploy/workflows).
- **Deployment is separate from publishing.** A project deployment binds one published version to
  one [environment](/platform/automation/deploy/environments), with its own connections and its own
  set of enabled workflows. The same version can be deployed to several environments.
- **A project belongs to exactly one workspace.** Data tables, knowledge bases, and connections are
  workspace-scoped, so they are shared across the workspace's projects rather than owned by one of
  them. See [Workspaces](/platform/automation/settings/workspaces).

Access is governed by [workspace roles](/platform/settings/users#roles-and-permissions) - Admin,
Editor, or Viewer - granted per member on the workspace and applying to every project inside it.
There are no per-project roles. In the Enterprise Edition a project also has a **visibility**, which
decides who in the workspace can see it at all; see [Project visibility](#project-visibility) below.

A project has a **draft** that the editor writes to, and any number of **published** versions.
Deleting a project is permanent; export it first if you might need it again.

## Project visibility

<Callout type="warn" title="Coming soon">
    Project visibility is on the upcoming release track and is not yet available in the latest
    released version of ByteChef. It is an Enterprise Edition feature.
</Callout>

Every project carries one visibility:

| Visibility | Who can see the project |
|---|---|
| **Shared with workspace** (`WORKSPACE`) | Every member of the project's workspace. This is the default. |
| **Private** (`PRIVATE`) | The project's creator, plus anyone it is shared with. |

A project belongs to exactly one workspace, so it cannot be shared across the organization: the
`ORGANIZATION` level that connections have does not exist for projects.

**Specific people** is not a third level. It is a private project plus a list of named workspace
members who were given access. Switching a project back to **Shared with workspace** keeps that list,
so making it private again restores the same audience. Only members of the project's workspace can be
named.

### Everything in a project follows its visibility

A project's workflows, deployments and workflow executions have no visibility of their own: they are
exactly as visible as the project. When a project is private, a member who cannot see it

- does not find the project, its workflows, its deployments or its executions in any list or search, and
- is refused (HTTP 403, or a GraphQL `FORBIDDEN` error) when opening any of them directly.

Visibility comes on top of workspace roles, not instead of them: a member still needs the scope for
what they do, such as `WORKFLOW_EDIT` to change a workflow. Visibility only decides whether the project
exists for them. It does not stop anything from running: deployments of a private project keep
executing on their triggers as before.

Organization admins (the `ROLE_ADMIN` authority) see every project, private or not.

### Choosing and changing visibility

- **When creating a project**, the **New Project** dialog offers **Shared with workspace** and
  **Private**. People can be named only after the project exists.
- **On the Projects page**, a project's visibility shows as a badge next to its name. For the
  project's creator and for organization admins the badge is a button: click it to choose **Shared
  with workspace**, **Private** or **Specific people**, and pick members from the workspace list.
  Everyone else sees a read-only badge.
- **Inside a project**, the project menu has a **Visibility** item that opens the same choices. It
  is offered to the project's creator and to organization admins.

Changes apply immediately; there is no separate save step. A workspace admin may also change a
project's visibility and sharing through the API.

When a project is deleted, its list of named people is deleted with it.

Each change is recorded in the audit log as `PROJECT_VISIBILITY_CHANGED`, `PROJECT_ACCESS_GRANTED`
or `PROJECT_ACCESS_REVOKED`. See [Audit Events](/platform/settings/audit-events).

In the Community Edition every project is shared with its workspace and there is no visibility
picker.

## Create Project

![The Create Project dialog](projects/create-project.png)

<Steps>
<Step>

Navigate to the **Projects** tab.

</Step>
<Step>

Click on the **New Project** button located in the top right corner.

</Step>
<Step>

Enter a name for your project. Optionally, provide a description, select a category, and add relevant tags.

</Step>
<Step>

Click **Save**.

</Step>
</Steps>


The dropdown arrow next to the **New Project** button offers two more ways to start a project: **From Template** and **Import Project**.

![The New Project dropdown, showing From Template and Import Project](projects/new-project-menu.png)

## Create Project from Template

<Steps>
<Step>

Click the dropdown arrow next to the **New Project** button in the top right corner.

</Step>
<Step>

Select **From Template** from the dropdown menu.

</Step>
<Step>

Browse the template gallery, pick a pre-built or community-shared project template, and import it.

</Step>
</Steps>

For details on the gallery and the import flow, see [Templates](/platform/automation/build/workflows/templates).

## Import Project

<Steps>
<Step>

Click the dropdown arrow next to the **New Project** button in the top right corner.

</Step>
<Step>

Select **Import Project** from the dropdown menu.

</Step>
<Step>

Choose the project archive (`.zip`) file exported from ByteChef.

</Step>
<Step>

The imported project, together with its workflows, appears in the project list.

</Step>
</Steps>

## New Code Project

A code project defines its workflows in JavaScript or Python source instead of on the canvas. Code projects require an
Enterprise Edition deployment.

<Steps>
<Step>

Click the dropdown arrow next to the **New Project** button in the top right corner.

</Step>
<Step>

Select **New Code Project** from the dropdown menu.

</Step>
<Step>

Pick the **Language** (JavaScript or Python), give the project a **Project Name**, and optionally add a
**Description**, a **Category** and **Tags**. ByteChef creates the project as a draft from a starter source and opens
it in the code editor.

</Step>
<Step>

Edit the source and save. Saves change the draft only; publish the project from its header when you're ready, exactly
like a visual project.

</Step>
</Steps>

To bring in an existing code project instead - a `.js`, `.py` or Java `.jar` file - pick **Import Code Project** from
the same menu; the upload is published right away. The
[sample repositories](/platform/sample-repositories#code-workflows) have a ready-made project in each language. A code
project runs on the same engine as a visually built one - see
[Code Workflows](/platform/automation/build/workflows/code-workflows) for the contract and
[Build Approaches](/platform/automation/build/workflows/build-approaches) for when to choose full-code.

## Workflows and Deployments

Each project row shows a summary such as **2 workflows - 1 deployment**. Click it, or the empty space
on the row, to expand the project. An expanded row has two tabs:

- **Workflows** - the project's workflows, with **New Workflow** on the right. The row always opens
  on this tab.
- **Deployments** - the project's deployments in the Development environment, with **New Deployment**
  on the right. See [View a Project's Deployments](/platform/automation/deploy/workflows#view-a-projects-deployments).

The deployment count covers all of the project's Development deployments, enabled or not.

## Share Projects and Workflows as Templates

A project, or a single workflow from its own actions menu, can be shared as a **template**. Anyone
with the link can import it into their own workspace. To back up a project instead, [export it](#export-project).

<Steps>
<Step>

Click on the three dots next to the project (or workflow) name and choose **Share**.

</Step>
<Step>

Enter a **Description** of what it does. The description is required.

</Step>
<Step>

Click **Export and generate template link**. The dialog shows the link and a **Copy link** button. The link has the form `/import/shared/projects/{uuid}` (workflows use `/import/shared/workflows/{uuid}`).

</Step>
<Step>

To disable the link, turn off the switch at the top of the dialog. The existing link stops working. Turn the switch on again to export the current version and re-enable the link.

</Step>
<Step>

If you change the project after sharing it, the dialog shows that an older version is shared. Click **Update template based on the current version** to share the current version.

</Step>
</Steps>

**Share with Community** is a separate action. It opens the template submission form in a new tab, for
projects and workflows that you want listed in the public gallery (see
[Templates](/platform/automation/build/workflows/templates)).
