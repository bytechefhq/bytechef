A workflow is a trigger followed by a sequence of steps (components and flow controls) that runs on the ByteChef workflow engine. Workflows belong to a [project](/platform/automation/build/workflows/projects) and are published and deployed with it. This page describes how to build a workflow in the visual editor, test it, and manage it.

#### Multiple triggers

A workflow can have **more than one trigger** - for example, run on a schedule *and* on an incoming webhook. On deployment every trigger that is not disabled is activated, and any of them can start a run of the same workflow.

- **Add a trigger:** click the dashed **+** slot next to the last trigger (to its right in the vertical layout, below it in the horizontal layout) and pick a trigger, or drag a trigger from the components list onto the slot.
- **Replace a trigger:** open the trigger's node menu and choose **Replace**, or drop a different trigger onto it.
- **Remove a trigger:** open the trigger's node menu, or right-click the trigger, and choose **Delete**. Delete is offered only while the workflow has more than one trigger, so a workflow always keeps at least one.
- **Test from a specific trigger:** click the trigger to open its panel, then click **Test** in the header. The test run starts from that trigger if it is enabled, with its sample output as the trigger's output. With no trigger panel open, a test run starts from the first enabled trigger.
- **Disable a trigger:** open the trigger's node menu (⋮) or right-click the trigger, and choose **Disable**. Choose **Enable** to turn it back on. The trigger keeps its configuration and is shown muted with a **Disabled** badge. See [Disabling a trigger](#disabling-a-trigger).

Every trigger connects to the first step of the workflow, and their connections join into a single line with one **+** for inserting a step after the triggers.

#### Disabling a trigger

Disabling a trigger keeps it in the workflow without letting it start runs. This is useful when you want to pause one trigger and keep the others.

Disabling takes effect the next time the workflow is published and deployed. A running deployment keeps its triggers until then.

While a trigger is disabled:

- It never starts a run, and it is not activated on deployment.
- Incoming requests to its webhook, chat or form URL are refused.
- It is not exposed through MCP, A2A or the API Platform.
- A subflow step that calls a workflow whose callable trigger is disabled fails.

A disabled trigger still needs its connections to be set up before you deploy.

The last enabled trigger cannot be disabled, so a workflow always keeps at least one. Manual triggers cannot be disabled.

### Node actions

Hover a node and open its **⋮** menu, or right-click the node.

| Node | Actions |
|---|---|
| Trigger | **Replace**, **Rename**, **Disable** / **Enable**, **Info**, **Delete** (only when the workflow has more than one trigger) |
| Task | **Cut**, **Replace**, **Copy**, **Paste**, **Rename**, **Disable** / **Enable**, **Reset position** (only when the node was moved), **Info**, **Delete** |

A disabled task is skipped during execution. It keeps its configuration and is shown muted with a **Disabled** badge.

### Canvas Layout

The editor arranges nodes automatically in a top-down flow as you build. Nodes are locked in place by default. Click **Unlock node movement** in the canvas toolbar to drag nodes to custom positions; the positions are saved with the workflow.

To discard your manual positions and snap everything back to the automatic layout, click the **Reset layout** button (the broom icon) in the canvas toolbar. To reset a single node instead, open that node's menu and choose **Reset position** (shown only when the node has been moved).

### Add Sticky Notes

Sticky notes let you annotate the workflow canvas - describe what a section does, leave review comments, or link a walkthrough video. They are documentation only and are never executed.

<Steps>
<Step>

Click **Add note** (the sticky note icon) in the canvas toolbar. A note appears in the middle of the visible canvas.

</Step>
<Step>

**Double-click** the note to edit its text. Markdown is supported. To embed a YouTube video, add `@[youtube](<video URL or ID>)` where the video should appear. Click outside the note or press **Esc** to save.

</Step>
<Step>

Drag the note anywhere on the canvas. Select it to show resize handles on its edges.

</Step>
<Step>

Hover over or select the note to show its toolbar. Pick a preset color, or open the custom color picker and enter any hex color; your recently used custom colors are remembered in your browser. The trash icon deletes the note.

</Step>
</Steps>

Sticky notes are saved with the workflow, so everyone who opens it sees the same annotations. They sit behind the workflow's nodes, don't affect the automatic layout, and can be moved even while node movement is locked. In read-only views notes are shown but can't be edited.

### Cluster roots on the canvas

A cluster root, such as an AI agent, is drawn by default as a frame on the main canvas, with its model, memory, RAG, guardrails and tools laid out inside it. Each element type has its own lane. The button in the top-left corner of the canvas switches between the inline frame and the cluster element editor dialog. It reads **Show cluster elements in the editor dialog** while the frame is shown and **Show cluster elements inline** while the dialog is used. The choice is remembered in your browser.

The frame starts locked. Unlock it from the frame header to drag its elements. The frame header also resets the elements' layout and collapses the frame to a compact card.

## Workflow Inputs

Workflow inputs are values supplied to a run from outside: a caller's parameters, a deployment configuration value, or a test value you enter in the editor. Define them in the **Workflow Inputs** panel.

![The Workflow Inputs sheet with the Create a new Input dialog open](workflows/workflow-inputs.png)

<Steps>
<Step>

In the workflow editor, click the **Workflow Inputs** icon in the right sidebar.

</Step>
<Step>

Click **New Input** and set the fields of the **Create a new Input** dialog:

- **Name** (required) - the key used to reference the input.
- **Label** (required) - the label shown when the input is filled in.
- **Type** (required) - one of Boolean, Date, Date Time, Integer, Number, String or Time.
- **Required** - whether a value must be provided. Default `False`.
- **Test Value** - a value used only when you test the workflow in the editor.

Click **Save**.

</Step>
<Step>

Use the row actions to edit or delete an existing input.

</Step>
</Steps>

Defined inputs are available downstream as [data pills](/platform/automation/build/workflows/data-pills) under the workflow's inputs.

In the workflow definition, inputs are stored in the top-level `inputs` list. The **Test Value** is not part of the definition; it is kept in the editor's test configuration.

```json
"inputs": [
  {
    "label": "Customer ID",
    "name": "customerId",
    "required": true,
    "type": "string"
  }
]
```

A step references an input by its name alone, without a node name: `${customerId}`.

## Editor Header Controls

The editor header, next to **Publish**, contains the controls for testing and deploying the current project.

### Deploy

**Deploy** (tooltip "Deploy the published project version") opens the deployment dialog for the current
project, the same dialog as on the project's **Deployments** tab. See
[Deploy Workflows](/platform/automation/deploy/workflows). Until the project has a published version,
**Deploy** is disabled with the tooltip "Publish the project before deploying it.", because a
deployment always uses a published version. The dialog has two tabs:

- **New** - creates a deployment (**Environment**, **Version**, **Name**, **Description**, **Tags**).
- **Change Version** - points an existing deployment to a different published version.

### Project Deployments

The **Project Deployments** button next to **Deploy** opens a side panel that lists the project's
deployments in the current environment. Use it to enable a deployment, change its version or open a
workflow's executions without leaving the editor. See
[View a Project's Deployments](/platform/automation/deploy/workflows#view-a-projects-deployments).

### Run, Test, and the Output panel

**Test** in the header runs the current workflow from its trigger and shows progress and results in
the **Output panel** at the bottom of the editor. While a run is in progress, the button changes to
**Stop**, which cancels the run. In a workflow with
[multiple triggers](#multiple-triggers), the run starts from the trigger whose panel is open if it is enabled, otherwise from
the first enabled trigger. If the trigger the run starts from is a
chat trigger, the button is labeled **Chat** and opens the [test chat panel](#test-with-chat); you run
the workflow by sending messages.

The button after **Publish** and **Deploy** (tooltip "Show the current workflow test execution output")
opens or closes the Output panel, so you can see the last run's result without starting a new run.

The canvas follows a test run as it executes. A task shows a blue status while it runs, then green with
its duration when it completes, or red when it fails. Edges along the path the run took are colored the
same way, so a branch the run did not take stays grey. A task that runs more than once, for example
inside a loop, shows its total time when the run has finished. Stopping a run, or a failed run, clears
the status of tasks that were still running.

The tools an [AI Agent](/platform/automation/build/workflows/ai/agent#seeing-which-tools-ran) calls are
colored the same way inside its frame and in the cluster element dialog. When the agent is drawn as a
compact card, the card shows the agent's own status and each element icon gets a ring: red if any
element of that type failed, blue if any is still running, otherwise green.

### Settings menu

The gear icon in the header opens the settings menu. It has a **Workflow** tab for the current
workflow and a **Project** tab for its project. The **Project** tab contains **Edit**, **Duplicate**,
**Share**, **Export**, **New Workflow**, **Workflow from Template**, **Import Workflow**, **Import n8n
Workflow** (requires an enabled AI provider), **Project History** and **Delete**. A small indicator on
the gear shows while changes are being saved and turns red when you are offline.

The left workflows sidebar offers the same actions: the **New Workflow** button creates a workflow in
the selected project, and its arrow menu contains **From Template**, **Import Workflow** and
**Import n8n Workflow**. The **+** button beside the project selector creates a new project from
scratch, from a template, or by importing one.

### Project History

**Project History** on the settings menu's **Project** tab opens a side sheet that lists every
version of the project: version number, publish date, a **Published** or **Draft** badge, and the
version description. It shows every version, regardless of which environment, if any, deploys it.
For deployments per environment, see [Deploy Workflows](/platform/automation/deploy/workflows).

![Project Version History, listing the draft and each published version](workflows/project-history.png)

Click the chevron next to a version, the draft included, to see which workflows changed in it compared
with the previous version. The list shows each added, removed or modified workflow, with the change
count for modified workflows, under a summary such as "3 workflows changed (1 added, 2 modified)". The draft is compared with
the last published version. Expanding or clicking inside the list doesn't select the version for restore.

Click a workflow in the list to open its changes in a dialog with three tabs:

- **Changes** - workflow-level changes such as the label and description, and the trigger, task, cluster
  element, input and output changes, with old → new values for every changed parameter. An added or
  removed workflow says so instead of listing changes.
- **Canvas** - a read-only canvas of the workflow with added nodes in green, modified nodes in amber,
  moved nodes in blue and removed nodes in red. A toggle switches between the previous and the selected
  version.
- **Definition** - a side-by-side diff of the workflow definition.

Values of sensitive parameters such as passwords, tokens and API keys are shown as `••••••`.

## Code Editor

Every workflow is stored as a JSON definition that you can edit in the code editor. Changes in the code editor are reflected on the canvas and the other way around. Use the code editor for bulk changes or to fix problems that are hard to fix on the canvas.

### Access the Code Editor

<Steps>
<Step>

Click the **Workflow Code Editor** icon in the right sidebar of the editor.

</Step>
<Step>

The code editor opens and shows the JSON definition of the workflow.

</Step>
</Steps>

![The editor control that opens the workflow code editor](workflows/code-editor-toggle.png)

A definition has a `label`, an optional `description`, the workflow `inputs`, the `triggers` list and the `tasks` list. Each trigger and task has a unique `name`, a `type` in the form `component/version/operation`, and its `parameters`. A minimal workflow with a manual trigger and one Logger step looks like this:

```json
{
  "label": "Log a greeting",
  "description": "",
  "inputs": [],
  "triggers": [
    {
      "label": "Manual",
      "name": "trigger_1",
      "type": "manual/v1/manual"
    }
  ],
  "tasks": [
    {
      "label": "Logger",
      "name": "logger_1",
      "parameters": {
        "text": "Hello from ByteChef"
      },
      "type": "logger/v1/info"
    }
  ]
}
```

The editor may also add a `metadata` object to a task. It holds editor state, such as the node position on the canvas, and does not change how the task runs.


### Add Component

To add a component in the code editor, look up its action and properties in the component reference and add a task object to the definition.

<Steps>
<Step>

Go to the [Component Reference](/reference) page.

</Step>
<Step>

Search for the component you want to add. This example uses the **Random Helper** component.

</Step>
<Step>

Click the **Random Helper** component to view its documentation.

</Step>
<Step>

In the Actions section, find the **Random Integer** action.

</Step>
<Step>

Under the `tasks` key, add a new object for the **Random Integer** action.

</Step>
<Step>

Enter the `label` for the UI display, e.g., `Generate Integer`.

</Step>
<Step>

Set the `name` as the action key, e.g., `generatedInt`.

</Step>
<Step>

Under `parameters`, specify the required properties. Here, we need `startInclusive` and `endInclusive` to generate a random integer between two numbers. Set `startInclusive` to `1` and `endInclusive` to `100`.

</Step>
<Step>

Add the `type` for this task: `randomHelper/v1/randomInt`. The `randomHelper/v1` is the component type, and `randomInt` is the action name.

</Step>
</Steps>

The task looks like this:

 ```json

    "label": "Generate Integer",
    "name": "generatedInt",
    "parameters": {
        "startInclusive": 1,
        "endInclusive": 100
    },
    "type": "randomHelper/v1/randomInt"
}
 ```

<Step>

Click the save icon (tooltip "Save current workflow"). Saving is disabled while the definition has errors.

</Step>
</Steps>
