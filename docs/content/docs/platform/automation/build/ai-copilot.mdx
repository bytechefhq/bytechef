The AI Copilot is an AI assistant built into the ByteChef editor. Use it to understand, design, build, and debug automation workflows, and to fill in individual fields, without leaving the editor.

> The AI Copilot is an Enterprise Edition feature and is disabled by default. See [Enabling Copilot](#enabling-copilot).

There are three ways to use Copilot:

- **Conversational Copilot** - a chat panel with **Ask** and **Build** modes for exploring and building whole workflows, scripts, skills, listing-page data, and more.
- **Guided generation** - menu items that open the Copilot panel in Build mode, pre-scoped to generating a whole workflow or skill from your description.
- **Inline generation** - sparkle buttons next to individual fields that generate a value, formula, JSON schema, sample output, or description from a short prompt.

---

## Conversational Copilot

Open the Copilot panel from the editor toolbar by clicking the **AI Copilot** button (sparkle icon). The panel header shows the **AI Copilot** title, a **Clean messages** button that clears the conversation and starts fresh, and a close button. The message composer at the bottom carries the **Build** toggle (off is Ask, on is Build) and the model picker (see [Choosing the model](#choosing-the-model)). If no AI provider is enabled yet, the panel shows a **No AI providers enabled** state with a **Go to AI Providers** button instead of the chat.

### Where it appears

Each surface has its own pair of Ask and Build agents with surface-specific tools and prompts.

| Surface | What it helps with |
|---|---|
| **Workflow editor** | Understand, design, and build the current workflow |
| **Code Editor** (Script component) | Generate and explain code blocks in JavaScript, Python, and Ruby |
| **Code workflow editor** | Ask and Build assistants scoped to a code-backed project or integration (see [Code Workflows](/platform/automation/build/workflows/code-workflows#copilot)) |
| **Cluster Elements** (AI Agent component, vector database components) | Generate full element configurations from scratch |
| **Workflow execution** | Analyze a finished or failed execution and debug errors |
| **Evals** (AI Agent editor) | Explain and edit an agent's evaluation scenarios, judges, and tests - the Copilot button sits in the **Evals** panel header, beside the agent editor's own |
| **Skills** | Explain, audit, and edit AI Skills - opens as a side panel for the open skill. To create a skill from a prompt, use **Create Skill → Create With AI** (see [Generating a workflow or skill from a prompt](#generating-a-workflow-or-skill-from-a-prompt)) |
| **Automation listing pages** - Projects, Project Deployments, MCP Servers, API Collections, Data Tables, Knowledge Bases, Context Stores, Skills, Files, Workflow Executions | A sparkle button in the page header opens a Copilot panel scoped to that page - Ask mode lists and reads the page's items, Build mode creates and modifies them. On Skills, this listing-page panel is in addition to the per-skill side panel described above |

On listing pages, opening Copilot while another Copilot conversation is open (for example, from a workflow editor) keeps the earlier conversation. Closing the listing-page panel returns you to it. Navigating to a different page closes the panel.

In the [embedded](/platform/embedded/get-started) product, the **integration workflow editor** has an integration-scoped Copilot panel, and the **workflow executions** sheet has an execution-analysis Copilot. These match the workflow editor and workflow execution surfaces described above.

Copilot outside the Embedded pages does not see Embedded projects: it cannot list, read, or change the automation catalog or your connected users' projects. The Copilot in the Embedded **Automation editor** can work with the catalog's projects and workflows, but not with connected users' projects.

### Ask mode

Ask mode is a **read-only** assistant for exploring and understanding the current surface. It cannot modify anything.

In the workflow editor, Ask mode has:

- Full context of the current workflow definition
- The last execution error on the workflow
- Read-only access to component and task definitions
- Grounding in the ByteChef documentation (see [How Copilot grounds answers](#how-copilot-grounds-answers))
- Optional internet search via Firecrawl or Brave (if configured)

Use Ask mode to get explanations, debug errors, research components, or plan changes before building. When a change is needed, it suggests switching to Build mode.

### Build mode

Build mode has full access to **create and modify** content on the current surface. In the workflow editor it follows a structured process:

> discover the right components → configure them → pre-validate each task → build → validate the full workflow → deploy

It fixes any validation errors before proceeding, and can deploy the finished workflow directly from the conversation.

### Interactive prompts

While building, Copilot may pause to ask you something rather than guess. In the workflow editor it can:

- Ask a short multiple-choice question to clarify intent
- List the connections available for a component and let you pick one (or start creating a new connection)
- Look up the real option values for a dynamic property (for example, a Slack channel or a spreadsheet column) and let you select one

You answer inline in the chat, and Copilot continues with your choice.

## Generating a workflow or skill from a prompt

Two menu items open a Copilot conversation pre-scoped to a specific build task, instead of the general-purpose panel you get from a surface's sparkle button.

| What | How to open | What it does |
|---|---|---|
| **Workflow** | In a project's workflow list (from the project list or project details), **Create Workflow → Generate with AI** | Opens the Copilot panel in **Build mode**, pre-scoped to generating a new workflow - trigger, actions, and data flow - in that project from your description |
| **Skill** | On the Skills page, **Create Skill → Create With AI** | Opens the Copilot panel in **Build mode**, pre-scoped to generating a new AI Skill (a `SKILL.md` and any bundled files) from your description |

Both open a regular Build-mode conversation, so you can keep refining the workflow or skill in the same conversation. Configure connections and other details afterward, as with any other workflow or skill.

A description that names the trigger, the systems, the fields and the conditions gives the best first draft. For example:

```text
When a new row is added to the "Leads" Google Sheet, skip it if the email column
is empty. Otherwise enrich the email with Hunter, create a contact in HubSpot with
the name, email and company, and post "New lead: <name> at <company>" to the
#sales Slack channel.
```

A description such as "sync my leads" leaves Copilot to guess the trigger, the target system and the field mapping.

## Inline generation

In the workflow editor, fields that Copilot can fill show a **sparkle** button. Click it, describe the value in plain language, and Copilot generates it in place.

{/* TODO screenshot: node properties panel with a field's sparkle button clicked open - the inline prompt popover where you describe the value to generate */} Each generator validates its output and retries once if the first attempt is not usable. If the second attempt also fails, it returns the draft with a note for you to review.

| Generator | Where | What it produces |
|---|---|---|
| **Value** | Any text property | A plain value for the field, using only data that exists in earlier steps |
| **Formula** | Properties that accept expressions | A single `=` expression, validated against the workflow's expression evaluator and the available functions |
| **JSON Schema** | The JSON Schema builder | A valid JSON Schema object for structured or typed properties |
| **Sample output** | A node's Sample Output editor | A realistic sample output (JSON object or array) for the step |
| **Description** | The Description field of a workflow or node | A concise description of the workflow or the selected step |

Inline generators reference earlier-step outputs (data pills such as `${nodeName.path}`) only when those outputs exist, and they validate formulas before returning them.

For example, on a number field, the **Formula** generator can turn the description "the order total plus 20% VAT" into a formula such as `=${trigger_1.body.total} * 1.2`, provided the trigger output has a `total` field.

The Sample Output editor opens Copilot as a full-height sidebar next to the editor instead of a one-shot prompt. You can refine the sample in conversation (for example, "add a nested address object" or "make it an array of five items"), and each reply updates the sample output in place.

## Choosing the model

By default, Copilot uses the workspace's configured chat model. To override it for a conversation, open the **model picker** in the composer, optionally filter with the **Search providers** box, expand a provider, and select a model. The selection applies to the rest of the conversation, and ByteChef remembers your last-used model per workspace.

{/* TODO screenshot: the Copilot model picker open - the provider search box, the "Use workspace default" item, and a provider expanded to show its model list */}

The picker lists the AI providers your workspace has activated for the current environment, using that environment's credentials. It also offers:

- **Use workspace default** at the top, which resets the conversation to the default model.
- **Configure credentials** on a provider that is not activated yet, which opens the [AI Providers](/platform/settings/ai/ai-providers) settings.
- **Choose model by ID** on providers that accept an arbitrary model ID, where you type the exact model name.

If no override is selected, or the selection cannot be resolved, Copilot uses the workspace default model.

## Dry-run validation

    Workflow simulation is on the upcoming release track and is not yet available in the latest
    released version of ByteChef.
</Callout>

When Build mode assembles a workflow, Copilot can **simulate** it before a real run. The workflow
executes end to end without external side effects: every action returns its declared sample output
instead of calling the external service. Copilot then reports per-node reachability and failure
reasons. The Build agent runs the simulation automatically to validate what it built; there is no
separate button.

## How Copilot grounds answers

Copilot indexes the ByteChef documentation and component references into a vector store and retrieves the most relevant passages on each turn (retrieval-augmented generation).

The documentation corpus is **instance-global**: it is the same for every workspace and tenant, so it is indexed once into a single shared table. Indexing runs at server startup and re-indexes only the documents that changed since the last run. The corpus is embedded with a dedicated key that is separate from per-tenant provider credentials (see [Documentation embeddings](#documentation-embeddings)).

## Enabling Copilot

Copilot is disabled by default. Use either of the following methods to turn it on.

### From AI Providers

Activate a provider on the [AI Providers](/platform/settings/ai/ai-providers) settings page and give it
credentials. Providers are activated **per environment**, so Copilot can be enabled in Development
and not in Production. The key is stored and rotated in ByteChef instead of in the deployment
configuration.

Use this method when the instance is already running: it needs no restart, and it uses the same
provider catalog as the [model picker](#choosing-the-model).

### From environment variables

Set the following variables to enable Copilot at startup, for example on an air-gapped installation
or a deployment whose configuration is managed outside ByteChef.

#### Anthropic (default provider)

```bash
BYTECHEF_AI_COPILOT_ENABLED="true"
BYTECHEF_AI_PROVIDER_ANTHROPIC_API_KEY="sk-..."
```

#### OpenAI (optional provider)

```bash
BYTECHEF_AI_COPILOT_PROVIDER="openai"
BYTECHEF_AI_PROVIDER_OPEN_AI_API_KEY="sk-..."
```

#### Documentation embeddings

Copilot embeds its instance-global documentation corpus into a single shared vector store table, in both single-tenant and multi-tenant deployments. Because the corpus belongs to the whole instance rather than to one tenant, it is embedded with a dedicated, operator-managed key. Select the embedding provider with `BYTECHEF_AI_COPILOT_EMBEDDING_PROVIDER` (`OPENAI` or `OLLAMA`):

```bash
BYTECHEF_AI_COPILOT_EMBEDDING_PROVIDER="OPENAI"
BYTECHEF_AI_COPILOT_EMBEDDING_API_KEY="sk-..."
```

This key is separate from the per-environment and per-tenant `BYTECHEF_AI_PROVIDER_*` keys. In cloud deployments, users configure their own AI provider in the UI while the operator's key embeds the Copilot documentation. With `OLLAMA`, the index uses `BYTECHEF_AI_PROVIDER_OLLAMA_URL` instead of an API key. When no embedding key is set, Copilot uses the embedding provider activated in the UI. When neither is configured, documentation indexing is skipped (the server still starts) and runs on the next restart after a key or provider is available.

> Anthropic does not provide an embedding model. When Anthropic is the chat provider, Copilot documentation still needs an embedding provider: `BYTECHEF_AI_COPILOT_EMBEDDING_PROVIDER` with its key or URL, or an OpenAI provider activated in the UI.

For the complete list of Copilot variables and every other ByteChef setting, see the [environment variables reference](/platform/use-bytechef/self-hosted/configuration/environment-variables#ai-copilot-configuration).
