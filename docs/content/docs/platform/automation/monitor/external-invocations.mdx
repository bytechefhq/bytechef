title: "External Invocations"
description: "A log of the calls made from outside ByteChef through your MCP servers and A2A servers - which tool or skill ran, how it ended, and how long it took."
---

When an AI client calls a tool on one of your [MCP servers](/platform/automation/deploy/mcp-servers),
or another agent calls a skill on one of your [A2A servers](/platform/automation/deploy/a2a-servers),
ByteChef records the call. **External Invocations** lists those records, so you can see which tools and
skills are being used, which ones fail, and how long they take. Open it from **External Invocations** in the left
sidebar, next to **Workflow Executions**.

The page is available on Enterprise Edition only.

<Callout type="info">
    A record holds the identity and outcome of a call only: which tool or skill ran, through which
    server, how it ended, and how long it took. The input parameters and the output are never stored.
</Callout>

---

## What is recorded

A record is written for every call that comes in through one of two surfaces:

| Surface | Calls recorded |
|---|---|
| **MCP** | Tool calls an AI client makes through an MCP server in the workspace: **component tools**, a component action exposed as a tool such as Slack's **Send Message**, and **workflow tools**, a project workflow exposed as a tool. |
| **A2A** | Skill calls another agent makes through an A2A server in the workspace. Each skill runs a project workflow. |

The call is recorded whether it succeeds or fails. A call to a tool, a skill or a server that is turned
off is rejected before it runs and is not recorded.

For a workflow tool or an A2A skill, the record also carries the id of the workflow execution the call
started, so you can find the run in [Workflow Executions](/platform/automation/monitor/workflow-executions).

Calls to the [management MCP server](/platform/settings/mcp-server), such as `listProjects` or
`buildWorkflow`, are not recorded.

The page lists automation calls only. Calls made through an embedded integration are recorded
separately and appear on the embedded [External Invocations](/platform/embedded/monitor/external-invocations)
page.

Tool calls an AI Agent makes while a workflow runs are not recorded here either. They appear in the
run's execution view, in the agent's call list, together with any approval a reviewer gave or refused.

## The invocations table

Each call is one row, newest first:

| Column | What it shows |
|---|---|
| **Status** | How the call ended, for example `SUCCESS`, `ERROR` or `TIMEOUT`. |
| **Tool** | The tool name the AI client called, or the name of the A2A skill. |
| **Surface** | Where the call came in: **MCP** or **A2A**. |
| **Server** | The MCP server or the A2A server the call came through. |
| **Source** | What ran: the component and operation of a component tool, such as `slack / sendMessage`, or the name of the workflow a workflow tool or a skill ran. |
| **Duration** | How long the call took, in milliseconds. |
| **Date** | When the call was made. |
| **Actions** | **View** opens the workflow run a workflow tool or skill started, with the input and output of each step. **Stop** stops that run while it is still going: the call ended with `TIMEOUT`, `APPROVAL_REQUIRED` or `SUSPENDED`. Both are unavailable for component tool calls, which start no workflow run. |

The list shows 50 rows per page. Use the **Refresh** button in the page header to load the latest
calls.

### How a workflow call ends

A workflow tool or an A2A skill starts a workflow run and waits for it. The status reflects where the run was when
the call returned:

| Status | The workflow run |
|---|---|
| `SUCCESS` | Completed, and the call returned its output. |
| `ERROR` | Failed, could not start, or was stopped before it finished. |
| `TIMEOUT` | Was still running when the call stopped waiting for it. |
| `APPROVAL_REQUIRED` | Paused at an approval step and waits for a person to decide. |
| `SUSPENDED` | Paused at a step such as a delay and continues on its own later. |

## Filter invocations

| Filter | Narrows the list to |
|---|---|
| **Surface** | Calls that came in through one surface. |
| **Status** | Calls that ended one way: Success, Error, Connection required, Timeout, Approval required, Approval denied or Suspended. |
| **MCP Server** | Calls made through one MCP server. The filter appears when the workspace has at least one MCP server. |
| **A2A Server** | Calls made through one A2A server. The filter appears when the workspace has at least one A2A server. |
| **Start date** / **End date** | Calls made within a date range. |

---

## Scope

The list is scoped to the current workspace and the current
[environment](/platform/automation/deploy/environments). Switching either one in the left sidebar
reloads the list and clears the filters. A call made through a server in Production does not appear
while you are looking at Development.

---

## Who can see it

Organization admins see every workspace's invocations. Other users see a workspace's invocations when
their [workspace role](/platform/automation/settings/users) lets them view workflows, which the
built-in Viewer, Editor and Admin roles all do. Connected users of an embedded integration cannot read
the log.

---

## Retention

Records are deleted after 90 days. A cleanup job runs once a day, at 02:30 server time. In a
multi-tenant installation it cleans up every tenant's records, and one tenant's failure does not stop
the others.

| Property | Purpose |
|---|---|
| `bytechef.external-invocation-log.retention-days` | How many days a record is kept. Defaults to `90`. |
