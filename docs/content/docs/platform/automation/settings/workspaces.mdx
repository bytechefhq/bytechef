A **workspace** is the boundary a team works inside. Projects belong to a workspace, and so do the
connections, data tables, knowledge bases, API keys, MCP servers, and A2A servers those projects use.
Workspaces share nothing with each other, so they are the unit for separating teams, business units,
or tenants.

Workspaces are administered from **Settings → Workspaces** in Automation (under **Organization** in the
Settings sidebar). The page requires the organization admin authority. The workspace you are in is
marked **Current**.

![The Workspaces page, with a row's actions menu open](workspaces/workspaces.png)

## What a workspace scopes

| Owned by the workspace | Notes |
|---|---|
| **Projects and their deployments** | Every project belongs to exactly one workspace. |
| **Connections** | Shared across the workspace's projects rather than owned by one of them. |
| **Data tables** | Workspace-scoped, so a lookup table is defined once and reused by every project. See [Data Tables](/platform/automation/data/data-tables). |
| **Knowledge bases** | Workspace-scoped in the same way. See [Knowledge Base](/platform/automation/data/knowledge-base). |
| **API keys** | Bound to the workspace and to an environment. See [API Keys](/platform/automation/settings/api-keys). |
| **MCP servers** and **A2A servers** | Bound to the workspace and to an environment. See [MCP Servers](/platform/automation/deploy/mcp-servers) and [A2A Servers](/platform/automation/deploy/a2a-servers). |
| **Members and their roles** | Managed per workspace. The workspace Users page is coming soon; see [Workspace Users](/platform/automation/settings/users). |
| **Git configuration** | One repository per workspace. See [Git Configuration](/platform/automation/settings/git-configuration). |
| **AI guardrails policy** | One content policy per workspace (coming soon). See [Guardrails](/platform/automation/settings/ai-agents/guardrails). |

All three [environments](/platform/automation/deploy/environments) exist inside every workspace.
Environments are not a workspace-level choice, and you do not model them with workspaces.

Settings that are **not** workspace-scoped: identity providers, the license, and the organization
user list are all instance-wide, and the encryption key protecting stored credentials is a single
deployment-level key rather than one per workspace.

## Create a workspace

1. Go to **Settings → Workspaces**.
2. Click **New Workspace**.
3. Enter a **Name** and an optional **Description**.
4. Click **Save**.

The new workspace starts empty.

## Edit, manage members, or delete

Each row's **⋮** menu offers:

- **Edit** - change the name and description.
- **Delete** - remove the workspace after a confirmation. Deletion cannot be undone.

</Callout>

## Workspace or project?

A **project** groups the workflows of one initiative and is the unit that gets published and
deployed. A **workspace** groups projects and the shared state around them.

| Situation | Reach for |
|---|---|
| Two teams that should not see each other's work | Separate workspaces |
| One team running several initiatives | Several projects in one workspace |
| Each customer isolated in a multi-tenant deployment | One workspace per tenant |
| Separating Development, Staging, and Production | Neither; use [environments](/platform/automation/deploy/environments) |
| Onboarding an acquired team | A new workspace |

Do not model stages as workspaces. Environments already exist inside every workspace, and versions
are deployed per environment. Separate workspaces per stage lose that and require copying projects
between workspaces by hand.
