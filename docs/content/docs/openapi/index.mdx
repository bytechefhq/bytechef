ByteChef exposes five public REST APIs for use from your own applications:

**Automation**

- **Workflow Executions** — fetch a workspace's workflow executions, and a single execution with its full detail. No reference page yet; its spec is not wired into the docs build.
- **[Projects](/openapi/automation-project-code-workflow)** — deploy a code-based project (CI/CD-style integration).
- **[Git](/openapi/automation-project-git)** — pull a project from its configured git repository.

Each embedded resource is reachable two ways, and the reference documents them separately because
the credential decides which one you can use.

**Backend — API Key**

Called from your own server. The connected user is named by the `{externalUserId}` path segment.

- **[Actions](/openapi/embedded-action)** — execute a component action for a connected user.
- **[Tools](/openapi/embedded-tool)** — list a connected user's available tools, and execute one.
- **[Integrations](/openapi/embedded-configuration-integration)** — the integrations available to your customers.
- **[Integration Instances](/openapi/embedded-configuration-integration-instance)** — a connected user's instance of an integration.
- **[Instance Workflows](/openapi/embedded-configuration-integration-instance-workflow)** — enable, disable and configure an instance's workflows.
- **[Connections](/openapi/embedded-configuration-connection)** — list a connected user's connections.
- **[Connected Users](/openapi/embedded-configuration-connected-user)** — update a connected user.
- **[User Workflows](/openapi/embedded-configuration-connected-user-project-workflow)** — a connected user's own workflows, including generation from a prompt.
- **[Workflow Catalog](/openapi/embedded-configuration-automation-workflow-project)** — the catalog projects available to connected users.
- **Workflow Executions** — fetch a tenant's workflow executions. Served by the internal API rather than a public spec, so it has no reference page; read executions in the ByteChef admin UI.
- **Tool Invocations** — fetch a connected user's tool and action invocation history. No public spec yet, so it has no reference page.

**Frontend — Signing Key JWT**

Called from the browser with a short-lived token your backend signs. The connected user comes from the token's `sub` claim, so these paths carry no user id.

- **[Integrations](/openapi/embedded-configuration-integration-frontend)** — the integrations available to the signed-in user.
- **[Integration Instances](/openapi/embedded-configuration-integration-instance-frontend)** — their instance of an integration.
- **[Instance Workflows](/openapi/embedded-configuration-integration-instance-workflow-frontend)** — enable, disable and configure that instance's workflows.
- **[Connections](/openapi/embedded-configuration-connection-frontend)** — list their connections.
- **[Connected Users](/openapi/embedded-configuration-connected-user-frontend)** — update the signed-in user.
- **[User Workflows](/openapi/embedded-configuration-connected-user-project-workflow-frontend)** — their own workflows, including generation from a prompt.
- **[Workflow Catalog](/openapi/embedded-configuration-automation-workflow-project-frontend)** — the catalog projects available to them.
- **[App Events](/openapi/embedded-webhook-app-event-trigger-frontend)** — fire an App Event to start every subscribed workflow.
- **[Request Trigger](/openapi/embedded-webhook-request-trigger-frontend)** — execute a single workflow synchronously and return its result.

**Platform**

- **[Custom Components](/openapi/custom-components)** — deploy a custom component to the platform. *Coming soon*.

## Base URLs

| API | Base path |
|---|---|
| Automation (all three) | `/api/automation/v1` |
| Custom Components | `/api/platform/v1` |
| Embedded (all) | `/api/embedded/v1` |

Prefix the operation path you see on each reference page with the corresponding base path, then with your ByteChef host (e.g. `https://your-bytechef-host.example.com`).

## Authentication

Every request carries a bearer token in the `Authorization` header. Which token you can use is not a
per-endpoint detail — it is the whole reason the reference is split in two, because the two
credentials identify the connected user in different ways.

| | **Backend** | **Frontend** |
|---|---|---|
| Credential | An **API Key** | A short-lived JWT signed with a **Signing Key** |
| Identifies the user by | the `{externalUserId}` path segment | the token's `sub` claim |
| Called from | your own server | the browser |

That difference is why the paths differ. An API Key says nothing about which of your end users a call
is for, so those operations carry the id in the path. A JWT already names the user, so its operations
do not — which in turn means an API Key cannot be used against them: there would be no user to act
for, and the request is rejected.

**Actions** and **Tools** are the exception that proves the rule. Their paths carry
`{externalUserId}`, so either credential resolves a user and both are accepted; they are listed under
Backend because that is how they are normally called.

Mint frontend tokens as described in [Installing the SDK](/platform/embedded/get-started/initial-setup/installing-the-sdk#2-generate-a-user-token-in-your-backend)
— the private key never reaches the browser, and the token is short-lived. See
[Signing Keys](/platform/embedded/administration/signing-keys) and
[Embedded API Keys](/platform/embedded/administration/api-keys) for issuing each credential.

Pass an optional `X-Environment` header (`DEVELOPMENT`, `STAGING`, or `PRODUCTION`) to scope the
request to a specific environment. If omitted, ByteChef uses `PRODUCTION`.
