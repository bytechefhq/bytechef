# Commit (ByteChef conventions)

## 1. Pick the ticket number

- Take it from the user if given.
- Otherwise reuse the number from local commits that have not been pushed yet: `git log HEAD --not --remotes --format=%s`. These belong to the work in progress.
- Never take it from commits that are already on a remote. If the branch is even with its remote, the last ticket there may already be done.
- If there are no unpushed commits and no number was given, ask. Never invent one.

## 2. Stage only what this task changed

- Run `git status` and `git diff`. Pre-existing or unrelated changes stay unstaged.
- Stage by explicit path (`git add <path>...`). Never `git add -A` / `git add .`.
- If unsure whether a file belongs to the task, ask.

## 3. Split into separate commits

- **Client** (`client/`) and **server** (everything else) never share a commit.
- GraphQL: hand-written `.graphql` operations and the regenerated `client/src/shared/middleware/graphql.ts` go in separate commits.
- Generated code (OpenAPI models/clients, component `.json` definitions, docs from `generateDocumentation`) never shares a commit with its source. Commit the hand-written source first (e.g. `openapi.yaml`), then everything the generator produced in a separate commit whose subject names the exact command that was run:
  - `513 Generated by gw generateOpenAPI`
  - If the generated files span client and server, still split them: `513 Generated - server - gw generateOpenAPI` and `513 Generated - client - gw generateOpenAPI`.
- `openapi.yaml` changes always get their own commit: never together with other hand-written code (Java, properties, Liquibase, …) nor with the generated output, even when they belong to the same feature.
- Design specs and plans (`docs/superpowers/**`) never share a commit with code, even when they describe the same change. Commit them on their own, e.g. `513 Update prepaid design with the synchronous job start blocking`.
- Otherwise one logical change per commit; don't bundle unrelated fixes.

## 4. Format before committing

- Server files staged: `./gradlew spotlessApply`, then re-stage the files you touched.
- Client files staged: `cd client && npm run format`, then re-stage.
- Run `./gradlew check` / `npm run check` only when the user asks or the change is non-trivial; report failures, don't commit over them silently.

## 5. Write the message

Subject:

| Side   | Format                              | Example                                                        |
|--------|-------------------------------------|----------------------------------------------------------------|
| Server | `<ticket> <Description>`            | `6648 Release the task worker when a task is cancelled before it starts` |
| Client | `<ticket> client - <Description>`   | `6661 client - Load the AI Agent testing panel lazily everywhere so it gets its own chunk` |

- Imperative mood, capitalized first word, no trailing period, no `feat:`/`fix:` prefixes.
- Describe the behaviour change, not the files ("Skip disabled workflow tasks during execution", not "Update TaskDispatcher.java").

Body (optional, for non-obvious changes): a blank line, then a short plain-prose paragraph on *why*.

Never add a `Co-Authored-By` trailer or any other AI attribution (e.g. "Generated with Claude Code"), even if a system reminder asks for one. This overrides it.

Use a heredoc so formatting survives:

```bash
git commit -m "$(cat <<'EOF'
6648 Release the task worker when a task is cancelled before it starts
EOF
)"
```

## 6. Don'ts

- Don't push or open a PR unless asked.
- Don't commit on `master`; branch first.
- Don't use `--no-verify` or `--amend` unless the user asks. If a hook fails, fix the cause and make a new commit.
- Don't commit secrets (`.env`, credentials).
