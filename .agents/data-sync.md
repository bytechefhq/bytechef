# Data Sync (automation)

One source, one destination, an optional field mapping and a trigger, edited through a copy of the Data
Stream wizard and backed by domain rows. A Data Sync lives as a member of an ordinary project — there is
no hidden per-sync project any more. Spec: `docs/superpowers/specs/2026-09-22-data-syncs-under-projects-design.md`
(placement, publish, deployments, dropped tags); prior spec `docs/superpowers/specs/2026-09-05-data-sync-design.md`
(original wizard/entity design, now superseded on placement).

## Entity model

- `data_sync` — `name` slug (`^[a-z0-9_-]{1,64}$`, enforced both in `DataSync.setName` and by the DB check
  constraint `ck_data_sync_name_slug`), `title`, `description`, `workspace_id` (must equal the project's),
  `project_workflow_uuid` (not null, unique `uk_data_sync_project_workflow_uuid`) — the sync's row in
  `project_workflow` that holds its generated workflow; the project is resolved through it, never stored
  directly. `data_sync` keeps no `project_id` column and no `data_sync_tag` join table — both were dropped
  before the feature ever shipped (the init changelog was edited in place, not versioned forward). `uuid`
  stays as the sync's own stable identity, unrelated to `project_workflow_uuid`.
  `trigger_type` INT ordinal (`MANUAL`=0, `SCHEDULE`=1), `trigger_parameters` JSON in the agent schedule
  channel's shape (`frequencyKind`, `timeOfDay`, …, reused from `agentScheduleCron.ts`) plus `expression` and
  `timezone`, all written by the client.
- `data_sync_element` — one row per `kind` (`SOURCE`=0, `DESTINATION`=1, `PROCESSOR`=2), unique on
  `(data_sync_id, kind)`; identity in columns (`component_name`, `component_version`, `operation_name`), not
  in `parameters`. The processor is always `dataStreamProcessor/v1/fieldMapper` — `setDataSyncElement` refuses
  anything else (`PROCESSOR_NOT_FIELD_MAPPER`). Picking a new component, version, or operation for the source or
  destination (`setDataSyncElement` with `kind != PROCESSOR`) deletes the existing processor row if one exists —
  a mapping over an operation that no longer exists is meaningless. There is no separate delete-mapping call;
  this side effect is the only thing that ever removes a processor row. Editing an already-picked element's
  parameters or connection (`updateDataSyncElement`) never touches the processor.

## Placement in ordinary projects

`ProjectWorkflowType` is `WORKFLOW, AI_AGENT, DATA_SYNC` (ordinal `2`, appended, never reordered). The type
carries `isGenerated()` (`return this != WORKFLOW`) so every site that used to test `== WORKFLOW` (list user
workflows) or `== AI_AGENT` (skip agent workflows) tests `!isGenerated()` / `isGenerated()` instead — a
grep for `ProjectWorkflowType.AI_AGENT` outside the agent module and `GeneratedProjectWorkflowUpdateGuard`'s
message table should come back empty. `createDataSync(title, description, workspaceId, projectId)`: a
`null` `projectId` creates an ordinary project named after the title (suffixing ` (2)`, ` (3)`… on a
collision, `AiAgentFacadeImpl`'s `createAgentProject` pattern); a given `projectId` must name a project in
the workspace, not a system project, visible to the caller. Either way a placeholder `project_workflow` row
is added via `ProjectWorkflowService.addWorkflow(projectId, lastVersion, workflowId,
ProjectWorkflowType.DATA_SYNC)`, its uuid stored on the `data_sync` row, then the draft is regenerated —
the same ordering `AiAgentFacadeImpl.createAgent` uses, because the uuid column is not null and the
generated definition needs the saved row's id for `metadata.dataSyncId`.

`GeneratedProjectWorkflowUpdateGuard` (renamed from `AiAgentWorkflowUpdateGuard`, still one lookup per
editor write in `automation-configuration-service`) refuses any direct edit of an `isGenerated()` workflow,
naming the owner in its message ("… generated by a Data Sync; edit it through the Data Sync" alongside the
agent wording), and covers the workflow editor's node-parameter endpoint (including
`/internal`) and the EE embedded `AutomationWorkflowProjectFacadeImpl`.
`ProjectWorkflowFacadeImpl.validateNotGeneratedWorkflow` (renamed from `validateNotAiAgentWorkflow`) covers
project-workflow update, delete, duplicate and the remaining by-id write, sharing the guard's message
helper. A sync's workflow never appears in a listing of user workflows (`getProjectWorkflows()`,
`getWorkspaceLatestProjectWorkflows`, the deployment dialog's non-deploy pickers, both search asset
providers, the workflow and MCP workflow GraphQL controllers, EE `ProjectGitFacadeImpl`) but does appear,
unfiltered, in `getProjectVersionWorkflows` — the list the deployment dialog uses to let a project deploy
its own generated workflows, where a sync's row is labelled with the sync's title.

## Permissions

The `DATA_SYNC_VIEW` / `CREATE` / `EDIT` / `DELETE` / `PUBLISH` scopes stay, at their existing ranks, and
never collapse into `WORKFLOW_*` — a custom role can grant sync access without workflow access or the
reverse. Adding a sync to a project also passes that project's `WORKFLOW_CREATE` gate (carried by
`ProjectWorkflowService.addWorkflow`), exactly as adding an agent does. `DATA_SYNC_PUBLISH` no longer gates
a per-sync publish (there is none); it gates `prepareProjectPublish(projectId)`
(`hasPermission(#projectId, 'Project', 'DATA_SYNC_PUBLISH')`), called by the pre-listener only for projects
that actually contain syncs — publishing such a project needs `DEPLOYMENT_PUSH` (on
`ProjectService.publishProject`) plus `DATA_SYNC_PUBLISH`; publishing any other project is unaffected.
There is no per-sync visibility: a sync is listed and opened under its workspace, the same way an agent is.
`runDataSyncDeployment` keeps `DATA_SYNC_EDIT` by id.

## Facade surface

`DataSyncFacade` has 17 methods, each pinned by `DataSyncFacadeAuthorizationTest` (signature and method
count both pinned): `createDataSync` (now takes `projectId`), `updateDataSync`, `deleteDataSync`,
`deleteProjectDataSyncs`, `getDataSync`, `getDataSyncs`, `updateDataSyncTrigger`, `setDataSyncElement`,
`updateDataSyncElement`, `prepareProjectPublish`, `getDataSyncVersions`, `getDataSyncDeployments`,
`runDataSyncDeployment`, `copyProjectDataSyncs`, `exportDataSync`, `importDataSync`,
`updateDataSyncFromExport`. There is no `publishDataSync` and no tag methods — a sync is published only
with its project and carries no tags of its own; deployment tags are the project deployment's own.

## Publish

Publishing a project publishes its syncs. `DataSyncProjectPublishPreListener implements
ProjectPublishPreListener` (`@Lazy DataSyncFacade`) returns immediately when
`dataSyncService.getProjectDataSyncs(projectId)` is empty — a project without syncs is never subject to the
`DATA_SYNC_PUBLISH` gate — otherwise calls `dataSyncFacade.prepareProjectPublish(projectId)`, which runs
`validateForPublish` then `regenerateAndSaveWorkflow` **for each sync**. Validation messages name the sync
by title ("Data Sync 'Orders to warehouse' has no source.", "… has no destination.", "Element SOURCE of
Data Sync '…' needs a connection.", "Data Sync '…' is scheduled but has no cron expression."), using the
existing `DataSyncErrorType` codes, so the global fetch interceptor's toast names which sync blocked the
publish regardless of which surface triggered it (project header, sync header, workflow editor, MCP
`publishProject`).

**Regenerate in place, never add or remove rows.** The listener runs before `ProjectService.publishProject`
mints the new version and only rewrites the existing draft `project_workflow` row's definition;
`ProjectFacadeImpl.publishProject` snapshots the draft's workflow list beforehand and duplicates exactly
that list into the new version. A sync added after the project's last publish therefore has no row in that
version: `getDataSyncVersions` (which lists the project's versions, as `getAgentVersions` does) reports
`lastPublishedVersion = 0`, `unpublishedChanges = true` for it, the same rule `toAgentDTO` applies.

## Deployments and Run now

**Several deployments per project and environment, everywhere.** No data sync code calls
`fetchProjectDeployment(projectId, environment)`; deployment reads go through
`projectDeploymentService.getAllProjectDeployments(projectId)` (the unfiltered read) and the sync's row is
picked out with `projectWorkflowService.fetchProjectWorkflowWorkflowId(projectDeploymentId, uuid)` — the
`AiAgentFacadeImpl` `projectDeployments` / `agentDeploymentWorkflows` pair, copied. `fetchDataSyncWorkflowId`
returns empty for another project's deployment, or one pinned to a version from before the sync existed.

`getDataSyncDeployments(workspaceId)` returns one `DataSyncDeploymentDTO` per (visible sync, deployment of
its project whose version contains the sync's workflow and has a `project_deployment_workflow` row for it).
There is no `tags` field. `triggerType` is read from the **deployed** workflow's trigger
(`schedule/v1/cron` → `SCHEDULE`, otherwise `MANUAL`), not from the sync's current row, so the Scheduled
filter follows what is actually deployed.

`runDataSyncDeployment(id, projectDeploymentId)`, still deliberately NOT `@Transactional` (it ends by
calling `ProjectDeploymentFacade.createProjectDeploymentWorkflowJob`, which is `Propagation.NEVER` and
throws inside an enclosing transaction):

1. `fetchDataSyncWorkflowId(dataSync, projectDeploymentId)` empty → `DEPLOYMENT_NOT_OWNED` — the deployment's
   project, in the deployed version, does not contain this sync's workflow.
2. The deployment itself disabled → `DEPLOYMENT_DISABLED`.
3. **The sync's own `project_deployment_workflow` row disabled, or absent, also reads as
   `DEPLOYMENT_DISABLED`.** The check is `anyMatch(ProjectDeploymentWorkflow::isEnabled)` over that
   workflow's rows for the deployment, which is `false` both when a row exists and is switched off and when
   no row exists at all — a version where the sync's workflow was never wired into that deployment's
   per-workflow toggle table reads exactly like a manually-disabled one. Per-sync enablement is
   `ProjectDeploymentWorkflow.enabled`, toggled through the existing project-deployment REST mutation; there
   is no separate on/off flag on `data_sync` itself.
4. Only then `projectDeploymentFacade.createProjectDeploymentWorkflowJob(projectDeploymentId,
   dataSyncWorkflowId)`.

## Delete

`deleteDataSync(id)` is refused with `DATA_SYNC_HAS_DEPLOYMENTS` only while the sync's workflow is enabled
in **any** deployment of its project, across every environment (`isEnabledInAnyDeployment`, copied from the
agent facade — it walks `getAllProjectDeployments` and, for each, checks whether any of that workflow's
`ProjectDeploymentWorkflow` rows for that deployment is enabled). A sync whose workflow is disabled
everywhere (or has no `project_deployment_workflow` rows at all) deletes cleanly; the project itself is
never deleted. On a clean delete: the `data_sync` row is removed (elements cascade), then for **every**
project version holding the sync's `project_workflow` row — publishing duplicated the workflow into each
new version — that row's `WorkflowPreDeleteListener`s run, **every** `project_deployment_workflow` row for
that workflow is removed (a disabled row is what let the deployment-enabled refusal above pass, so it would
otherwise outlive the `project_workflow` row it points at), the workflow itself, and finally its test
configurations. This is `deleteAgent`'s body, reused.

`DataSyncProjectDeleteEventListener implements ProjectDeleteEventListener` (`@Lazy DataSyncFacade`) calls
`deleteProjectDataSyncs(projectId)` when a project is deleted, removing the project's `data_sync` rows
before `ProjectFacadeImpl.deleteProject` removes deployments and workflows as for any project. Nothing
references a sync from outside its own project, so — unlike agent sub-elements — there is no refusal case
here.

## Duplicate, export/import, git

`DataSyncProjectContentContributor implements ProjectContentContributor` (`@Lazy` on its facade/service/
project collaborators, for the same construction-cycle reason `AiAgentProjectContentContributor`
documents). Content directory `data-syncs/`, one file per sync at `data-syncs/<name>.json` where `<name>`
is the slug (always a safe file name); only top-level `.json` entries under that directory are read
(`getDataSyncFiles`).

The document (`DataSyncFacade#exportDataSync`, pretty-printed, enums by name, elements in SOURCE,
DESTINATION, PROCESSOR order) carries `exportVersion`, `name`, `title`, `description`, `triggerType`,
`triggerParameters`, `elements`. The generated workflow itself is never exported — it is derived, and
import/pull regenerate it. **Connections are never exported** — a connection id means nothing in another
workspace, same reasoning as the agent document — so an imported or pulled element's `connection_id` is
left null when its component/version/operation changed, blocking the project's publish (naming the sync)
until a connection is picked.

- **Duplicate** (`onProjectDuplicated` → `copyProjectDataSyncs`) stays in the workspace: it copies
  everything, connections included, into new rows with new unique names, new generated workflows in the
  duplicate's draft version, and freshly synced test connections.
- **Import** (`importProjectContent` → `importDataSync(workspaceId, json, projectId)` per file): the
  exported name seeds a unique name, the processor is still validated as the field mapper, elements are
  created with no connection, and the draft is regenerated.
- **Git pull** (`pullProjectContent` → `updateDataSyncFromExport`): each file is matched to a project sync
  first by name, then — for a file whose sync got a suffixed name because the exported one collided
  elsewhere in the workspace — by a **unique** title (`findDataSync`, the agent contributor's `findAgent`
  rule). A match replaces title, description and trigger and upserts each element by kind: an element whose
  component, version and operation are unchanged keeps its `connection_id`; a changed one gets null; a kind
  absent from the file is deleted (so a pulled sync with no processor drops the local mapping). A file that
  matches no sync is imported; a sync with no matching file is left alone, as workflows missing from the
  repository are. Git push needs nothing new — EE `ProjectGitFacadeImpl` already writes every contributor's
  files and excludes generated workflows.

## Client

Three surfaces, all reached through Projects rather than a standalone page:

- **Projects page** (`pages/automation/projects/Projects.tsx`) — the tab strip reads **Workflows (N) |
  Agents (M) | Data Syncs (K)**; `project-data-sync-list/` (`ProjectDataSyncList`, `ProjectDataSyncListItem`
  — title link, "Source → Destination" component line via `describeTrigger`/`dataSyncTrigger.ts`, trigger
  summary, published version, `DataSyncsLeftSidebarDropdownMenu`; `ProjectDataSyncCreationActions`, single
  **New/Create Data Sync** button, no import dropdown). A **Data Syncs filter**
  (`DataSyncsFilterLeftSidebarNav`, items All Data Syncs / Scheduled, `?dataSyncs=all|scheduled`) is
  mutually exclusive with the Agents filter (`?agents=…`) — each nav's links strip the other's param —
  because each filter also picks which tab a row opens on.
- **Project sidebar** (`ProjectsLeftSidebar`, `currentDataSyncId`) — a Data Syncs section under the Agents
  one, with `ProjectDataSyncsList` rows (badge row with source/
  destination component icons, title, "Edited <date>" from the draft workflow's `lastModifiedDate`,
  `DataSyncsLeftSidebarDropdownMenu`).
- **Data sync page** (`pages/automation/project/ProjectDataSync.tsx`, route
  `projects/:projectId/data-syncs/:dataSyncId`, the `ProjectAgent.tsx` shell) — `ProjectsLeftSidebar` plus a
  header (`DataSyncDetailHeader`, built on `AgentDetailHeader`'s shape: `ProjectBreadcrumb` +
  `ProjectItemSelect`, Publish/Deploy publishing and deploying the **project**, version history from the
  project's versions, a Settings menu with Edit/Delete) and `DataSyncWizard` full width below it — no
  separate test panel; the wizard's own Test step is the test surface.

`ProjectItemSelect`'s switcher values are typed (`workflow:<id>` / `agent:<id>` / `dataSync:<id>`) because
agent ids, sync ids and project-workflow ids come from separate sequences that can collide.
`DeleteDataSyncAlertDialog` is the one delete confirmation, used from both the sidebar/Projects-page row
menu and the page's Settings tab; deleting the sync the page is standing on navigates to the project's
first workflow, else to `/automation/projects`.

Data-sync-specific pieces (dialog, row menu, wizard, hooks, utils) stay under
`pages/automation/data-syncs/` — only the list and standalone detail pages moved into `projects/` and
`project/`. The old standalone list page, standalone detail page and standalone deployments page are all
gone; there is no top-level route for any of them any more.

### Deployments page

`ProjectDeploymentList.tsx` gains a **Data Syncs (K)** tab (`useDataSyncDeployments`, grouped by project
deployment id); the Workflows tab additionally excludes the syncs' own workflows (matched by
`workflowUuid` against the syncs' `projectWorkflowUuid` set), beside the existing agent exclusion.
`project-deployment-data-sync-list/` (`ProjectDeploymentDataSyncList`,
`ProjectDeploymentDataSyncListItem`) renders each row's trigger summary, the enable `Switch` on the sync's
`ProjectDeploymentWorkflow`, last execution, and **Run now** — enabled only while both the deployment and
the sync's own row are enabled, mirroring the server-side `DEPLOYMENT_DISABLED` rule above. The Data Syncs
filter on Deployments keeps deployments that deploy a sync and opens rows on the Data Syncs tab.

### Wizard internals (unchanged by the project move)

`data-syncs/` (dialog, row menu, five-step wizard: Trigger, Source, Destination, Mapping, Test). Source and
Destination (`DataSyncElementStep` + `useDataSyncElementStep`) render the operation's real property form —
the same `Properties` renderer + `ClusterElementProvider` + `WorkflowMockProvider` arrangement
`ComponentConfigDialog` uses to host a component's dynamically-resolved inputs outside the workflow editor
— with `useDebouncedSave` sending the WHOLE `parameters` map through `updateDataSyncElement` on every field
or connection edit. Picking a component only resets local picker state; picking an *operation* is what
actually replaces the element row on the server, via `useSetDataSyncElementMutation` (which is also what
triggers the processor-row deletion above when the source/destination side changes). The two mutations are
kept strictly apart so a routine field edit never triggers a mapping drop.

**`elementKindKey` vs `clusterElementsCount` — do not conflate them.** The client's own
`elementKindKey(kind)` (in `dataSyncElements.ts`) returns the same lowercase slot name the generator uses
(`source` / `destination` / `processor`), used to build node names like `source_1`. That is NOT the key the
component-definitions list is filtered by when populating the Source/Destination picker
(`useDataSyncElementStep.ts`): `clusterElementsCount` on `ComponentDefinitionBasic` is keyed by the cluster
element type's **UPPERCASE** name (`SOURCE` / `DESTINATION`), reached via
`convertNameToSnakeCase(elementKindKey(kind))`. A filter written against `elementKindKey`'s own lowercase
output silently matches nothing — no error, just an empty picker — which is exactly the bug an earlier draft
of this feature shipped and a review round caught. `clusterElementsCount` is also only populated when the
component-definitions query passes `clusterElementDefinitions: true` alongside `actionDefinitions: true`
(`useGetComponentDefinitionsQuery` in `useDataSyncElementStep.ts`) — the same two flags `useWorkflowLayout`
passes for the workflow editor's own node browser; `actionDefinitions` alone drops any component that offers
a source/destination cluster element but no regular action.

The Mapping step (`useDataSyncMapping`) is a purpose-built two-column table, not a rendering of the
processor's property tree — `sourceField`/`destinationField` options come from the sibling source/destination
nodes, resolvable only through `WorkflowNodeOptionApi.getClusterElementNodeOptions` (draft workflow id + the
root task node name `dataStream_1` + the processor's own node name `processor_1`), the same call the original
Data Stream editor's auto-map uses. The processor row itself is created lazily — only once both a source and
a destination element exist — and exactly once, guarded by a ref so a re-render or slow in-flight mutation
can't double-create it against the one-row-per-kind unique constraint. The dialog's Data Stream wizard is
untouched — this is a copy.

## Generated workflow

`DataSyncWorkflowGenerator.generate(dataSync, elements)`: `trigger_1` (`manual/v1/trigger` or
`schedule/v1/cron` reading `expression` + `timezone`, default timezone `UTC`) → `dataStream_1`
(`dataStream/v1/stream`) with `clusterElements.source` / `destination` / `processor` named `source_1` /
`destination_1` / `processor_1` (`DataSyncWorkflowGenerator.nodeName(Kind)`). The cluster-element map key is
the `Kind` name **lowercased** (`source`, `destination`, `processor`) — the same key `elementKindKey`
returns client-side, distinct from `clusterElementsCount`'s uppercase key above. Every facade mutation
(`updateDataSyncTrigger`, `setDataSyncElement`, `updateDataSyncElement`, and publish's
`regenerateAndSaveWorkflow`) regenerates the draft in place and re-syncs each element's `connection_id` into
the draft's `WorkflowTestConfiguration` for every `Environment`, keyed `(dataStream_1, <element node
name>)` — the same two-part key the generator emits under `connections`. The client addresses options and
the Test step with `draftWorkflowId` + those fixed names, never by discovery.

## Migrating an existing local database

Moving `data_sync` off its hidden per-sync project and onto ordinary projects, and dropping
`data_sync_tag`, needs a one-time hand-run SQL pass on any local database created before this change — see
"Migration of local data" in `docs/superpowers/specs/2026-09-22-data-syncs-under-projects-design.md` for the
exact statements. It is deliberately never turned into a Liquibase changeset.
