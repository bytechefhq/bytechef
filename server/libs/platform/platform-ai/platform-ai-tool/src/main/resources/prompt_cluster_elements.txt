Some actions contain cluster elements — sub-components nested within a task.
Rules:
- Before building any action that has cluster elements, call getAction(componentName, actionName, version) to get cluster element types.
- Then use searchClusterElements(clusterElementType) for each cluster element type to retrieve all possible options for that type. Not all types need to be implemented.
- Then call getClusterElement(componentName, clusterElementName, version) to retrieve the definition for the task you need.
- Once retrieved, nest the retrieved cluster elements task or tasks inside the action, under clusterElements property, keyed by their type.
- A cluster element's "type" is always "<componentName>/v<version>/<clusterElementName>", built from a component and one of its cluster element names that searchClusterElements or getClusterElement returned, for example "anthropic/v1/model", "inMemoryChatMemory/v2/chatMemory", "dateHelper/v1/getCurrentDate", "csvFile/v1/reader", "script/v1/javaScript". Names are case sensitive. Never use a model name, an action of the component, or a bare "<componentName>/v<version>" as the type.
- Put each element under the key of its own cluster element type (model, chatMemory, tools, rag, guardrails, source, processor, destination, ...). Use an array for a type that allows multiple elements and an object otherwise; getAction on the root tells you which.
- Use the root's native cluster element types for what the request asks for, never a script and a condition around the agent. To block or redact personal data (PII), put "checkForViolations/v1/checkForViolations" (block) or "sanitizeText/v1/sanitizeText" (redact) under the agent's guardrails, with "pii/v1/piiCheck" nested under its own checkForViolations or sanitizeText key.
- Saving the workflow reports a cluster element whose type does not exist or that sits under the wrong key, and saves nothing until you fix it.
- An AI Agent tool's parameters that the agent decides at run time (the numbers to add, the message to post, the record to look up) must be fromAi expressions, for example "firstNumber": "=fromAi('firstNumber', 'NUMBER', {'description': 'The first number to add'})". A fixed value makes the tool always use that value. Use fixed values only for settings the user gave you, such as a Slack channel.
- Work the agent does belongs in its tools; later workflow tasks cannot read a tool's result. When a human must approve what the agent does (for example every Slack post), wrap those tools in an approval gate: put an "aiAgentUtils/v1/approvalGate" element in the agent's tools with parameters {"name": "<what is approved>"} and its own clusterElements {"tools": [the gated tools], "approvalChannels": [the channels]}. For approval in the chat use "chat/v1/chat" as the channel. Never put "approval/v1/requestApproval" or another gate inside a gate.
- "Our knowledge base" means ByteChef's built-in knowledge base: use "knowledgeBase/v1/vectorStore" for RAG (an agent's rag slot holds a "questionAnswerRag/v1/rag" element whose vectorStore slot holds the "knowledgeBase/v1/vectorStore"; a vector store never sits on the agent itself) and the knowledgeBase load element or action for loading documents, unless the user names another store. When knowledge bases exist, let the user pick one for knowledgeBaseId with selectClusterElementPropertyOption. Use the built-in knowledge base even when none exists yet: only then leave knowledgeBaseId unset and tell the user to create one. Never switch to pgVector, Pinecone or another store because the knowledge base id is unknown. When the knowledgeBase component is not found, the built-in knowledge base is turned off on this server: use the vector store the user named, otherwise ask which one to use, and never pick one silently.
- A cluster element property with dynamic options (its definition reports "lookupRequired": true, for example knowledgeBaseId on "knowledgeBase/v1/vectorStore") is filled by letting the user pick a value with selectClusterElementPropertyOption, passing the element's componentName and clusterElementName. When you only need to check the values, look them up first with lookupClusterElementPropertyOptions. Never leave such a property empty silently and never invent an id; if you lack these tools, leave it empty and name it in your answer.
- The Approval component's "approval/v1/requestApproval" action pauses the workflow until a human decides. It delivers the request itself through the channels nested under its own clusterElements {"approvalChannels": [...]}, for example "slack/v1/slack", "email/v1/email", "chat/v1/chat"; every channel carries the approve and reject links. Never send the request with separate Slack or email tasks. Its output already has "approved" (boolean) and "comment"; add form inputs only for extra fields the approver must fill in. Branch on ${<task name>.approved} after it.
Example of tasks with cluster elements:
"tasks": [
  {
    "label": "task with cluster elements",
    "name": "taskName_1",
    "type": "<action type>",
    "parameters": { ... }
    "clusterElements": {
      "clusterElementTypeObject": {
        "label": "<custom label>",
        "name": "<clusterElementTypeName>_1",
        "type": "<componentName>/v<version>/<clusterElementName>",
        "parameters": { ... }
      },
      "clusterElementTypeArray": [
        {
          "label": "<custom label>",
          "name": "<clusterElementTypeName>_1",
          "type": "<componentName>/v<version>/<clusterElementName>",
          "parameters": { ... }
        }
      ]
    }
  }
]
