# AI Gateway — Experiments

Replay curated datasets through the AI gateway and compare outputs across prompt versions / models. Combined with the dataset module and `AiEvalRule` evaluators, this enables prompt regression testing: *"did my v2 prompt drop faithfulness more than 5% on the golden set?"*

## How it Works

1. **Create a dataset** (see the sibling [dataset module](../automation-ai-gateway-dataset/README.md)) and freeze a version as your golden reference.
2. **Trigger an experiment** — `POST /api/ai-gateway/v1/experiments` with `{ datasetVersionId, promptVersionId, model }`. The gateway persists the experiment in PENDING state and dispatches execution via `@Async`.
3. **Each dataset item replays through the gateway** — `AiExperimentExecutor` parses `item.input` into an `AiGatewayChatCompletionRequest` and calls `AiGatewayFacade.chatCompletion(...)`. The replay goes through the same routing, cost, and trace machinery as any production call — producing a real `AiObservabilityTrace` with `source = EXPERIMENT`.
4. **Evaluation scores the results** — after each run completes, `AiEvalExecutor.evaluateTrace(traceId, workspaceId, EXPERIMENT_TRACE)` dispatches any eval rules scoped to experiment traces. External evaluators (RAGAS etc.) can also score these traces via the [External Scores API](../README-external-scores.md).
5. **Compare via GraphQL** — `experimentComparison(experimentIds: [ID!]!)` returns per-item diffs + per-experiment score averages.

## Operator console UI

The LLM Gateway tab in the workspace UI has an **Experiments** view that lists workspace-scoped experiments via `aiExperiments(workspaceId)`, lets the operator multi-select rows and click **Compare** to load the side-by-side comparison view, or click **View runs** on any row to drill into the per-run detail (status, latency, cost, error message, source dataset item) via `aiExperimentRuns(experimentId)`. A **Datasets** view in the same tab surfaces dataset → version → item drill-down so an operator can spot-check the golden set the experiment ran against without leaving the console. Production traces in the **Traces** view get a "this trace was generated by an experiment replay" banner with a back-pointer to the source experiment / run / dataset item, computed via `aiExperimentRunByTraceId(traceId)`. All three lookups are workspace-scoped and enforce the same uniform-error contract as `experimentComparison`: missing-id and wrong-workspace surface as a single 403 payload to prevent cross-tenant id enumeration.

The UI is **read-only**. Operators inspect; experiments and datasets are still curated programmatically via the SDK / public REST API (this module's `POST /api/ai-gateway/v1/experiments` and the dataset module's `/datasets` endpoints). Mutating from the workspace UI is intentionally not supported — most experiments are fired by CI on every PR, not hand-rolled in the console.

## Endpoints

### POST /api/ai-gateway/v1/experiments — Trigger an experiment

Required: `Authorization: Bearer <gateway-api-key>`, `X-ByteChef-Workspace-Id: <workspace id>`, `Content-Type: application/json`.

Body:

```json
{
  "datasetVersionId": 7,
  "promptVersionId": 42,
  "model": "gpt-4o",
  "metadata": { "notes": "baseline run with v2 prompt" }
}
```

Response: `202 Accepted` with:

```json
{
  "id": 123,
  "workspaceId": 42,
  "datasetVersionId": 7,
  "promptVersionId": 42,
  "model": "gpt-4o",
  "status": "PENDING",
  "createdDate": "...",
  "startedDate": null,
  "completedDate": null
}
```

The experiment status progresses `PENDING → RUNNING → (COMPLETED | FAILED)`. Poll `GET /experiments/{id}` for progress.

### GET /api/ai-gateway/v1/experiments/{id} — Status + summary

Returns aggregate run counts + lifecycle timestamps:

```json
{
  "id": 123,
  "workspaceId": 42,
  "datasetVersionId": 7,
  "model": "gpt-4o",
  "status": "COMPLETED",
  "totalRuns": 10,
  "completedRuns": 9,
  "failedRuns": 1,
  "createdDate": "...",
  "startedDate": "...",
  "completedDate": "..."
}
```

### GET /api/ai-gateway/v1/experiments/{id}/runs — Per-item run details

```json
[
  {
    "id": 501,
    "experimentId": 123,
    "datasetItemId": 7001,
    "traceId": 9001,
    "status": "COMPLETED",
    "latencyMs": 842,
    "cost": 0.002430,
    "errorMessage": null,
    "createdDate": "..."
  }
]
```

### GraphQL — `experimentComparison(experimentIds: [ID!]!)`

Returns a cross-experiment view:

```graphql
{
  experimentComparison(experimentIds: [123, 124]) {
    experiments {
      id model totalRuns completedRuns failedRuns totalCost averageLatencyMs
    }
    rows {
      datasetItemId
      runsByExperiment {
        experimentId runId traceId status cost latencyMs
        scores { name value stringValue dataType }
      }
    }
    aggregateScoreDeltas {
      scoreName
      deltas { experimentId average count }
    }
  }
}
```

Authorization: `ROLE_ADMIN` (cross-workspace aggregation). Only NUMERIC scores contribute to `aggregateScoreDeltas`; BOOLEAN and CATEGORICAL are included per-run in `runsByExperiment[].scores` but not aggregated.

## Error Responses

| Status | Reason |
|--------|--------|
| `400 Bad Request` | Missing/non-numeric `X-ByteChef-Workspace-Id`, malformed JSON, or `datasetVersionId` missing |
| `403 Forbidden` | Experiment belongs to a different workspace (`AiScoreWorkspaceBoundaryException`) |
| `404 Not Found` | Experiment id does not exist |

## Persistence Model

Two new tables (migration `00000000000007_ai_experiment_init.xml`):

- `ai_experiment` — one row per experiment definition. Columns: `workspace_id`, `dataset_version_id`, `prompt_version_id`, `model`, `status` (INT ordinal: `PENDING=0, RUNNING=1, COMPLETED=2, FAILED=3`), `metadata` (CLOB), lifecycle timestamps.
- `ai_experiment_run` — one row per dataset item in the experiment. Links to the synthetic `ai_observability_trace` via `trace_id`. Columns: `experiment_id`, `dataset_item_id`, `trace_id`, `status`, `latency_ms`, `cost`, `error_message`.

New trace source: `AiObservabilityTraceSource.EXPERIMENT` (ordinal 3, append-only) — distinguishes synthetic experiment traces from production traffic for retention/analytics filtering.

## Execution Model — @Async (not atlas-coordinator)

Each `POST /experiments` call returns immediately after persisting the experiment. `AiExperimentExecutor.execute(experimentId)` is annotated `@Async("aiExperimentTaskExecutor")`, so the loop over dataset items runs on a bounded `ThreadPoolTaskExecutor` (corePool=2, max=8, queue=100) registered as the named bean `aiExperimentTaskExecutor` in `AiGatewayExperimentAsyncConfiguration`. The pool is intentionally NOT registered as the global `@Async` executor — other modules continue to use Spring's default executor — so a noisy experiment workload cannot starve unrelated `@Async` callers in the same JVM.

**Known limitations** of the current `@Async` approach:
- **Cancellation is best-effort** — the stop flag is checked at iteration boundaries; an in-flight `chatCompletion` finishes before the loop exits.
- **Orphan recovery fails stale runs rather than resuming them** — JVM restarts mid-experiment leave PENDING/RUNNING runs that the startup hook transitions to FAILED with diagnostic messages; users re-trigger.
- **Single-JVM execution** — `@Async` runs in the gateway service's process. Horizontal scale across worker nodes is a future migration (atlas-coordinator considered + rejected for v1; resilience plan documents the alternative path).

**Resilience hardening (resilient `@Async`, not atlas migration):** the three concrete pain points with the current `@Async` executor — cancellation, retry on transient gateway failures, orphaned `RUNNING` runs after JVM restart — are addressed by targeted small fixes:

- **Cancellation** — `stop_requested` column on `ai_experiment` + `POST /experiments/{id}/stop` endpoint + per-iteration check in the executor.
- **Per-run retry** — Spring `RetryTemplate` around `AiGatewayFacade.chatCompletion(...)` with exponential backoff (250ms → 2000ms, 3 attempts, network-adjacent exceptions only).
- **Orphan recovery** — `@EventListener(ApplicationReadyEvent.class)` scans for `RUNNING` experiments older than 10 minutes and fails their unfinished runs with a diagnostic message. The runner is opt-in via `bytechef.ai.gateway.experiment.orphan-recovery.enabled=true` so multi-instance deployments can pick a single designated node.

A full atlas-coordinator migration was considered and rejected — the three fixes deliver the operationally real benefits (restart durability, retry, cancellation) without the architectural overhead of a new task-dispatcher module, workflow registration ceremony, or feature-flagged rollout across two executor paths.

## Relationship to `AiEvalRule`

`AiEvalRule.target` (added in Phase 3 Task 3.1) filters which rules match which traces:

| Target | Scope |
|--------|-------|
| `LIVE_TRACE` (default) | Live production traces only |
| `EXPERIMENT_TRACE` | Synthetic traces from experiment replay only |

Existing rules default to `LIVE_TRACE` (ordinal 0), preserving pre-Phase-3 behavior. Create experiment-scoped rules by setting `target = EXPERIMENT_TRACE` when defining the rule.

Experiment runs dispatch `AiEvalExecutor.evaluateTrace(traceId, workspaceId, EXPERIMENT_TRACE)` on completion — so experiment-scoped rules only score experiment traces, and live-scoped rules only score production traffic. An eval-dispatch failure does NOT flip the experiment run into FAILED (the replay itself already succeeded by that point).

## Known Limitations

- **Replay input shape** — items are parsed as JSON into `AiGatewayChatCompletionRequest`. Items produced by promote-from-trace paths may carry the trace's full tags object; the executor forwards tags verbatim (with `workspace_id` injected) so routing policies that read tags still apply during replay.
- **Cost/latency totals** come from the `ai_observability_trace` row after persistence, not from the gateway response directly. If trace lookup fails post-replay, the run still marks COMPLETED but `traceId`/`cost`/`latencyMs` remain null.
- **GraphQL `aggregateScoreDeltas`** returns per-experiment averages only; the caller computes pairwise deltas. NUMERIC-only aggregation; BOOLEAN/CATEGORICAL deferred.
- **No partial-progress resume** if the JVM restarts mid-experiment — orphan recovery fails stale runs rather than resuming them, so users re-trigger from scratch (see @Async limitations above).
- **No microservice deployment support** — the module ships an in-process `@Async` executor only; remote-client stubs (the `@ConditionalOnEEVersion` pattern used by other EE microservice modules) have not yet been scaffolded, so distributed deploys are unsupported until that work lands.
